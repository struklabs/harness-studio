# Security Model

This document describes Harness Studio's security model: where secrets are kept, which network and permission rules apply, and which areas matter for security. To report a vulnerability, see [SECURITY.md](../../SECURITY.md) in the repository root.

## Archive Extraction

Harness-managed runtime, ONNX, Python-environment, and RAG archive extraction rejects symlinks, absolute paths, and `..` paths; it never overwrites existing files and removes SUID, SGID, and sticky permission bits. Application updates use the upstream Tauri updater and require signature verification before extraction.

## Scope

Findings in these areas matter in particular:

- **Keychain secrets:** The Hugging Face token (pasted, or the "Sign in with Hugging Face" OAuth session) and the llama-server API key are kept in the OS keychain; they must not leak to the UI or the command line.
- **Sign in with Hugging Face (OAuth):** see the "Hugging Face account" section below.
- **Third-party tool configurations:** Writes to the OpenCode, Open Design, and Continue configs are done with a `.bak` backup, an atomic write, and a preview before applying. Overwriting a corrupt config counts as a vulnerability.
- **Downloader:** HTTPS enforcement, checks against local/private network access (SSRF) and escape through redirects, and SHA-256 verification.
- **Runtime archive:** The downloaded llama.cpp archive is verified with the GitHub SHA-256 digest; if it does not match, it is not extracted and is deleted. If the digest is missing or invalid, nothing is downloaded and `runtime.integrity_unverified` is returned; the UI shows the archive name, size, and source URL and asks for explicit confirmation. The background automatic update never installs an archive that cannot be verified.
- **Third-party runtimes (Settings > Runtime, `harness runtime`):** The download address of a runtime installed from a GitHub release can only be `https://github.com/<owner>/<repo>/releases/download/...`, and every archive is verified with the GitHub SHA-256 digest; if there is no digest, installation is possible only with explicit confirmation (`allow_unverified`, a checkbox in the UI, `--allow-unverified` in the CLI), and the record is kept with an "approved, unverified" trust level. At install time and when a local folder is added, a SHA-256 manifest of all code files (exe/dll/so/dylib/metal, `llama-*`, `ggml*`) is produced. On every launch, size and modification time are compared against the manifest; if a file has changed or is missing, the server is not started (`runtime.changed`). `verify` re-hashes the files; accepting a change is possible only for local-folder runtimes (a GitHub install must be reinstalled). Local folders are used in place, and Harness never modifies or deletes them (removal only deletes the record; if it was copied, the copy is deleted). In the Control API, add/verify/remove require the `admin` scope; a runtime in use cannot be removed without `--force` (`runtime.in_use`). Forks (for example PrismML) are not official llama.cpp: the trust decision is the user's.
- **Harness Control API:** token validation, scopes, permissions on the session token file, Host/CORS checks (see below).
- **Protected llama-server parameters:** `--host`, `--port`, `--api-key`, `--api-key-file`, `--cors-origins`, `--tools`, `--agent`, and `--mcp-*` cannot be given through `custom_args` or the parameter catalog (including the `--x=y` and `--x_y` spellings). The `LLAMA_ARG_*` environment variables of the same flags are removed from the child process.

## Bundled Modules

The Modules screen installs only bundled backend definitions; it never downloads UI or JavaScript. The first optional module, Speech Recognition, reuses the hash-pinned `transcribe-cpp` Python environment installer and the existing Playground Speech screen. Install explicitly approves the displayed download, managed-file, and backend-process permissions; these describe existing backend privileges, not a new sandbox or per-permission enforcement layer.

Module inspection requires `read` in the Control API; install, cancel, and removal require `admin`. Cancellation uses process-tree cleanup. Installation state and component owners are saved atomically in `config/modules.json`; interrupted installations can be retried. Removal refuses a detected running speech worker and deletes only the managed speech environment when no other module owns it. Models, outputs, datasets, and shared uv/Python support tools are retained (other existing Python engines also use those tools). Disk and download values are estimates, including shared dependencies; module update/rollback and free-space preflight remain W3 work. Training, Automations, and REA are planned and cannot be installed.

Agents uses the official Hermes source installer with explicit user approval, without a fork or downloaded UI. This installer is upstream-owned and is not a hash-pinned Harness runtime. Connection/task commands are desktop IPC only. Connect issues an inference-only named token restricted to one selected model and chat/model-list endpoints; its value stays in the private Hermes config and never enters IPC or process arguments. The prior config is backed up privately and restored atomically; external edits are never silently overwritten. Disconnect revokes even when restore encounters a conflict. Harness tasks use the official Python API in a temporary home with an empty tool allowlist, no user rules/memory/hooks/skills/MCP configuration, and a cleared credential environment. This is not OS sandboxing of upstream code. Stop kills only the Harness-owned task process tree. Module removal retains the upstream installation and user data. See [Hermes Agent](HERMES_AGENT.md) for compatibility, open-loopback policy limits, and recovery.

## Harness Control API

The local management API (`/api/harness/v1`, default `127.0.0.1:11500`) is off by default; it is turned on in Settings > Developer > Control API.

- **Token required:** Every request except `/health` needs `Authorization: Bearer <token>`. A request with no token or an invalid one gets `401 api.unauthorized`, and insufficient scope gets `403 api.insufficient_scope`.
- **Session token:** Regenerated at every start (256 bits). It lives in the `<data directory>/api-token` file; only the current user can read the file (a protected ACL on Windows, 0600 on Unix). The file is deleted when the API closes.
- **Named tokens:** Created with the scopes `read`, `inference` (access to the gateway), `models:write`, `downloads:write`, `servers:write`, `servers:control`, `conversations` (reads/exports/compacts chat history; not part of `read` because it is private content), `tools` (runs Harness tools: file, shell, network; not part of `read`; the saved permission policy applies, and `approved` and choosing the working folder require `admin`), and `admin`. The value is shown only once, at creation; only a salted SHA-256 digest is kept on disk. Revocation takes effect immediately. Token management and the "Open Anyway" confirmation are done only with the `admin` scope.
- **Narrow scopes:** `servers:control` starts, stops, and retries servers and loads/unloads models; it cannot change or delete definitions and profiles. `downloads:write` starts, pauses, resumes, and cancels downloads; it cannot delete models. `servers:write` and `models:write` cover these respectively; every write scope also covers read. Token editing (`PATCH /tokens/{id}`) is done only with `admin` and does not change the token value; a change takes effect on the next request.
- **Token file:** `config/api_tokens.json` schema v2 (policy fields). The older version's file is migrated on first launch, and an `api_tokens.json.bak-v1` backup is taken before migration; old tokens remain unrestricted.
- **Binding:** An address other than loopback cannot be started without the "Allow network access" setting and at least one named token. While on loopback, the `Host` header can only be `127.0.0.1`, `localhost`, or `[::1]` (DNS rebinding protection).
- **CORS:** Off by default (browser pages cannot read the API). Only explicitly written `http(s)://host[:port]` origins are allowed; `*` is not accepted.
- **Origin check:** A request that carries an `Origin` header (a browser) is accepted only from the Harness window or an origin on this CORS list; anything else, including `Origin: null` and preflights, gets `403 api.forbidden_origin` before any route runs. A "simple" cross-site POST needs no preflight, so CORS headers alone would not stop its side effects. Requests without `Origin` (CLI, curl, SDKs) are unchanged.
- **Network rules:** Every server start made through the API goes through the same `prepare_launch` rule; a keyless network bind is rejected with `409 network.lan_without_key`.
- **Responses:** No response or OpenAPI schema contains an API key (only `api_key_set` and the keychain reference).
- **Single owner:** A single process manages the data directory at a time (`instance.lock`); the API runs only in the owner process and writes its address to `instance.json`.
- **Shutdown:** `POST /shutdown` requires `admin` and works only on a headless owner (`harness serve`); the GUI returns `409 api.shutdown_unsupported`.
- **CLI (`harness`):** Connects to the local instance by reading the session token file; since the file is open only to the user, other users cannot connect. A remote instance needs a named token (`HARNESS_TOKEN`; the value is not shown in help output). Temporary instances bind only to `127.0.0.1` and a random port, and delete the session token file when the command ends. `profile export` does not write the key reference and the binary path. `HARNESS_MEMORY_SECRETS=1` makes it use an in-memory secret store instead of the keychain (for tests).

## Headless Browser Administration (0.2 W5, Slice 1)

`harness serve` serves the bundled Svelte static build on the Control API listener (see [CLI setup](CLI.md#browser-management)). Desktop IPC and the Gateway keep their existing authentication boundaries. The browser shell exposes servers, Library/definition loading, Hugging Face downloads, basic launch defaults, and named tokens; native pickers, folder reveal, and local integrations are omitted. Paths and operations refer to the server machine.

- **Bootstrap:** Until an administrator exists, the terminal prints a random 256-bit one-time setup code, valid for 15 minutes. It is held only in memory, never sent to the browser or stored in ready JSON. Successful setup atomically saves an Argon2id password hash with a random salt to private `config/browser-admin.json` and consumes the code. Minimum password length is 12 bytes. Restart generates a fresh code only while setup is incomplete. This slice has one administrator; multiple users/roles are later work.
- **Sessions:** Login rotates the cookie identifier. A host-only `__Host-harness` cookie is `Secure; HttpOnly; SameSite=Strict; Path=/`, with an eight-hour absolute lifetime. At most 64 sessions are active. Sessions and CSRF secrets live only in memory and are invalidated by listener/process shutdown. No bearer token is exposed to JavaScript or browser storage. Logout revokes the current session; Settings revokes all browser sessions. Admin bearer clients may also call `DELETE /api/harness/v1/browser/sessions`. Cookie-authenticated SSE connections, including logs and telemetry, close within one second of expiry/revocation.
- **CSRF/origins:** Cookie-authenticated writes require an exact same-origin `Origin` and a session-bound `X-Harness-CSRF` header, obtained from the same-origin session endpoint. Login/setup require the same origin too. Cross-site fetches are rejected, including origins on the API CORS allowlist; CORS never grants cookie administration. Bearer clients continue through existing scope checks. Browser administrators have the existing `admin` scope with a distinct browser principal; they cannot read local-owner-only server API keys, even on loopback. The scope includes server file/process authority; sign-in explicitly explains this grant.
- **Abuse controls:** Failed setup/login attempts use a process-wide exponential backoff (2-64 seconds) with `429` and `Retry-After`. Password verification is serialized, off the async executor; spoofed IP/proxy headers cannot bypass the backoff. The global limit deliberately trades availability under attack for bounded password work. Restart resets the limiter. Authentication responses and API data use `Cache-Control: no-store`.
- **TLS:** User-supplied PEM certificates/keys apply to the entire Control API/static UI listener. Network binds require a configured exact `public_origin`, existing network approval, and a named API token. Proxy headers are never trusted. Plain HTTP on a non-loopback bind prints a warning and refuses password login; use direct TLS. Loopback HTTP is for local development in browsers that accept Secure localhost cookies. Gateway TLS and ACME automation are outside this slice.
- **Recovery:** Restart revokes sessions without changing the password or named tokens. With local owner access, stop the server and move the private administrator hash aside to repeat setup; protect the replacement code as an administrator credential. Named API tokens remain independently scoped and revocable.

## Harness Gateway

The single endpoint (default `127.0.0.1:11435`) is off by default; it is turned on in Settings > Gateway or with `harness serve --gateway`. It runs only in the process that owns the data directory.

- **Loopback:** The default address is `127.0.0.1`; no token is required (like Ollama/LM Studio, for local clients). If `require_token` is turned on, a token is required on loopback too. While on loopback, the `Host` header can only be loopback (DNS rebinding).
- **Network:** An address other than loopback cannot be started without the "Allow network access" setting and at least one named token with the `inference` scope (`gateway.network_without_token`); on a network address a token is always required. There is no keyless LAN.
- **Accepted tokens:** A named token with the `inference` or `admin` scope, or the gateway client token, via `Authorization: Bearer` or `x-api-key`. Other scopes get `403`, and an invalid token gets `401`. On an open loopback gateway without tokens, the placeholder keys that clients send are ignored.
- **Token policy:** A named token can be given allowed model alias patterns and endpoint groups. The order: identity → endpoint (`403 endpoint_not_allowed`) → rate limit → model resolution → model permission (`403 model_not_allowed`). Model lists and the "available models" suggestion do not include aliases the token cannot see. The gateway client token and the llama-server key are unrestricted.
- **Rate limit:** Requests per minute, tokens per minute, and concurrent requests per token. When exceeded, `429` + `Retry-After` (the request does not reach the server and no model is loaded). The per-minute request and token counters are written to `analytics.db` every 2 s, survive a restart (an expired window is reset), and are shared across Harness instances that share the same data folder; the concurrency limit is in-process. It is a budgeting tool, not an abuse limit.
- **Open-loopback warning:** On a loopback gateway that does not require tokens, a client that sends a token is subject to its policy, but a request without a token is subject to no restriction. For restrictions to be binding, "Require a token on this computer too" (`require_token`) must be turned on; the UI warns in this case.
- **Client token:** `hsg_` + 256 bits, renewed at every start; used by Harness's own clients (Playground, CLI). It lives in the `<data directory>/gateway-token` file (open only to the user, the same protection as api-token) and is deleted when the gateway closes.
- **llama-servers:** Servers that the gateway loads JIT always bind to `127.0.0.1`; the llama-server API key is never sent from the gateway to the client, and the gateway adds it upstream.
- **CORS:** The origins of the Harness window and explicitly written `http(s)://host[:port]` origins; no `*`.
- **Origin check (gateway port and Ollama port):** One middleware in front of every route, including OPTIONS preflights. A request with an `Origin` header is accepted only if it is the Harness window (`tauri://localhost`, `http(s)://tauri.localhost`, the dev server) or on the "Allowed browser origins" list; every other origin, `Origin: null` and a cross-site request without `Origin` (`Sec-Fetch-Site: cross-site`) get `403 forbidden_origin`, before the body is read, a worker is resolved or a model is loaded. This closes the "simple" cross-site POST (multipart, urlencoded, `text/plain`) that a web page can send to `127.0.0.1` without a preflight and that would otherwise load models and use compute even though the page cannot read the answer. An allowed origin keeps working even when the browser marks the fetch cross-site (e.g. Open WebUI on another port). Requests without `Origin` (curl, SDKs, Ollama/OpenAI clients) and the token rules are unchanged.
- **Limits:** Request body at most 64 MiB, a bounded queue per definition, a request timeout. Only a metadata event is published per request and written to `analytics.db`; content is stored only if content recording is on in its definition (below).
- **Ollama-compatible API:** `/api/*` is subject to the same token rule (Ollama clients do not send tokens; on a gateway that needs a token, the client's `Authorization` header must be set). Listening on the Ollama port (11434) is off by default, binds to the same address as the gateway, and never disables a program running there (real Ollama included); if Ollama is installed (even if it is not running), it does not take this port. `/api/pull` downloads only `hf.co/...` names and only when "Allow downloads through /api/pull" is on (off by default); a local process that reaches the tokenless loopback gateway therefore cannot start a download without permission.
- **`/metrics`:** The combined Prometheus output is subject to the same token rule as `/v1/models` (open on tokenless loopback, token required on the network). It carries no content or secrets: model aliases, endpoint paths, error codes, server ids, and numbers.

## Stored Responses (`previous_response_id`)

The gateway's `/v1/responses` endpoint is stateful like OpenAI's: if `store` is not sent it counts as `true`, and the request's input items and the whole response (text, tool calls, tool results) are written **as plain text** to `<data directory>/state.db` (the `gateway_responses` table) on this computer. It is separate from analytics content recording (per definition, off by default): the purpose of this feature is to store the conversation.

- **Who can read:** A stored response belongs to the named token that created it; Harness's own client (`harness`) and callers without a token (`anonymous`, only on a loopback gateway that does not require tokens) are separate scopes. A response of another scope gets the same 404 as an unknown id for `GET`, `DELETE`, `input_items`, and `previous_response_id`. On an open tokenless loopback gateway, every local process on this machine shares the `anonymous` scope; to separate them, "Require a token on this computer too" must be turned on.
- **Retention:** 30 days from last use, at most 1000 responses and 100 MiB (Settings > Gateway > Stateful Responses). When a limit is exceeded, the least recently used are deleted. The pages of deleted rows are zeroed; "Delete All" also truncates the WAL file.
- **Turning it off:** Per request with `"store": false` (the response is never written and cannot be retrieved later), or by turning off Settings > Gateway > "Store responses" (`settings.gateway.responses.store`); while off, new responses are not stored, and older ones remain until they expire or "Delete All".
- Stored content does not enter the event path, logs, or OTLP; it cannot be read through the Control API (only the gateway endpoints, with its own token).

## Request Analytics and Content Recording

The metadata of every request that passes through the gateway is written to `<data directory>/analytics.db` (SQLite, separate from `state.db`).

- **No content by default:** What is recorded is time, model/alias, client label, `User-Agent`, `X-Harness-Client`, the token **name** (not the value), endpoint, status, error code, token counts, durations, context fill, VRAM/RAM peak, and backend. The prompt, messages, tool arguments, and response text are not written. A real end-to-end test (`analytics_e2e`) verifies this by searching the file bytes: the unique marker in the prompt and in the model's response is not in the `analytics.db`, `-wal`, and `-shm` files.
- **Content recording is per definition and optional:** If "Record request content" (`capture_content`, off by default) is turned on in the Model Definition window, the body and response of the requests to that definition are stored as plain text in a separate table (`request_content`). The retention period is in the definition (`content_retention_days`, 7 days if empty, at most 3650). Cleanup: `data:` URIs (base64 images/audio) are replaced with a size note, and each side is cut at 256 KiB. Content never enters the event path (`/events`) or the logs. The UI tells you when you turn it on that plain text will be written to disk.
- **Deletion really deletes:** `secure_delete` is on for the connection; expired content and rows deleted with "Delete Analytics" are overwritten, and then the WAL is truncated (`wal_checkpoint(TRUNCATE)`). An end-to-end test verifies that the marker of expired content does not remain in the files.
- **Retention:** Raw rows are kept for 30 days by default (Analytics > Retention settings, 1–3650), and then converted into daily totals (counts without content) and deleted. "Delete Analytics" deletes all rows, totals, and content; it does not affect conversations. Recording can be turned off entirely (`settings.analytics.enabled`).
- **Access:** In the Control API, `GET /analytics/summary`, `/analytics/requests`, `/analytics/requests/{id}`, and `/metrics` require the `read` scope. `/analytics/requests/{id}` returns recorded content; turn content recording on only for definitions where you trust the clients to which you give this scope.
- **Tool compatibility:** Unsupported tool types are not dropped silently; there is an explicit 400, or ignoring with explicit per-definition permission (the `X-Harness-Compat` header and an event record).

## OpenTelemetry (OTLP) Export

- **Off by default:** Unless it is turned on, no connection is made and nothing is sent. The feature is behind the `otel` cargo feature; a build without it contains no network code at all. OTLP/HTTP uses the same HTTP client as the application's other requests (reqwest 0.12, the operating system's TLS and root certificates). OTLP/gRPC (tonic + rustls/ring, system roots) exists only in builds compiled with `otel-grpc`; gRPC cannot be selected in the default builds (`otel.grpc_not_built`).
- **Headers:** The values of collector headers (for example `authorization`) are kept in the OS keychain (`otel-headers`); only their names appear in `settings.json` and in API/GUI responses.
- **Content:** Spans and, if separately enabled, `/v1/logs` request logs carry metadata (model, alias, token **name**, client label, endpoint, status, error code, durations, token counts). The log signal is off by default. Prompt and response text is added only if "Send content too" is on **and** content recording is on in that model definition (truncated to 16 KB). Tests against a real collector verify that the prompt marker is not in the trace and log OTLP bytes when content recording is off.
- **Distributed trace:** Only a `traceparent` in W3C version 00 form, with lowercase hexadecimal and trace/span ids that are not all zero, is accepted; an invalid header is ignored. The accepted remote parent and an optional valid `tracestate` are attached to the exported server span; the log record carries the same trace/span ids.
- **Changing and testing** (`PUT /otel`, `POST /otel/test`) are done only with the `admin` scope; the test sends data to an address supplied by the caller. Reading (`GET /otel`) requires `read`.

## Tool Engine (`harness_core::tools`)

Tools (file read / write / search, shell) let the model do something on the user's machine; the rules live in the core, and every surface (Control API, CLI, Playground, MCP, gateway) goes through the same service.

- **The class is fixed, the policy is the user's:** Each tool's permission class (safe / restricted / dangerous) is set in the registry; the model cannot change the class through arguments or the call format. The policy (`settings.tools`: off / ask every time / allow trusted tools / allow all) and the trusted list are the user's setting alone. The default is "ask every time": every non-safe call asks for approval. "Off" is not opened even with approval.
- **The API cannot ask:** In the Control API, a call that needs approval returns `403 tools.approval_required` and an off policy returns `403 tools.disabled`. Running, changing the policy, and the tool log require the `admin` scope (listing and reading the policy require `read`). `approved` in the body is only for a client that really asks the user (the CLI); it gives no new authority to a token that is already `admin`, since such a token can loosen the policy anyway.
- **Working-directory scope:** File tools work within a single directory tree. A path is first cleaned lexically (`..`), and then, after the operating system resolves links, it is checked that it stays within the root (an absolute path, a symbolic link, a Windows junction, the deepest existing ancestor of a path to be written that does not yet exist). Listing does not follow links. A call with no working directory does not guess and fails with `no_workspace`. **The shell is not limited by this scope:** `exec_shell_command` starts in the working directory but can do anything the user can; this is why it is in the dangerous class.
- **Playground:** The approval decision is made in the core; the UI shows the approval prompt only if the core says `ask`, and passes `approved` only for that call. "Always approve in this session" is held only in memory in that window (the persistent policy does not change, and it goes away when the app closes) and cannot override an "off" policy. Persistent trust is given only in Settings > Tools, visibly. A call the user rejects does not run and is logged as `approval_required`.
- **Limits:** Every call is subject to a timeout (default 120 s, 1-60 s for the shell), a result size (16,000 characters), and cancellation. A timeout, cancellation, or the call being dropped (the client disconnected) kills the shell's entire process tree (a Windows Job Object, a Unix process group).
- **`git` is not run:** The search tools read `.gitignore` files themselves; an external `git` is not used because a repository's `.git/config` could make a `git` call run a program.
- **Tool log:** Every call (denied ones included) is written to `analytics.db` (client, model, tool, arguments, duration, result length, network target). Long argument texts (file content, scripts) are replaced with their length; the result text is not stored. If analytics recording is off, the tool log is not written either.
- **Network tools:** `fetch_url` and a user-addressed SearXNG accept only HTTP(S) (the host:port that the user configured for SearXNG may be local/LAN; this exception does not apply to redirects or URLs given by the model); credentials inside a URL are rejected. Every target is resolved through DNS, and if even one of the answers is a private address in loopback/private/link-local/ULA/unspecified/multicast/CGNAT (100.64/10) or IPv4-embedded IPv6 (::ffff:, NAT64) forms, the call stops; reqwest is pinned to the verified addresses, the system proxy is not used, and every redirect passes the same check again. This prevents DNS rebinding and localhost/metadata redirection. Download is limited to 2 MiB and five redirects; binary content is not run or saved.
- **Web search secrets:** The Brave and Tavily keys are in the OS keychain under the account `web-search:<provider>`. `settings.json` carries only the provider and the SearXNG address; the API/GUI return only `api_key_set`. A key is never a tool argument, a tool-log entry, or error text. SearXNG sends the query to the server the user chose; the model cannot choose the provider; the responding server is learned from the `source` field in the result. The keyless option sends the query in the order DuckDuckGo → Bing → Mwmbl → DuckDuckGo Lite → Wikipedia (the query goes to these sites; the last is an encyclopedia only).

### Tool Package Network Permissions

Installed/generated tools use three explicit `permissions.network` scopes: `[]` (No Network Access), `["*"]` (Entire Internet, public hosts only), or a domain list (Only These Domains). Existing empty lists remain denied; existing domain lists retain their scope. The builder defaults to Entire Internet; the user's selection is the generation upper bound, and excessive requests are rejected for correction. Network/file permissions still require explicit installation approval, including automatic tools; Entire Internet is named in the permission summary.

Every real HTTP request and redirect checks the scope, rejects Harness ports (default and configured Control API/gateway/Ollama listeners, the automatic server port range, the Dashboard profile port, and running server ports), resolves DNS, and refuses the host if any answer is loopback, private/RFC1918, link-local/metadata, CGNAT, IPv6 ULA, or another blocked local range. Connections are pinned to the validated addresses with system proxies disabled. The wildcard never bypasses these checks. Offline test mocks grant no real network access.

## Harness MCP Client (`harness_core::tools::mcp_client`)

Harness connects to the MCP servers in `mcp_servers.json` itself and offers their tools to the model. A local (stdio) server means running a program on this computer with the user's privileges; a remote (HTTP) server sends tool results and arguments to a third party.

- **Adding is approval:** A stdio server runs only when the user adds it (the form or the import screen; both show the command and arguments and carry a "only add a program you trust" warning). There is no server that is discovered and started on its own: the Claude Code, Codex, Cursor, and LM Studio configurations are only read, and are not imported unless the user selects them. The Control API `GET /tools` (`read`) starts configured servers on the first call; these are already programs the user added.
- **The server's declaration is not trusted:** A tool's `annotations` (for example `readOnlyHint`) cannot be verified, per the spec. A hint can therefore only lower the default: if there is no hint or it is not read-only, the tool is *dangerous* (approval every time), and with `readOnlyHint: true` it is *restricted*; no hint makes a tool *safe*. The user changes the class per tool (`settings.tools.mcp_classes`); the model cannot. MCP tools go through the same policy, approval, time/size limits, and tool log as built-in tools (`source: mcp` in the log).
- **Text coming from the server goes to the model:** An MCP server (or the web content it fetches) can embed instructions in a tool result (prompt injection). The policy is therefore applied to the call, not the tool result: dangerous tools ask for approval.
- **The server cannot ask the client for anything:** `roots`, `sampling`, and `elicitation` are not offered; the server's requests are rejected with `Method not found` (only `ping` is answered). In the modern era an "input required" result ends with an explicit error.
- **Secrets:** The server's environment variables and HTTP headers stay in the keychain (a placeholder in the file) and return masked to the UI; they are resolved only at connection time and given to the child process / request. For a protected remote server, either a token in a header or OAuth authorization is used (see [MCP.md](MCP.md)); the OAuth session is also stored in the keychain.
- **Process control:** A stdio server runs in its own process group (a Job Object on Windows) without a console window; when the connection closes, stdin closes, and the whole process tree of a server that does not exit is killed; on orderly shutdown. Forced host termination is covered by Windows Job Objects, not by Unix process groups. Verified by tests: no orphan process remains after shutdown, a drop, removal from the configuration, and the server dying on its own.

## Harness MCP Server

The MCP server through which agents use Harness as a tool ([MCP.md](MCP.md)) runs on top of the Control API; it has no authority of its own.

- **HTTP (`POST /api/harness/v1/mcp`):** Bearer token and loopback `Host` checks like the other endpoints. A valid token is enough to connect; each tool requires its own scope: `read` (listing, info, hardware, recommendation, endpoint, metrics, log, comparison), `servers:control` (load, unload, start, stop; `servers:write` also suffices), `servers:write` (benchmark), `downloads:write` (download from Hugging Face; `models:write` also suffices), and `models:write` (delete a model). `tools/list` shows only the tools the token allows. The tool calls the API in-process with the caller's token; the scope is checked there a second time. If the `Origin` header is present, only origins in the CORS list are accepted (403). No session id is generated.
- **stdio (`harness mcp`):** The local session token is fully privileged, so the MCP layer narrows it with `--scope`. The default is `read,servers:write,tools`: the agent can load and unload models, but downloading and deleting require `--scope read,servers:write,tools,models:write`. The `tools` scope opens nothing by itself: Harness's file/shell/network tools are offered to MCP only if the user turns on Settings > Tools > "Offer to MCP Clients" (off by default), and every call is decided by the saved permission policy. Since MCP cannot ask for approval, only calls the policy lets run without asking will run; those that need approval return a tool error saying "make it trusted", and if the policy is "off", no tool is offered. The client cannot send `approved` or a working folder. The tools of MCP servers that Harness consumes are not re-offered. Calls are written to `tool_calls` as `mcp:<client name>`. `admin` does not exist unless explicitly given.
- **No network exposure:** No tool changes the bind address or gives the "Open Anyway" confirmation. A profile that binds to the network also goes through the network rule via `start_server` (`network.lan_without_key`).
- **No secrets:** `get_endpoint` and the other tools never return the llama-server API key (only whether it is required).
- **"Add Harness MCP":** Adds/removes only the `harness` entry, takes a `<file>.harness-<date>.bak` backup beforehand, and does not touch a file that cannot be parsed. The stdio entry contains no secret. The HTTP entry writes the named token to the tool's file in plain text; the UI states this and recommends stdio. The backups (`<file>.harness-<date>.bak`, the last 5 per file) carry this token too; after "Remove", the tokens found in the `harness` entry in Harness's backups are replaced with `removed-by-harness` in all backups (the rest of the file and the backup of the state before Harness are not touched). To invalidate the token completely, revoke it in Settings > Developer > Control API.

## Integrations and `harness launch`

- **`harness launch` / "Launch":** The token (the gateway client token, a named `inference` token, or the llama-server key) is given only to the launched tool's process environment. For Claude Code, the same values are also written to a temporary `claude-settings.json` file (open only to the user, `%TEMP%\harness-launch-*`), and the folder is deleted when the tool exits. No global configuration (`~/.claude`, `~/.codex`...) is written. `--dry-run`, JSON output, and log lines show the token as `***`. Provider variables not belonging to Harness (`ANTHROPIC_API_KEY`, Bedrock/Vertex keys, `AIDER_*` model settings) are removed from the tool's environment; a real account key is therefore not sent to the local server.
- **Persistent integrations:** On a loopback gateway, only the placeholder `harness-local` is written to tool files. On a direct endpoint, if the server has an API key, it is written in plain text to the tool's file (Codex `http_headers`, Continue, OpenCode, LibreChat...); in VS Code it is left to VS Code's secret store with `${input:...}`, and in Goose it is redirected to the `HARNESS_API_KEY` environment variable. The preview shows everything that will be written.
- **Ledger and backups:** `config/integrations.json` keeps not the written values themselves but their SHA-256 and the key's previous value (the previous value is the user's own setting). Timestamped backups (`<file>.harness-*.bak`, 5 generations) carry the file's content at that moment, with its keys if any; backups stay in the original file's folder.
- **Connection test:** A single small request goes only to the Harness endpoint shown; the key stays in the request header and is not shown in the result.

## Network Access Rules

The rules live in one place, `harness_core::network`. Every launch path (the Dashboard, a saved profile, restore at startup, "Prepare Server", router mode) goes through the same function, and the same rule is checked again when the process is started.

- **Bind address:** Only an IP address or `localhost` is accepted. A host name, a comma-separated address list (llama-server binds to every address in the list), and a UNIX socket path are rejected. The default is `127.0.0.1`; "Local network (0.0.0.0)" or a single IP can be selected in Settings > Network & Security. A profile with its own address uses its own address.
- **Loopback** (`127.0.0.0/8`, `::1`, `localhost`): always allowed.
- **Network binding** (`0.0.0.0`, `::`, a LAN IP): allowed if there is an API key. Without a key it is **rejected** even if tools are off (`network.lan_without_key`).
  - If the user explicitly says "Open Anyway" for that server, the confirmation is written with a timestamp into `settings.json` → `network.exposure_acks`; for a server running this way a persistent warning strip appears in the app. The confirmation can be removed from Settings.
  - When tools or MCP are on, the confirmation does not pass: because the model gains file and process access, a key is mandatory (`network.tools_without_key`).
- **API key:** Kept only in the OS keychain and passed to llama-server through the `LLAMA_API_KEY` environment variable (it does not appear on the command line). "Generate Strong Key" produces 32 random bytes (base64url, 43 characters).
- **CORS (`--cors-origins`):** If the user has a list, that is sent. If the list is empty: on a loopback server, llama-server's default stays (when tools/MCP are on, llama-server itself narrows to `localhost`); on a server open to the network `none` is sent, meaning no browser page can reach the server through CORS. Desktop clients and command-line tools are not affected by CORS.
- **Firewall:** Harness Studio does not change firewall settings; LAN addresses are shown for information only.

## Hugging Face Account

- **Storage:** The pasted access token and the OAuth access token live in the OS keychain in the `com.harnessstudio.app` / `huggingface_token` entry. The OAuth session (access + refresh token, expiry, client ID, scopes, user name/avatar) is in the separate `huggingface_oauth` entry. Only `hf_token_set` and the public `hf_oauth_client_id` are written to `settings.json`; the token goes to no file, log, or UI (the `Debug` output of the Rust types hides the token, and error messages carry only the server's `error_description`). If the keychain cannot be read, the state is not treated as "signed out"; `secrets.hf_read_failed` is returned.
- **Where the token goes:** `Authorization: Bearer` is added only to HTTPS requests to `huggingface.co` / `hf.co` (and subdomains); on a redirect to another host, reqwest drops the header.
- **Sign-in flow:** OAuth 2.0 Authorization Code + PKCE (S256, a 32-byte random `code_verifier`), a 24-byte random `state`. The redirect arrives at a one-time listener bound to `127.0.0.1` on a random port chosen by the operating system; only `GET /callback` is handled, and `state` is compared in constant time. A request with a wrong or missing `state` gets 400 and sign-in continues (a local process cannot hijack the sign-in; at most it delays it). The listener closes when the code arrives, when cancelled, or after 5 minutes. No client secret is used: a public client.
- **OAuth application:** Harness has no distributed client ID. The user (or distributor) creates an application **without a secret** at huggingface.co/settings/applications/new: the redirect address `http://127.0.0.1/callback` (Hugging Face ignores the port for loopback addresses), and the scopes `openid profile read-repos gated-repos`. `read-repos` is for reading private repositories and `gated-repos` for reading gated repositories you have been granted access to; no write scope is requested. The client ID is entered in Settings > Storage > Hugging Face Account > Advanced: OAuth application, in the `HARNESS_HF_OAUTH_CLIENT_ID` environment variable, or in the same variable at build time.
- **Sign-out:** Hugging Face has no token revocation endpoint. "Sign Out" / `harness hf logout` deletes the two keychain entries; to remove the application's access to the account completely, use huggingface.co/settings/connected-applications (huggingface.co/settings/tokens for a pasted token). The UI and the CLI show this link.
- **Refresh:** If less than 2 minutes remain before the access token expires, it is refreshed with the refresh token before the next Hub request or download (one refresh at a time within the process); if the refresh fails, the old token stays and the request ends with a keyed error (`hub.gated_*`, `hf.repo_not_accessible`); it does not silently fall back to an anonymous request.

The application sends no telemetry; diagnostic reports are stored only locally.

## Trust Levels and Revocation

Trust describes execution authority, not publisher reputation. Official registry entries and user-created tools receive the same controls. Permission classes (`safe`, `restricted`, `dangerous`) govern call approval separately; they do not confine native code. Grant screens and Settings > Network & Security > Permissions show these distinctions and reuse the installed-item controls.

| Trust Level | Files/Folders | Network, Shell, Services | Accounts and External Data | Revoke |
| --- | --- | --- | --- | --- |
| Scoped JavaScript (QuickJS; registry or user-created) | Manifest read/write folders, enforced by host APIs | Manifest public-host network scope; no shell or service API | No automatic keychain access; permitted HTTP can upload readable file data | Disable/remove under Installed Tools; reinstall for changed grants |
| Native Program (stdio MCP, Hermes, module backends) | Anything the OS user can access | User authority; process limits below are not access controls | Inherited/supplied environment and user-readable credentials; can exfiltrate data | Disable/remove MCP; stop Hermes task and disconnect; stop/disable module |
| Remote Service (HTTP MCP) | No direct local filesystem access through this client | Remote host authority; requests go to the configured endpoint | Tool arguments/results and configured headers/OAuth reach that service | Disable/remove connection; revoke OAuth/key with provider |
| Future Trainer | No grants or executable trainer shipped | Not implemented | Future grant must name dataset roots, output roots, network/service endpoints and account scopes | Must support stop and revocation before shipping |

Hermes task read-folder grants constrain the Harness task adapter, not Python or upstream code. A model-scoped inference token does not give admin authority. Disconnect revokes that token; stopping a task ends its process group. A folder edit affects the next task, not an already running one: stop first. Disable/remove prevents later calls; already running QuickJS calls may finish within their timeout. MCP removal closes the configured transport. Revocation does not undo writes, recall data, or revoke a separately issued upstream credential. Revoke provider keys/OAuth at the provider as well. Externally launched Hermes sessions are outside Harness process ownership.

## Native Process Containment by OS

No administrator rights, firewall edits, system settings, AppContainer, seccomp, namespaces, or macOS sandbox entitlement are requested. Native code retains the logged-in user's file, network, shell, service, and account authority. These are lifecycle/resource controls, **not a security sandbox**.

| OS | Implemented Controls | Limits |
| --- | --- | --- |
| Windows | command-group creates a Job Object, launches suspended, assigns before resuming, enables kill-on-close, and does not enable breakaway. MCP, shell, Hermes, job backends and managed installer helpers kill their trees on stop/drop and host termination. ProcessManager service backends also use jobs. | No filesystem/network/token isolation. Services or work submitted to unrelated existing processes are not descendants. A restrictive enclosing job can reject assignment; errors are surfaced. |
| Linux | Separate process groups; SIGKILL on stop and owned-operation drop, including normal shell completion. Pre-exec rlimits for core dumps (0), open files (at most 1024), and optional address space. | A descendant can escape using setsid/setpgid. Abrupt host termination does not run Rust cleanup and is not guaranteed to kill the tree. Existing Linux ProcessManager parent-death handling covers its direct child only. No namespace/seccomp sandbox. |
| macOS | Same process-group cleanup and pre-exec rlimits as Unix above. | No App Sandbox/Seatbelt isolation. Escaped descendants and forced host termination have the same limitations; OS address-space enforcement varies and a rejected limit fails startup. |

Set `HARNESS_CHILD_MEMORY_MIB` in the **Harness host environment** to a positive MiB integer to opt into a native workload memory ceiling. Unset means no additional memory cap. Invalid/overflowing values fail startup. Unix applies `RLIMIT_AS` before execution, retaining stricter inherited hard limits; this is virtual address space, not resident RAM or GPU memory. Windows adds a nested job with an aggregate committed-memory limit; assignment occurs just after the primary job starts execution, so early allocations/children can precede the supplemental memory limit. It is not a race-free memory boundary. Failure to apply an enabled limit fails the launch; the primary job still owns cleanup. Existing GPU/driver allocations are not capped. Limits apply to MCP, builtin shell, Hermes probes/tasks/installer, generic jobs, managed Python helpers and ProcessManager backends; other external integrations are not covered by this option.

The Windows Rust test `tools::mcp_client::stdio::containment_tests::killing_host_kills_mcp_child_tree` starts a separate host using the actual MCP stdio transport and a Node server plus grandchild, forcibly terminates the host (no Drop), then waits on both OS process handles. Run with Node available on PATH. This tests the shared host-death mechanism; it is not an end-to-end packaged Tauri UI test. Unix behavior requires platform execution; a Windows run does not validate Unix rlimits.
