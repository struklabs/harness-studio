# Remote App Protocol

Remote access is an opt-in preview, compiled with the `remote-access` feature and
disabled by default. Settings → Server Defaults → Advanced offers **Remote Access
via StrukLabs**. The account sign-in/ticket endpoint is not deployed yet; the
desktop uses a `TicketProvider` interface rather than a placeholder account URL.
The browser side is authoritative for the wire format: this desktop is **aligned with
struklabs-web APP_PROTOCOL @777d3e8** (commit
`777d3e8ed9c0b3464dad6ef060a02135ed12f72a`, `docs/APP_PROTOCOL.md` plus
`packages/app-protocol`). Cross-implementation vectors generated by that package live in
`crates/harness-core/src/pairing/remote/fixtures/web-interop.json` (source commit recorded in the
file); the desktop tests reproduce the SAS, the commitment, the fingerprint, the poll digest, the
frames, the 256-byte records and the relay frame check byte for byte.

## Existing HTTP Pairing (#399)

These routes remain compatible with existing devices. They are served by the
gateway, not the Control API. Outside a trusted LAN use HTTPS.

| Operation | Request | Successful response |
| --- | --- | --- |
| Claim | `POST /v1/harness/pair/claim` with `{code, device_name, platform?, client_nonce}` | HTTP 200 `{claim_id, poll_secret, verification, server_nonce, expires_at}` |
| Poll | `GET /v1/harness/pair/claim/{claim_id}`, header `x-harness-pair-secret: <poll_secret>` | HTTP 200 `{status, token, device_id, role, preset, scopes, endpoints, models}` |
| Self-report | `POST /v1/harness/device/report`, device bearer token, `DeviceSelfReport` JSON | HTTP 204 |

`platform` defaults to the empty string. `device_name` is trimmed, 1–48 characters,
without control characters. `client_nonce` is 16–128 ASCII alphanumeric characters.
The eight code digits may be grouped (the offer displays `1234-5678`). Timestamps
are Unix seconds. Default offer and claim TTLs are 300 seconds; the owner may set
an offer TTL of at most 900 seconds. Five wrong claims within a rolling 60-second
window lock claiming until the oldest failures leave that window. This is a
host-wide limiter, not a per-IP limiter.

Poll `status` is `pending`, `approved`, `denied`, or `expired`. All four use HTTP
200. Optional fields are `null` when absent; the arrays are empty. An approved
token is delivered once. Repeating that poll returns `pairing.not_found`.

| HTTP error | Code |
| --- | --- |
| 400 | `pairing.device_name_invalid`, `pairing.nonce_invalid`, other pairing failures |
| 403 | `pairing.invalid_code` (also consumed/expired offer), `pairing.not_a_device` |
| 404 | `pairing.not_found` (including incorrect poll secret or already delivered token) |
| 429 | `pairing.locked`, `pairing.too_many` |

The error body contains `error.code` and `error.message`. The existing lockout
response does **not** provide `retry_after_s`. This confirms the actual #399
paths, fields, and mapping requested in APP_PROTOCOL section 14 Q1/Q2; its draft
201/202/410 mappings and `name`/`nonce`/`verification_code` fields do not describe
these HTTP routes.

Legacy verification is the first four bytes of
`SHA256(code_digits || 0 || client_nonce || 0 || server_nonce || 0 || claim_id || 0)`,
interpreted as a big-endian u32, modulo 1,000,000, formatted as six decimal digits.
All four inputs use their UTF-8 text representations. This derivation remains
unchanged for existing clients.

## Browser Pairing Inside Noise

The encrypted `pair.request` / `pair.response` adapter uses the browser schemas
and their HTTP-style status field. It does not change the legacy HTTP contract.
Envelopes have `v: 1`, a strictly increasing per-direction `seq` beginning at 0,
and a request `id` echoed in the response. All operations require mode `pair`.

**Keys never travel in bodies.** `Kc`, `Kd` and the handshake hash `h` come only from the
Noise session. A request body of any operation that carries a key field (`static_pub_c`,
`static_pub_d`, `noise_static_pub`, any name containing `static` or ending in `_pub`) is refused
with status 400 `pairing.key_in_body` before anything is consumed; it is never compared and
never used. The old field names `nonce_d`, `static_pub_d`, `nonce_c`, `static_pub_c` and the
`verification_code` answer are gone from the wire.

1. `op: "claim"`, `body: {code, name, commit}`. `code` is exactly eight digits.
   `commit = base64url(BLAKE2s("struklabs/pairing/sas-commit/v1" || L(nc)
   || L(Kc) || L(h) || L(name)))` where `nc` is the claimer's 32-byte nonce, `Kc` is the
   claimer's Noise static key, `h` is the Noise handshake hash of this session and `name` is
   the trimmed device name. The desktop consumes the offer atomically, fixes the commitment and
   only then generates its fresh 32-byte nonce `nd`. `claim_id` is assigned by the desktop
   and is never a SAS input.
2. Status 201 returns `{claim_id, poll_secret, nd, expires_at, poll_interval_ms}`. Nonces are
   unpadded base64url, `expires_at` is UTC RFC 3339 ending in `Z` (a pending claim lives 180 s
   from the claim), and polling is every 2000 ms. A QR fingerprint is checked by the browser
   before claiming. Only a claim-salted digest of the poll secret is retained
   (`base64url(BLAKE2s("struklabs/pairing/poll/v1" || claim_id || 0x00 || poll_secret))`). The
   legacy HTTP poll route cannot deliver browser claims; delivery requires the bound Noise peer.
3. `op: "reveal"`, `body: {claim_id, nc}`. The desktop recomputes the commitment from `nc` and
   the `Kc` and `h` of the claiming Noise session and the stored name, comparing in constant
   time. A mismatch erases the claim, counts a strike and returns 403
   `pairing.invalid_reveal`. A reveal from a session whose key is not the claiming key is
   `pairing.not_found`. One reveal per claim. No claim can be approved or shown to the owner as
   pending before a successful reveal.
4. Status 200 returns `{status:"revealed"}`. The browser computes the SAS itself from `nc`,
   `nd`, `Kc`, `Kd`, `h` and the name, and the desktop shows the same number to the owner; the
   owner approves only if both screens match. The desktop sends no code on the wire.
5. `op: "poll"`, `body: {claim_id, poll_secret}`. Valid only after a valid reveal and only
   from a session whose Noise static key equals the claiming key; anything else is
   `pairing.not_found`. Pending: status 202 `{status:"pending"}`. Denied: 403
   `pairing.pending_denied`. Approval: status 200 `{status:"approved", token,
   token_type:"bearer", device_id, desktop_id, desktop_name, scopes, token_policy,
   noise_static_pub}`. The desktop key is pinned with the token; subsequent app handshakes must
   verify it before sending `hello` and the token.
6. `op: "ack"`, `body: {claim_id, poll_secret}`. **Delivery is idempotent until
   acknowledged**: the same poll re-delivers the same token for 60 s after the first delivery.
   The browser stores the token first and only then sends `ack` (200
   `{status:"acknowledged"}`), after which the desktop wipes its copy. An `ack` before any
   delivery, from another key, or twice is `pairing.not_found`. An approved claim is not subject
   to the 180 s claim TTL: it waits up to 300 s for its first poll, then the token copy is wiped
   (the device record stays; the owner revokes it from the device list).

Browser errors use 403 for `pairing.invalid_code` / `pairing.invalid_reveal` /
`pairing.pending_denied`, 410 for `pairing.expired` / `pairing.not_found`, 429 for
`pairing.locked` (with `retry_after_s: 60`) and 400 for `pairing.key_in_body` and malformed
input. Malformed crypto inputs fail closed. No legacy token can authenticate a browser app
session: its registry record must bind its Noise key.

### Verification and Fingerprint

Let `L(x) = u16be(byte_length(x)) || x` and `H` = BLAKE2s-256. The browser and the
desktop each derive the same six digits (first eight digest bytes as a big-endian
u64, modulo 1,000,000, zero-padded):

```text
SAS = H("struklabs/pairing/sas/v1" || L(nc) || L(nd)
        || L(Kc) || L(Kd) || L(h) || L(name))
```

`Kc`, `Kd` and `h` come from each side's own Noise session. A relay that
terminates Noise on both legs produces different `h` and keys per leg, and it
must fix its commitment before seeing `nd`, so it cannot grind a matching
code (the old `claim_id` input was grindable and is removed). The reveal answer
carries no code: the human comparison of the two screens is the control. A bad
reveal, a denial or a mismatch burns the claim.

### Relay Tickets

The desktop ticket flow follows APP_PROTOCOL 7.2. After the StrukLabs account sign-in, a
`TicketProvider` calls `POST /account/api/relay/desktop-ticket` on the platform with the
account access token (never a Harness token) and the body
`{device_id, noise_static_pub}` (`relay::desktop_ticket_request`); the platform answers
`{ticket, expires_at, relay_url}` and `RelayTicket::from_response` builds the ticket. The relay
URL is fixed (`wss://relay.struklabs.com:7843/v1/app`): an answer naming another URL is refused.
The sign-in itself is not deployed, so the default provider still reports it as unavailable.

Before dialing, the desktop pins `alg = EdDSA` (rejects `none`/HS*) with a `kid`,
requires `aud = struklabs-relay`, an `https` `iss`, a `sub` of 8 to 128 characters,
`role = desktop`, no `mode`, `device` and `noise_static_pub` equal to its own, the signed
`limits {sessions: 8, bytes_per_minute: 8388608, idle_timeout_ms: 60000}`,
`exp - iat <= 300`, `iat - 5 s <= now < exp`, and rejects a reused `jti`. Signature
verification, the `kid` allowlist and `iss` matching belong to the relay (platform JWKS).

**The desktop does not call `POST /account/api/relay/redeem`.** That endpoint is operator
authenticated and belongs to the relay: after every other check it claims the `jti` in the
platform's durable store (200 on first redemption, 409 otherwise) before accepting `auth`, so a
relay restart or a second node cannot accept a captured ticket again. Each reconnect fetches a
fresh ticket; the desktop never holds a long-lived relay credential.

### Relay Session Rules

The relay connection multiplexes up to eight sessions (APP_PROTOCOL 7.5). The desktop speaks and
listens only for sessions the relay created for it (`session.incoming`):

- **Ownership.** Binary frames, `transport.fallback`, `peer.left`, `ice`, `sdp.offer` and
  `ping` carrying another session id are dropped and never touch an owned session; a `leave` is
  only ever sent for an owned session. A frame too short to hold a session id is fatal.
- **Ids are never reused.** A `session.incoming` for an id that is live or was already used on
  this connection is fatal.
- **Per-direction order.** The desktop (responder) accepts exactly a 32-byte handshake frame 0,
  then a 64-byte frame 2 (it sends the 96-byte frame 1), and transport frames only afterwards.
  The key-less relay check `validate_relay_frame` is ported from the web package and the
  channel applies it to every inbound frame.
- **Buckets and sizes.** A transport Noise message is whole 256-byte record buckets plus the
  16-byte tag, at least 272 and at most 16,656 bytes; the frame body is at most 16,673 bytes.
- **One live session per device.** When a `hello` authenticates a device that already has a
  live session, the older session receives the fatal `session.superseded` and is closed; it
  does not detach the chats the new session took over.

The QR fingerprint is
`base64url(BLAKE2s("struklabs/pairing/fingerprint/v1" || Kd)[0..16])`.
All labels are literal UTF-8 bytes without a trailing zero. QR links use
`https://app.struklabs.com/devices/pair#code=...&desktop=...&fp=...`; fragment
values do not reach the app server. Never put tokens in a URL.

## Noise and Relay

Noise suite: `Noise_XX_25519_ChaChaPoly_BLAKE2s` using `snow`; browser initiates,
desktop responds. Prologue: `StrukLabs-App/1|<pair-or-app>|<32-lowercase-hex-session>`.
Empty handshake payloads produce exactly 32, 96, and 64 bytes. The desktop's
long-lived secret is held by Windows Credential Manager, macOS Keychain, or Linux
Secret Service, never a JSON file. A locked/corrupt store is an error, not a key
rotation. Each connection uses fresh ephemeral keys. Failed decryption is fatal.

Each whole-message transport carries one frame:
`u32be(body_length) || kind:u8 || session:16 || Noise_message`.
Kinds are 1 (handshake) and 2 (transport); the body maximum is 16,673 bytes. Encrypted
records contain `flags:u8 || data_length:u16be || data || zero_padding`, padded to
the exact next multiple of 256 bytes (a bucket, so small `chat.delta` envelopes of different
lengths look alike). Only flag bit 0 (more fragments) is permitted, each record
holds at most 16,384 data bytes, every non-final fragment is exactly full, an envelope has at
most 128 fragments, and an assembled UTF-8 JSON envelope is at most
1 MiB. Wrong padding length, non-zero padding, session mismatches, replay, ordering errors, invalid padding and malformed
frames close the session. There is no plaintext application transport.

Desktop WSS is outbound to `wss://relay.struklabs.com:7843/v1/app`, subprotocol
`struklabs.app.v1`. A signed-in account ticket is single-use, expires within 300
seconds and is bound to the desktop key. The ticket issuer is an injected trait;
the default provider reports that account sign-in is unavailable. Auth uses
`{v:1,seq:0,session:<all-zero-id>,type:"auth",role:"desktop",credential}`.
Relay text envelopes handle presence, incoming sessions, fallback, ping/pong and
peer departure. Binary application frames are accepted only after
`transport.fallback`. At most eight sessions share a desktop relay connection.
The channel interface is independent of WSS so a future ordered, reliable
WebRTC data channel can carry identical frames.

Errors added by the alignment: `chat.limit_reached` (retryable) is returned when a token's
concurrent chat limit is reached (it replaces the earlier `chat.busy` for that case; `chat.busy`
now means the same chat id was reused for a different request), and `session.superseded`
(fatal, see above). A `chat.start` whose id and request are identical to a running chat attaches
to it instead of starting a second generation. The prompt limit is 262,144 UTF-8 bytes in total.
The wire `message` texts are English; the browser app owns the user-facing EN and TR copy.

Chat replay retains unacknowledged deltas for at most 256 KiB / 30 seconds per
chat. `chat.ack {id,index}` acknowledges the contiguous delta index; the outer
envelope `seq` still increases independently in each Noise session. Reconnection
uses `hello.resume [{chat_id,last_index}]`; accepted cursors are echoed in
`hello.resumed`, otherwise `chat.resume_unavailable` is returned. Retained deltas
are re-encrypted under the fresh Noise session, never replayed as old ciphertext.
Revocation clears retained state and cancels generation, including while offline.
`device.revoke {id}` revokes the authenticated
device's named token, clears its buffer and answers encrypted
`device.revoked {id}`. It cannot revoke an arbitrary other device.

`models.list` is filtered by the token policy. `chat.start` uses the existing
gateway scheduler and upstream chat stream, enforcing model/endpoint permission,
request rate and concurrency limits. `chat.cancel` drops the upstream stream and
its scheduler lease. The relay can observe connection metadata and padded frame
sizes, never pairing secrets, tokens, prompts or application envelopes. Account
ticket issuance and WebRTC remain unavailable in this preview.

Known gaps against APP_PROTOCOL (tracked, not silently diverging): the single-open-offer rule
and the offer burn after 15 wrong codes in total are not applied (the legacy HTTP pairing keeps
its own offer list and limits), and the token policy still caps a browser device at one
concurrent chat.
