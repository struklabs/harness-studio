# Harness Studio - System Architecture (ARCHITECTURE.md)

## 1. Overview and Philosophy

**Harness Studio** is a lightweight, minimalist and reliable control center that manages the `llama.cpp` binary (`llama-server`) directly in order to run local AI models.

### Core Principles
1. **Low resource usage (design principle):** While idle, the goal is minimal background RAM and CPU consumption. Heavy runtimes such as Electron are avoided. The real memory and CPU footprint is tracked by benchmarking on the target operating systems (Windows, Linux, macOS).
2. **Direct and transparent llama.cpp integration:** It manages the `llama-server` process directly; every server's own port stays reachable without an extra layer. An optional gateway for multi-model single endpoint, JIT loading and per-request observability runs inside the application process; no separate daemon is installed (see §13).
3. **User-friendly runtime management:** A two-tier runtime approach that spares users from hunting for binaries on the internet, while still letting advanced users run binaries they built themselves.
4. **Privacy-first diagnostics:** Error and crash diagnostics are collected only with the user's explicit consent; user prompts, model responses and personal paths never leave the system.

## 3. Hardware Detection and Runtime Management

### 3.1. Minimal Hardware Detection and Driver Compatibility
To pick the right official `llama.cpp` package (CUDA, Vulkan, CPU, Metal, ...) automatically and safely, minimal hardware and driver information is queried:
* **Operating system and version:** Windows, Linux, macOS.
* **CPU architecture:** x86_64, arm64.
* **System memory:** Total physical RAM.
* **GPU and memory:** GPU vendor (NVIDIA, AMD, Intel, Apple Silicon), model name and VRAM size.
* **Driver and runtime compatibility:**
  * For NVIDIA GPUs, the installed driver version (from the adapter) and whether the CUDA driver library is present (`nvcuda.dll` in System32 on Windows; `libcuda.so` via `ldconfig -p`, `/usr/local/cuda` or WSL on Linux). No CUDA version is queried: CUDA eligibility is a driver threshold, 528.33 for CUDA 12 builds on Windows (`hardware::windows_cuda12_driver_supported`; below it Vulkan is recommended) and 580 for CUDA 13 builds (`runtime::select_asset_for_driver`).
  * Vulkan support (presence of the Vulkan loader/instance).
  * Metal support on macOS.
* **Selection principle:** The GPU vendor name is never hard-coded blindly. For example, even if the system has an NVIDIA GPU, a stale driver or missing CUDA libraries lead to a safe fallback to the **Vulkan** or **CPU** build, or the user is offered an explicit choice.
* **Implementation (`hardware::advise_backend`):** NVIDIA + CUDA driver -> CUDA; RDNA3/RDNA4 AMD (RX 7000/9000, W7000, R9700) -> ROCm/HIP (on Linux `/dev/kfd` is required, otherwise Vulkan); Intel Arc -> SYCL (Windows), Vulkan (Linux, so oneAPI is not required); any other GPU -> Vulkan; Apple Silicon -> Metal; Intel Mac -> CPU. Only packages listed in `official_backends(os, arch)` and actually published in the official release are recommended; if the chosen package is missing, it falls back to Vulkan, and then to CPU. The recommendation reaches the UI as `BackendAdvice { recommended, reason_key, gpu_name, alternatives }`.
* **Backend switching is never automatic.** The backend of the installed build is read from the ggml libraries next to it (`runtime::detect_backend_in_dir`). Package query priority: user's request > `managed_runtime.backend` > installed build > recommendation (first install only). For this reason auto-update never changes the backend. If a ROCm/SYCL build cannot see at least one device of its own backend in Stage 1 (`--list-devices`), the staging folder is deleted and `runtime.backend_no_device` is returned.
* **Devices (`devices.rs`):** The runtime's `--list-devices` output (total/free VRAM, backend name, integrated GPU flag) is cached for ~20 s keyed by binary path + mtime + size; on error, the last value in the capability record is returned. On AMD/Windows, the free memory reported by Vulkan does not change with the loaded model; therefore `available = min(free, total - OS adapter usage)` (PDH). With two or more discrete devices, a main GPU (the one with the most available memory) and a `--tensor-split` proportional to free memory are suggested.

### 3.2. Managed Runtime vs. Custom Binary

1. **Managed runtime (managed by Harness Studio):**
   * The official `ggml-org/llama.cpp` GitHub release package that matches the detected hardware is downloaded and placed under `bin/managed/`.
   * The active version number (`bXXXX`) is recorded; update checks run automatically or manually.
   * Supports updating and rollback.

2. **Custom binary (user-defined):**
   * The user can select a `llama-server` path they built themselves or that already exists on their system.
   * **No-interference rule:** Harness Studio **never auto-updates, modifies or rolls back** this binary.
   * **Minimal compatibility check:** When a custom binary is selected, Harness Studio performs a basic check:
     - Can the binary be executed?
     - Can the version output (`--version`) be read?
     - Are the basic features Harness needs supported (in particular the `--metrics` flag and the `/health` endpoint)?
     - If an incompatibility is detected, the user gets a clear warning, but launching is not blocked if they want to force it.

### 3.3. Runtime Update and 2-Stage Verified Rollback Flow
The active runtime stays in place until the new version is verified. The rollback mechanism only runs for verification failures caused by an update:

```mermaid
sequenceDiagram
    autonumber
    actor User as User / Auto-update
    participant RM as Runtime Manager
    participant GH as GitHub Releases API
    participant PM as Process Manager
    participant FS as File System (bin/)

    Note over RM,FS: The currently running runtime (bin/managed/) stays active.
    User->>RM: Start update
    RM->>GH: Download new version (e.g. b12000)
    RM->>FS: Extract the new version into bin/staging/
    
    Note over RM,PM: Stage 1: Basic binary verification
    RM->>PM: Test the staging binary (`llama-server --version`)
    alt Stage 1 failed (missing DLL / broken binary)
        PM-->>RM: Error (process crash / exit != 0)
        RM->>FS: Clean up bin/staging/
        Note over RM,FS: The current runtime was never touched! No rollback needed.
        RM-->>User: Update cancelled (binary could not be executed)
    else Stage 1 passed
        Note over RM,FS: Stage 2: Activation and runtime verification
        RM->>FS: Move the current version in bin/managed/ to bin/backup/
        RM->>FS: Move the new version in bin/staging/ to bin/managed/
        RM->>PM: Start the new version with a temporary test model and poll GET /health
        alt Stage 2 passed (health OK)
            PM-->>RM: Health check passed
            RM->>RM: Update the active version record (b12000)
            RM-->>User: Update completed successfully
        else Stage 2 failed (runtime crash / health 503 timeout)
            PM-->>RM: Health check failed
            RM->>FS: Clean up bin/managed/ (the faulty new version)
            RM->>FS: Restore the previous working version from bin/backup/ into bin/managed/ (rollback)
            RM-->>User: "The new version failed the run test; safely rolled back to the previous version."
        end
    end
```

### 3.4. Background Runtime Auto-Update
When "Auto-update" is enabled under Settings > Runtime (`runtime_update.rs`):
* The first check runs 30 s after startup, then every 6 hours. Versions are compared by build number (`bXXXX`).
* The new version is downloaded and passed through the Stage 1 verification in §3.3; staging operations run only one job at a time (busy guard).
* Activation happens **only when no server is running**; if a server is running, it is deferred. When finished, a `runtime-updated` event is sent to the UI.
* Auto-update never runs in custom binary mode.
* **The backend is preserved; it never silently drops to CPU:** The update looks only for the installed build's backend (`managed_runtime.backend`, or the one detected from the files; `PickMode::Exact`). If there is no Vulkan/ROCm/CUDA build, if the staging build turns out to be a different backend, or if the installed build does not see the GPU, the current version is kept (`kept_current` + a warning in Settings > Runtime). A CPU build that was never recorded is not updated on a machine with a GPU (`runtime.update_cpu_on_gpu`). Falling back to another backend (Vulkan, then CPU) only happens on the first install, driven by the hardware recommendation.
* **Partially uploaded release:** GitHub lists a release while its archives are still being uploaded (alphabetically: on Windows `win-cpu` appears ~40 s before `win-vulkan`). Each backend candidate is first searched across all releases; the newest release that does not yet have the requested archive is skipped and the previous complete release is chosen.
* **Backup:** A `.harness-runtime.json` (version + backend) is written into the activated build folder. Only a working build (one that has a binary) is moved to the backup slot; if the backup has no binary, the revert returns `runtime.no_backup` (the installed build is not deleted), and otherwise the two swap places (the reverted build moves into the backup). On Windows, a folder move that fails with "access denied" is retried for ~3 s (antivirus scanner lock).
* The same steps are also available on the Control API as `GET /runtime/managed`, `POST /runtime/managed/install`, `POST /runtime/managed/rollback`, and on the CLI as `harness runtime managed status|install|rollback`.

## 4. Child Process Management (`llama-server` Lifecycle)

### 4.1. Process Isolation and Working Directory (CWD)
* **CWD rule:** On Windows, so that the CUDA, Vulkan and GGML dynamic libraries (`ggml.dll`, `llama.dll`, `cublas*.dll`) load without problems, the child process's working directory (`cwd`) is set to the folder containing the `llama-server` binary being run.
* **Windows Job Objects:** The process runs inside a Windows Job Object carrying the `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` flag (`command-group`, `kill_on_drop(true)`). When Harness Studio exits or crashes, `llama-server` cannot linger in the background, and VRAM is released immediately. This behavior is guarded by an E2E test (the parent process is killed and the server is verified to die too).
* **Orderly shutdown:** On `RunEvent::Exit`, all servers are stopped with `stop_all`. Helper processes (`--version`, `--help`, llama-bench) run on Windows with `CREATE_NO_WINDOW`, without opening a console window.
* **Linux / macOS:** The process is isolated with a process group (`setpgid`); on shutdown `SIGTERM` is sent, and after a 5-second timeout `SIGKILL` is applied. On Linux, `prctl(PR_SET_PDEATHSIG, SIGKILL)` is used as well. **On macOS, llama-server can survive an application crash** (orderly exit, tray exit and the update path call `stop_all`); a watchdog is planned (see [ROADMAP](ROADMAP.md)).

### 4.2. Launch Parameters (Argument Builder)
* `-m <path_to_model_or_shard_1>`: Model path (only the first shard for a split GGUF).
* `-ngl <layers>`: Number of GPU layers.
* `-c <ctx_size>`: Context window.
* `--host 127.0.0.1` and `--port <port>`: Passed explicitly on every launch (including the router and embedding/rerank). llama-server's own default port (8080; its log says it will become 9931 in the future) is never used (`test_build_args_always_pass_host_and_port`).
* `-t <threads>`: Logical CPU threads.
* `--metrics`: **Mandatory.** Enables the Prometheus `/metrics` endpoint.
* `--tools`: no longer passed (the old `server_tools` path was removed; tools run in Harness). It remains a protected flag: it cannot be enabled through `custom_args` or `LLAMA_ARG_TOOLS`.
* `--mcp-servers-config <path>`: When MCP is enabled in the preset, the path of the backend-generated `config/mcp_servers.runtime.json` (see §9).
* **Exposure check:** If tools or MCP are enabled and the server is going to bind to a non-loopback address (`--host 0.0.0.0`, etc.), `--api-key` is mandatory; otherwise the launch is rejected.
* **`--fit`:** When `fit=on` is given explicitly, `-ngl` is not sent. With `--fit`, llama-server changes only the values that are not set; if `-ngl` is given, it cannot choose the layer count itself. The context size is still sent.
* **Harness-level keys:** `serve_mode` and `load_timeout` live in the parameter layers but are not sent as flags.
* **Memory defaults (`harness_default`):** Parameters that carry `harness_default` in the catalog (`cache_ram` = 1024, `ctx_checkpoints` = 4) are sent in catalog order if the user gave no value, no spelling of the flag appears in the custom arguments, and the runtime recognizes the flag (`params::with_harness_defaults`). llama-server's own values (8192 MiB prompt cache, 32 checkpoints per slot) would hold GiBs of system memory with use; measurements are in [PERFORMANCE.md](PERFORMANCE.md). If the runtime is unknown (`build_args` without a runtime), nothing is added.

### 4.3. Readiness Check vs. Log Capture
* **Readiness verification:** Instead of fragile log regex matching, after the process starts, the `http://127.0.0.1:{port}/health` endpoint is polled at short intervals (200 ms). As soon as a `{"status":"ok"}` response arrives, the server moves to the "Running" state.
* **Log capture:** The `stdout` and `stderr` pipes are read non-blocking and written to a circular memory buffer (ring buffer, last 1,000 lines). Logs are captured not for the state machine but only to be shown to the user in the live console in the UI.
* **Load timeout:** `ServerConfig.load_timeout_secs` (default 300, 1-7200). A `load_timeout` value in the definition/profile overrides the setting. When the time runs out, the process is stopped and a `servers.load_timeout` error is recorded.
* **Failure classification (`failure.rs`):** When the process exits, the log reader threads are awaited, and this run's lines (after `run_log_start`) and the exit code are passed to `failure::classify`. Order: OOM markers -> Windows loader statuses (0xC0000135, etc.) -> unknown architecture -> corrupt file -> model not found -> port -> invalid argument -> Linux/macOS shared library errors -> `crashed` / `start_failed`. The result is stored as `ServerFailure { code, kind, message_key, params, phase, exit_code, evidence }`, `[code]` is appended to the `ServerStatus::Error` text, and a `server_failed` event is emitted. The patterns are tested with real b11236 logs under `tests/data/failures/`.
* **OOM recovery (`recovery.rs`):** `oom_options` derives concrete values from the GGUF metadata (layer count, KV size/token), the free VRAM and a 1 GiB margin. An option is a parameter layer: `orchestrator::retry_with_overrides` applies it temporarily on top of the last launch, first stops another server if needed, and performs a real launch. If `save` is given, the layer is recognized and written into the profile (only for keys it already defines).
* **Restart on crash:** If `auto_restart` is on (off by default), the supervisor calls `schedule_restart` after an exit. The delay is `2 s x 2^(attempt-1)`, at most 60 s; at most `restart_max_attempts` (3) attempts. If the server runs healthy for 300 s, the counter resets. Configuration-caused classes (invalid argument, corrupt model, architecture, model not found, missing library, port in use) are not restarted. In a user-initiated run, a failure during loading is not restarted either. A pending attempt is visible as `RestartState` (`server_restart` event), and `stop` cancels it. A supervisor generation counter prevents old attempts from overriding a new launch.
* **Persistent log files:** Every run is also written to `logs/servers/<server id>/<unix s>-<ms>.log`, with each line timestamped relative to the run start (`[+1.234s]`). When a run's file exceeds 16 MiB, the same run continues in a new file; per server, the newest files are kept up to 20 files and 64 MiB in total (the newest file is always kept).
* **Search and export:** The live buffer or a saved run log can be searched as plain text or with a regex (with a case-sensitivity option). By default, export writes the text, passed through the same sanitizing rules as the diagnostics module (user paths, tokens, e-mail addresses), to a file the user picks. For large files, the last 8 MB are read.

### 5.2. GGUF Header Parsing (Metadata Extraction)
The first bytes of every scanned `.gguf` file are read:
* The `GGUF` magic number (`0x46554747`) is verified.
* The model architecture (`general.architecture`), default context size (`{arch}.context_length`) and quantization type are read.

### 5.3. Split GGUF Download and Management Behavior
To prevent running a split model with a missing shard, the Model Manager applies these rules:
1. **Set detection:** The `*-00001-of-0000X.gguf` file pattern in the Hugging Face repository is analyzed to produce the list of all related shards.
2. **Complete download:** When the user chooses to download a split model, all shards from `00001-of-...` to `0000X-of-...` are downloaded in order or through the queue.
3. **Integrity check:** Until all shards are completed in `.cache` and moved, the model is not marked "Ready" in the UI. If a shard is missing, the model is marked "Incomplete / Downloading" and cannot be run.
4. **Single logical model display:** The UI shows one model card with a "Split (4 parts)" badge, not four separate files.
5. **Launch parameter:** When starting `llama-server`, **only the path of the first shard (`-00001-of-...`)** is passed; `llama.cpp` links the remaining shards from the same folder automatically.

### 5.4. Resumable Downloader
* Interrupted downloads are resumed from where they stopped using the HTTP `Range: bytes=X-` header.
* Files are kept as `models/.cache/{filename}.part` until complete.
* **Persistent queue:** Downloads sit in a queue stored in `config/downloads.json` (Queued, Downloading, Verifying, Paused, Completed, Error). One job runs at a time; a job can be paused, resumed, moved to the front or removed. The same file is never queued twice. The queue is restored when the application reopens.
* **HF token:** The token is read at download time via `hf_auth::current_token()` (an OAuth access token that is about to expire is refreshed first); it is never written to the queue.
* **Untagged repositories and task support (`hub_tasks.rs`):** HF's `pipeline_tag=` filter drops untagged repositories (most of the re-quantizations). Since the listing already returns the tags, file names, `library_name` and the `gguf` metadata block (architecture, `causal`, whether a chat template exists) through `expand[]`, the task is derived with no extra request (`hub_tasks::analyze_repo`; `full=true` was dropped because it does not return `gguf` and `library_name`). Order: the declared `pipeline_tag` (JSON, otherwise the README front matter `cardData`); reranker tag/name (checked before the task-name tag, because HF adds a `feature-extraction` tag to every BERT-type GGUF); a tag that is a task name; embedding tag/name and `library_name: sentence-transformers`; an `mmproj` file or a vision/multimodal tag and name word -> VLM; GGUF header `causal: false` or an encoder architecture (`bert`, `nomic-bert`, ...) -> embedding; a chat template in the header or `conversational` / `text-generation-inference` / `base_model:quantized:` -> LLM; if there is nothing else, the architecture in the header -> LLM (untagged `ggml-org/models-moved`, `llama` -> text-generation). Repositories that cannot be run get an explicit status instead of a guess (`not_runnable`): a file list exists but no `.gguf` (`no_gguf`), a LoRA adapter (`gguf-my-lora` tag / only `*lora*.gguf`; `adapter`), a diffusion tag or an image/video architecture (`flux`, `sdxl`, `wan`, ...; `not_language_model`); `inferred_task` stays empty for these. The result is `HfModelSearchResult.inferred_task` (only when `pipeline_tag` is empty; shown on the card as "inferred", with `inferred_source` in the tooltip: tags/name/files/library/gguf) and `not_runnable` ("Can't run" + reason; also on the model card). Fixture with real HF responses: `crates/harness-core/tests/data/hf-repo-signals.json`. For text-generation / feature-extraction / text-ranking / image-text-to-text, the task filter fetches two lists: tagged (`pipeline_tag=`) and untagged candidates (no filter; only repositories whose `pipeline_tag` is empty and whose inferred task matches are kept; if this half fails, the tagged page is still correct). The two are merged by the sort key (rough ordering: the same page range of both lists); the combined cursor is `<tagged>.<untagged>` (an empty half = finished). `HfSearchOptions.include_untagged = false` gives the old behavior. The "Runs here / Doesn't run here" table is now `hub_tasks::task_support`: the per-task baseline (what llama-server can do) is downgraded by the installed runtime's capability record (the `--embeddings`, `--rerank`, `--mmproj` flags; `verified` if the endpoint was confirmed in a real run); without the flag, "Doesn't run here" and the reason are shown. Tauri `get_task_support`; `hub/tasks.ts` holds only the id/name/group (a test checks that it lists the same tasks as the Rust table).
* **Hugging Face listing (`search_models_page`):** `GET /api/models` is always sent with `filter=gguf`, `direction=-1`, `full=true` (file names for the quant list); `search` is sent only if the query is non-empty, so task (`pipeline_tag`), license (`filter=license:<id>`), publisher (`author`) and sort (`sort=trendingScore|createdAt|likes|downloads|lastModified`) can each produce a list on their own. `downloader::search_params` builds the parameters and discards values that are not plain identifiers. The next page uses the cursor in the `Link: <...&cursor=...>; rel="next"` header (`HfSearchPage.next_cursor` -> `HfSearchOptions.cursor`). The GUI command is `search_hf_models_page`; the older `search_hf_models` (including the CLI) returns the first page and retries a query with no results once more with a sanitized query. The cache lives in the UI (`hub/hubData.ts`: 5 min per session, identical requests are merged); the token is read on every request with `current_token()`.
* **Gated access check:** On the model card, access is checked by probing for a `.gguf`, `.safetensors` or `config.json` file in the repository, and the user is warned if there is no access. Hugging Face refusals (`401/403` + `X-Error-Code: GatedRepo`, `429`) are turned into keyed errors (`hub.gated_no_token`, `hub.gated_no_access`, `hf.repo_not_accessible`, `hf.rate_limited`) by `downloader::hf_refusal`; both the access check and the download use this function.
* **Sign-in with Hugging Face (`hf_auth.rs`):** OAuth 2.0 Authorization Code + PKCE, `127.0.0.1` loopback redirect, device code flow, refresh and `whoami-v2`. The session is kept in the OS keychain (`secrets::hf_oauth_*`); because the access token is also written to the same record as a pasted token, code that uses the token (search, card, variants, download, Control API `/models/pull`, Ollama `/api/pull`) only calls `current_token()`. Opening the browser is the surface's job: the GUI opener plugin, the CLI `open_in_browser`. Details: [SECURITY_MODEL.md](SECURITY_MODEL.md#hugging-face-account).

### 5.4b. Memory Estimation and Measurement (`vram.rs`)
* Single source of estimates: Tauri `estimate_fit` (batch), Control API `GET /models/{id}/fit`, `harness show`. The UI only contains labels (`src/lib/fit.ts`).
* The input `FitInput`: file path/size, context, ngl, KV types, slots (`null` = Auto, §5.4d), launcher (`origin`), `--ctx-checkpoints`, unified KV, FA, ubatch, `--swa-full`, KV offload, mmproj. From the GGUF header it reads layers, embedding size, KV heads, FFN/expert FFN, the SWA window and pattern, and the `token_embd` and `output` tensor sizes (`gguf.rs`).
* Calculation (verified with real loads on b11236): weights = (file - `token_embd` - untied `output`) x offload/layers (+ `output` if ngl > layers; with tied embeddings, a copy on the GPU); the KV cell count is rounded to 256, SWA layers hold `min(n_ctx, pad256(n_swa*n_seq + n_ubatch))` cells; compute with FA on is `4*ub*ff_eff*4 + ub*n_ctx*2`; the runtime margin is 150 MiB.
* Correction: if a measurement exists with the same `settings_key`, values come from the measurement (`measured`); under a different setting, component ratios (measured/estimated, clamped to [0.25, 4]) are applied (`corrected`). For a measurement where only the process total is known, the difference is attributed to "runtime margin". Measurements are stored in the `vram_measurements` table of `state.db` (§13.10).
* The class (`full_gpu`, `tight`, `hybrid`, `cpu_heavy`, `oom_risk`) depends on the budget; the budget is the discrete GPU's VRAM, or the unified memory budget on Apple Silicon. `recommended_gpu_layers` is the largest ngl that fits within 90% of the budget (binary search).

### 5.4c. KV Cache Precision (`kv_policy.rs`)
In the UI this is "Conversation memory precision" (Dashboard > Advanced > Memory and KV Cache). Measurements and sources: [PERFORMANCE.md](PERFORMANCE.md#kv-cache-precision).
* **Levels** (`KvLevel`): Full = f16/f16; Keys 8-bit = K `q8_0` + V f16 (an automatic step only when flash attention cannot be enabled); Balanced = `q8_0`/`q8_0`; Saving = K `q8_0` + V `q4_0`; Compact = `q4_0`/`q4_0` (only when chosen by hand: the Saving choice on CUDA, Metal and ROCm, where matched pairs are fast; never automatic, it broke Qwen3-0.6B at 8k/32k on CUDA and raises the KL divergence to 3.5-8.5 times that of K q8_0 + V q4_0 on every model measured); Custom = any other pair (K/V selectors).
* **Auto** (K and V empty in the definition/preset, no `-ctk/-ctv` in the custom arguments, not a router, chat mode): the `choose` ladder (`kv_policy::ladder_for`) tries f16 -> q8_0/q8_0 -> K q8_0 + V q4_0 in order on Vulkan and CPU, and f16 -> q8_0/q8_0 only on CUDA, ROCm and Metal (`CUDA_LADDER`: the default CUDA build converts mixed pairs to f16 on every token, 27-38% slower generation; when q8_0/q8_0 does not fit the gateway shrinks the context); the first one that fits is picked (90% of the VRAM budget and 80% of RAM, via `vram::fit_with`, including the measurement correction). If none fits: if the weights fit without KV, the tightest step (`tightest`, the least overflow); if they do not fit, f16 (`too_big`, quantizing gains nothing). If flash attention cannot be enabled (the runtime does not recognize `--flash-attn`, or `-fa off` is in the custom arguments), the ladder is f16 -> K q8_0 + V f16. With FA available, the K-only step is not used: in measurement it gave the same KLD as q8_0/q8_0, saved half as much, and was slower on gpt-oss.
* **Launch** (`ProcessManager::start_run`, after `serve_mode::prepare`): `kv_policy::apply` writes the types into the launched copy (the stored setting stays empty); if V is quantized and FA is unset it adds `--flash-attn on` (if `-fa auto` resolves to off, llama.cpp stops with "quantized V cache ... requires Flash Attention"), and if the user said `-fa off` it returns V to f16. The decision is written to the server log and stored with `ProcessManager::kv_launched`; the VRAM measurement (`record_after_load`) is keyed by the types actually used.
* **Estimate:** `FitInput.kv_auto` makes the same choice and returns `FitResult.kv` (`KvChoice`: level, types, reason, f16 and chosen KV bytes, prompt-processing slowdown measured on this backend). `vram::input_from_launch` turns on `kv_auto` for a configuration with empty types; this way the gateway scheduler's eviction decision and the Control API `GET /models/{id}/fit` (when no types are given) see the same number as the launch. The Dashboard shows this below the fit indicator as a plain sentence; the technical flags are in the tooltip.
* **Prepare Server** (`prepare.rs`) uses the same ladder: at and above the recommended context, quality comes first (the best-fitting step); below it, context comes first. If f16 fits at the recommended context, a "larger context, 8-bit" alternative (`larger_ctx`) is offered. OOM recovery (`recovery.rs`) also steps the KV option down to the next rung of the machine's ladder (`RecoveryInput::kv_ladder`): f16 -> q8_0 -> K q8_0 + V q4_0 on Vulkan and CPU, f16 -> q8_0 on CUDA, ROCm and Metal, where the smaller-context option is the way down after that. The speed allowance in the Dashboard note (`prompt_slowdown_pct`) is the worst prompt-processing slowdown measured per backend: Vulkan q8_0 7%, K q8_0 + V q4_0 14%, K-only 10%; CUDA 6%, 6%, 3% (q4_0/q4_0 5%); ROCm 5% for every level; Metal 0% for matched pairs and 87-90% for mixed ones. No number is shown on other backends.
* **Principles:** explicit choices and custom arguments always take precedence; V is never quantized without flash attention; the automatic policy never lowers keys below 8 bits.

### 5.4d. Concurrent Requests (slots, `slots.rs`)
How many requests does one llama-server answer at the same time (`-np`)? The setting is per server/definition: **Auto** (default), 1, 2, 4, 8 or a custom number (Dashboard > Parameters > "Concurrent requests"). Measurements: [PERFORMANCE.md](PERFORMANCE.md#concurrent-requests-slots).

**Research:**
* llama-server's own default is `-np -1` (auto) = **4 slots + unified KV** (`--kv-unified`): a single pool of `-c` tokens, where every request can use the whole context ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [server.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server.cpp), [PR #16736](https://github.com/ggml-org/llama.cpp/pull/16736), Nov 2025). When `-np N` is given explicitly, `kv_unified` stays off and each slot gets `n_ctx / N` ([llama-context.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp)).
* In the unified pool, the KV of full-attention layers does not grow with slots. What does grow: sliding-window layers, with `pad256(n_swa*n_seq + n_ubatch)` cells ([llama-kv-cache-iswa.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache-iswa.cpp)); recurrent/hybrid layers (Mamba, Qwen3.5/3.6 gated delta net), one state per slot (`recurrent_rs_size = max(1, n_seq_max)`, [llama-model.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-model.cpp)); and the context checkpoints of these models in system memory (at most `--ctx-checkpoints` per slot, [PR #15293](https://github.com/ggml-org/llama.cpp/pull/15293)).
* If concurrently running requests exceed the pool, llama-server first evicts idle slots, then shrinks the batch; if that still does not fit, **all running requests** get "Context size has been exceeded" ([server-context.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server-context.cpp)). The pool is shared but there is no admission control.
* Ollama: the `OLLAMA_NUM_PARALLEL` default is now **1** (it used to be 4/1 depending on memory), and the context is allocated as `num_ctx x num_parallel`; hybrid families (qwen35, qwen3next, nemotron_h, lfm2, ...) are forced to 1; `OLLAMA_MAX_QUEUE` is 512, `keep_alive` is 5 min ([envconfig/config.go](https://github.com/ollama/ollama/blob/main/envconfig/config.go), [server/sched.go](https://github.com/ollama/ollama/blob/main/server/sched.go), [FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx)).
* LM Studio 0.4: "Max Concurrent Predictions" defaults to 4 + unified KV ("no extra memory"); JIT loading, idle TTL 60 min, auto-evict ([parallel requests](https://lmstudio.ai/docs/app/advanced/parallel-requests), [TTL and auto-evict](https://lmstudio.ai/docs/developer/core/ttl-and-auto-evict)).
* vLLM / TGI / SGLang: memory is a shared token pool (PagedAttention / RadixAttention), concurrency is flexible and **admitted by token budget** (vLLM `max_num_seqs` 256-1024, `gpu_memory_utilization`; TGI `max_concurrent_requests` 128 + `max_batch_total_tokens`; SGLang `max_running_requests`) ([vLLM arg_utils](https://github.com/vllm-project/vllm/blob/main/vllm/engine/arg_utils.py), [TGI launcher](https://github.com/huggingface/text-generation-inference/blob/main/launcher/src/main.rs), [SGLang server args](https://docs.sglang.io/advanced_features/server_arguments.html)).
* Decoding is limited by memory bandwidth: when several requests are processed together, total generation goes up and per-request speed goes down. Agents (Claude Code sub-agents, OpenCode) can send several requests at once in a single session ([Claude Code sub-agents](https://code.claude.com/docs/en/sub-agents)).

**Inference for a single-user desktop with local agents:** if a slot is cheap (unified pool, full attention), 4 slots as in llama-server/LM Studio is right; if it is expensive (sliding window, recurrent state), few slots as in Ollama is right. But because the pool is shared, the slot count should be as many as the simultaneous requests can fit; otherwise, instead of waiting in line, two requests at once both get errors.

**Decision - the Auto rule (`slots::decide`, deterministic):**
1. **Pool:** slots <= `context / request length` (1, 2 or 4). The request length is 8k tokens for a server started by the user (Dashboard, Playground, Library, CLI `serve`), 2k for the gateway's JIT loads (`launched_by = gateway`), and 32k tokens for a direct agent server ("Prepare Server", `launched_by = agents`) (32k = the smallest context among agent tools). The gateway can use 2k because the scheduler weighs each request's estimated tokens against the pool (token admission, `Scheduler::acquire`): requests that do not fit the pool wait instead of getting an error, and in the unified pool each request can still use the whole context. Before this, on the gateway's 32k default context, Qwen3-4B got 1 slot and four parallel streams ran one after another (in a comparison: 53 t/s total versus 157 for LM Studio). With an 8k share the same happened on a 4 GB NVIDIA card, where the 4B's context is 12k: 54 t/s total and up to 14.5 s to the first token; through the gateway with 4 slots 148 t/s and 0.8 s, with the single-stream speed unchanged. On CUDA the host prompt cache stays on for such a pool so idle slots are cleared from it; on the other backends it is turned off (`--cache-ram 0`; PERFORMANCE "Unified pool + main-memory prompt cache stall").
2. **Memory:** if one more slot costs more than 64 MiB by the `vram::fit_with` estimate (VRAM + checkpoint RAM): **1** for a user server; **2** for an agent server, but only if the model fits entirely on the GPU with 2 slots as well (85%), otherwise 1. If the model does not fit completely anyway, 1.
3. If the result is 4, Harness sends nothing (llama-server's own default). If there are multiple slots in the unified pool and the user did not choose, `--cache-ram 0` is added: on llama.cpp b11552, unified KV + the main-memory prompt cache stalls every request wave by ~3.7 s (4 streams: 172 t/s total, 400 with `--cache-ram 0`; [PERFORMANCE.md](PERFORMANCE.md#out-of-the-box-settings-and-parallel-requests)). For fewer, `-np N`, and `--kv-unified` if N > 1 (an explicit `-np` would turn off the unified pool and split each request's context).
* A value chosen by the user is used as-is (for N > 1, if the user did not choose `kv_unified`, `--kv-unified` is added); `-np`/`--parallel` in the custom arguments takes precedence over everything (Harness does not send its own `-np`), and likewise `--kv-unified`/`--no-kv-unified`. Router mode is left untouched. On old builds without the `--kv-unified` flag (before late 2025), Auto sends nothing (that build's default is 1).
* Examples (on a 16 GB test GPU): Qwen3-4B 32k chat -> 4 (not sent); 8k -> 1; agent 64k -> 2. gpt-oss-20b (window 128, ~3 MiB per slot) -> same as Qwen3-4B. Gemma-4-12B -> chat 1 (320 MiB VRAM per slot + 4 x 320 MiB checkpoints), agent 64k -> 2. Qwen3.6-27B Q4 (does not fully fit on a 16 GB card) -> 1.

**Implementation:**
* `vram::fit` (`estimate_fit`, `GET /models/{id}/fit`, `harness show`) treats `parallel_slots: null` as Auto and returns `FitResult.slots` (`SlotAdvice`: `slots`, `auto`, `recommended`, `recommended_agents`, `reason` i18n key, `per_slot_bytes`, `ctx_per_slot`); the estimate is made with the chosen slots. In the lower-level `fit_with`, `None` is still llama-server's 4 slots.
* Order: slots first, then KV precision (§5.4c) for that slot count. When types are automatic, the slot rule decides with f16 KV (one slot is not "paid for" by quantizing the cache); `vram::fit` returns both `FitResult.slots` and `FitResult.kv` in the same order.
* Launch (`ProcessManager::start_run`): `slots::plan_for_launch` adds `-np`/`--kv-unified` to the arguments without changing the stored configuration and writes a line to the server log. `vram::input_from_launch` uses the same plan: the gateway's eviction estimate and the key of the load measurement (`record_after_load`) see the real slot count.
* The estimate now accounts for: the SWA layers' own KV heads/head size (Gemma 4: 8 x 256 on a window layer, 1 x 512 on full attention; per-layer `head_count_kv` + `sliding_window_pattern` arrays and `key_length_swa` in the GGUF), recurrent state (`ssm.*`, `full_attention_interval`; KV only on attention layers) and the checkpoint ceiling (`checkpoint_bytes`, added to RAM: slots x `--ctx-checkpoints` x window/state copies).
* UI: "Concurrent requests" under Dashboard > Parameters (moved from Advanced > Performance); under it a single line: "Auto: N requests · reason", "Recommended: N · reason" if the chosen value differs from the recommendation, and "If agents load through the gateway: N" if the agent recommendation differs. "Prepare Server" no longer writes `parallel_slots: 1` (it removes the key from the definition; the gateway loads with the agent rule); "prepare the server for this tool" in the GUI restarts the running server with Auto + `launched_by: agents`.
* Gateway: `ModelSlot.waited` = the number of requests that arrived while all slots were busy since this load; under Settings > Gateway > Models it is shown as a hint for a model with fewer than 4 slots (increase "Concurrent requests" on the next load). If a model is reloaded with fewer slots, the excess permits are taken back from the semaphore.
* **Token-budgeted admission (`gateway::admission`, `scheduler`):** in the unified pool (`kv_unified` + `-np N`), `n_ctx` is the whole pool; when concurrently running requests exceed it, llama-server drops all of them. Each `Entry` has, besides the slot semaphore, a **token semaphore** (as many permits as the pool size, from `/props`; on a JIT load `adopt` rereads it). `acquire_tokens(def, Some(&Demand))` takes the slot first, then the permits for the `Demand` (prompt + generation) in fair order (FIFO `acquire_many`); both are held in the `Lease` until the request ends. `Demand`: text bytes/3 (upper estimate), image 1024, 8 per message, generation `max_tokens`/`max_output_tokens`/`max_completion_tokens`/`num_predict` or 1024; for prompts over 8 KiB, the server's `/tokenize` (5 s, falling back to the estimate). A request that does not fit the pool alone is clipped to the pool size (it goes alone in the queue; if it overflows, it gets the server's own error, the gateway does not invent one). Embeddings, rerank and `count_tokens` are outside the budget; on a server whose slots are not unified, there is no budget. Waiting is subject to `queue_timeout`, and `Lease.waited` = `slots` | `tokens` is written to analytics.
* **Queue hint (`analytics::queue_hints`):** `requests.slots` and `requests.waited` (v2) summarize the last 7 days per definition; the rule is `QueueHint::suggest` (>= 10 requests, waited share >= 20%, mean wait >= 500 ms, slots < 8, suggestion 2/4/8). Only slot waits are counted; a pool wait is not a reason to increase. The UI writes the suggestion into `parallel_slots`; a reload is required (no live adaptation).
* **No live adaptation:** the only way to change the slot count without interrupting a running generation is to reload; automatically increasing it from queue statistics would make pool overflow (above) more likely. Instead, token-budgeted admission (like TGI/vLLM) and a hint based on queue history are on the [ROADMAP](ROADMAP.md).

### 5.5. Import from External Model Stores (`importer.rs`)
* **Ollama:** `~/.ollama/models/manifests` is read and the model layer is resolved to a `blobs/sha256-<hex>` file; only blobs that carry the GGUF magic number are accepted.
* **LM Studio:** the `downloadsFolder` in `~/.lmstudio/settings.json` is scanned; `mmproj` files are matched to models and split sets are reduced to the first shard.
* **Mode:** *Link* (the file stays in place and is added to the library via `config/external_models.json`) or *Copy* (a hard link is tried first, otherwise a real copy). Only paths returned by a fresh scan can be imported.
* Models added by link cannot be deleted or moved by Harness Studio; only their links can be removed.

## 6. Live Telemetry Stream

While a server is active, a lightweight telemetry poll runs in the background (`orchestrator::run_telemetry_sampler_watched`): once per second (1 Hz) while a request is being processed or the window is open, every 5 s when servers are idle and the window is closed/minimized; and one sample immediately when a gateway request finishes. The sampler sleeps while no server is running; while the Dashboard's memory indicators are visible, only RAM/VRAM is read every 2 s. The UI does not poll: the backend pushes changes as events (`servers-changed`, `telemetry` only for the watched server and when there is a meaningful difference, `server-logs`, `downloads-changed`, `gateway-changed`; `src-tauri/src/push.rs`, `harness_core::changes`). Measurements: [PERFORMANCE.md](PERFORMANCE.md).
* **Tokens/sec (instantaneous generation speed):** read directly from the gauges `llamacpp:predicted_tokens_seconds` (response speed) and `llamacpp:prompt_tokens_seconds` (prompt processing speed) in the Prometheus output that `llama-server` exposes with `--metrics`.
* **Slot status:** `GET /slots` (enabled by default) is read to show the number of concurrently active/idle slots.
* **RAM / VRAM:** On Windows, the PDH `GPU Adapter Memory` counter (the query is kept open, `gpu::VramMonitor`); on Linux, system-wide VRAM via sysfs (AMD/Intel) and NVML for NVIDIA (`nvml.rs`, loaded from `libnvidia-ml.so.1`; nvidia-smi when NVML cannot load); RAM via sysinfo (only memory is refreshed). System memory is shown even when no server is running (read on demand, `TelemetryPoller::fresh_snapshot`).
* **Multi-server monitoring:** The sampler already reads all active servers every round; when a view says "show all running servers" with `watch_telemetry(server_id, memory, all)`, `push::TelemetryWatch` compares each server's `material_change` against the last one sent and pushes the `telemetry` event only for servers that changed (`get_telemetry_all` provides the initial state). In the UI, `app.telemetryAll` / `app.tpsByServer` are keyed by server id; the selected server's `app.telemetry` and `app.tpsHistory` are derived from them. There is no new timer; `all` is requested only while the Dashboard telemetry panel is open. Logs: `stores/serverLogs.svelte.ts` reads the buffers of the displayed servers with a per-server cursor (the `server-logs` push) and gives lines an arrival order from a single counter.
* **Memory breakdown (RAM and VRAM):** `TelemetrySnapshot.ram_breakdown` and `vram_breakdown` are the same type (`MemoryBreakdown`: Harness Studio, per server, other). Process trees are built once with `telemetry::process_trees` (own process tree - server subtrees; each server's child processes are attributed to it); `attribute` sums per-tree values with saturation, and `other = used - Harness - servers` never goes below 0. The RAM value is the process working set; the VRAM value is the GPU memory dedicated per process: on Windows, PDH `\GPU Process Memory(*)\Dedicated Usage` (a single query kept open, `gpu::ProcessVramProbe`; instances whose name's `luid_...` matches the monitored graphics card are summed per pid with `sum_by_pid`), on Linux for AMD/Intel, the DRM lines in `/proc/<pid>/fdinfo` of the processes in the tree, and on Linux for NVIDIA the NVML process list (not yet verified on hardware). If there is no counter (macOS, or Linux+NVIDIA when NVML cannot load), `vram_breakdown = None` and the UI shows an undivided bar; no value is estimated. Segment colors come from `serverColor.ts` (per server `--chart-1...5`, then a hatch pattern) and `memorySegments.ts` (pure splitting).
* **Per-server history:** All running servers are polled in parallel; each server's in-memory history is kept separately and is preserved after the server stops.

## 7. Privacy and Error Diagnostics Architecture (Privacy-First Diagnostics)

### 7.1. Explicit Consent and Onboarding Flow
* When the application is opened for the first time, an explicit consent dialog is shown:
  > *"Would you like to share anonymous usage, hardware and error diagnostics data to help us improve Harness Studio?"*
* Unless the user consents, **no network request (network diagnostics request) is made.**

### 7.2. Granular Permission Categories (Settings > Privacy)
The user can turn each data category on or off independently from the settings screen:
1. **Crash Reports:** Stack traces of unexpected application crashes.
2. **Application Errors:** Harness Studio UI or Rust core errors.
3. **llama.cpp Errors:** Error codes and sanitized error logs of the `llama-server` child process.
4. **Hardware Information:** The minimal system profile for hardware and driver compatibility analysis (OS, GPU model, RAM/VRAM, driver version).
5. **Performance / Runtime Metrics:** Model load times and average tokens/sec statistics.
6. **Anonymous Usage Analytics:** UI interactions and session frequency *(a toggle fully independent of Diagnostics)*.

### 7.3. Diagnostics Transport Limits and Offline Crash Reporting
* **Secure transmission:** Data is sent only over HTTPS, to the official diagnostics endpoint controlled by Harness Studio.
* **Payload scope:** Only data belonging to the categories the user has explicitly left "ON" is added to the payload.
* **Hard data limits:**
  * ❌ User prompts and model responses (chat contents) are never sent.
  * ❌ File contents and API request bodies are never sent.
  * ❌ API keys are never sent.
  * ❌ Personal file paths are sanitized before sending (`C:\Users\UserName\...` -> `C:\Users\<USER>\...`).
* **Offline crash capture:** If the application cannot send a report at the moment of a sudden crash, the crash record is safely written to a local temporary file (`logs/crash_dump.json`). On the next launch, **only if the user's Crash Reports permission is still on**, this report is sent and the local copy is deleted; if the permission is off, the report is silently destroyed.

## 8. Multiple Servers and Profiles

* **Server Registry (`servers.rs`):** Keeps one `ProcessManager` per server id; the default id is `default`. All server-related commands take an optional `serverId`; if not given, the default server is used.
* **Port safety:** Before launching, the port is checked both for a clash with another Harness server and for being occupied at the operating system level (connect + bind attempt). Because on Windows a `0.0.0.0` bind can succeed while `127.0.0.1` is taken, a connect attempt is made as well.
* **Automatic port (`ports.rs`, `orchestrator::settle_port`):** The user does not have to choose a port.
  - When `LaunchConfig.port_auto` (and `ServerProfile.port_auto`; port 0 means the same) is on, the port is chosen at launch from Harness's range (`ports::AUTO_RANGE`, 11440-11499). If the last chosen port (`port`) is free it is used again; otherwise the first free port is taken, skipping the ports of other running servers and saved profiles. The range contains none of the ports commonly used by other software (`ports::WELL_KNOWN`: 8080, 3000, 5000, 5173, 8000, 8888, Ollama 11434, LM Studio 1234, Harness's own 11435/11500, 9931 which llama.cpp will use by default in the future, ...).
  - On a fresh install, `settings.server.port` is 0 (automatic). A port in previously saved settings and profiles (e.g. 8080) counts as an explicit choice and works as before; if the `port_auto` field is missing, it is off.
  - New servers (Dashboard "New Server", server duplication, `LoadTarget::NewServer`) and the `gw-*` servers the gateway opens via JIT use the same rule (previously the gateway searched from its port+1 and the Dashboard form from port+1).
  - If the port chosen by the user is occupied, the launch is rejected and the error names the program holding the port: `servers.port_in_use_by {port, program, pid}` ("Port 8080 is used by 'ollama.exe'"), `servers.port_in_use_at {port}` if the program cannot be found, `servers.port_in_use_server {port, server}` if it is another Harness server. All start with `servers.port_in_use` (CLI exit code 4, HTTP 409).
  - The process holding the port (`ports::holder`): on Windows `GetExtendedTcpTable` (`TCP_TABLE_OWNER_PID_LISTENER`, IPv4 + IPv6), on Linux `/proc/net/tcp*` (inode of the LISTEN line) + `/proc/<pid>/fd`, on macOS `lsof -iTCP:<port> -sTCP:LISTEN`; the name comes from `sysinfo` (on Linux `/proc/<pid>/comm`).
  - **Bind race:** Between the port check and llama-server's bind, another program can take the port. If a run with an automatic port exits during loading with the `port_in_use` class, `ProcessManager` keeps the server in the "Starting" state, picks the next free automatic port and repeats the same launch there (`MAX_PORT_RETRIES` = 3, reset by a user launch; the log says "retrying with automatic port ..."). The gateway's pending request is not dropped meanwhile. There is no retry on a port chosen by the user; the classified error stays and the program holding the port is written to the log.
  - **Model status and load/unload:** `router::list/load/unload` call the router's `GET /models`, `POST /models/load`, `POST /models/unload` endpoints (`status.value` = `loaded` | `loading` | `unloaded`; `failed`/`exit_code` on a failed load; unknown model 404). Surfaces: Tauri `list_router_models`/`load_router_model`/`unload_router_model`, Control API `GET /servers/{id}/router/models` and `POST …/router/models/load|unload` (`{model, wait_seconds}`), CLI `harness router models|load|unload`, and in the UI a model list under the running router in the Servers list and on the Dashboard (Load/Unload buttons, 1-3 s polling). If the server is not running or is not a router: `router.not_running`/`router.not_router` (HTTP 409).
  - **Per-model preset:** When a router starts (`ProcessManager::run_claimed`), a section is written to the `--models-preset` INI file (`config/router-presets/<server>.ini`) for every Harness model definition in the served directory: the section name is the definition's alias, `model =` is the file path, followed by the options a single-model server would receive. The options are produced from the definition via `resolve_launch` + `serve_mode::prepare` + automatic context + `build_args_with` (context, ngl, KV types, template, mmproj, LoRA, draft model, ...), so the GGUF metadata fixes of the single-model server (e.g. the `--override-kv` of `gemma3.attention.sliding_window=int:512` for Gemma 3 QAT) also reach the model in the router. Server-level options (`--host`, `--port`, `--api-key`, `--alias`, `-m`, `--models-*`, `--cors-origins`, `--webui*`, `--log-*`, ...) are not written to the preset; multi-line values are skipped. The keys this build accepts were measured: `c`/`ctx-size`, `ngl`, `flash-attn on`, `ctk`, `override-kv`, `jinja`, `cache-ram`, `no-warmup`, `kv-unified` (an unrecognized key prevents the router from starting at all; so keys are derived only from flags the runtime knows, from the `build_args_with` output). If the definition is outside the directory, no section is written; models in the directory with no definition load with llama-server defaults.
  - **Gateway routing:** For a model name that matches no definition or `srv-` server, `Scheduler::resolve` looks at the `GET /models` list of running router servers (`router_externals`) and produces a temporary definition for each model (`srv-<server>/<model>`, `router_external_models`); `definition_states::serves` counts the router server as serving these definitions. The request goes straight to the router, which loads the model if it is absent. A router model with the same alias as a registered definition is left to the registered definition. `/v1/models` lists these models too. Limit: the gateway counts the router's models as single-slot (the router does not report slots in `/props`).
  - Tests: `router.rs` unit tests (preset INI, argument-to-key conversion, `/models` parsing), a `scheduler` routing test, and `crates/harness-core/tests/router_e2e.rs` with a real runtime (`cargo test -p harness-core --test router_e2e -- --ignored --nocapture`: two GGUFs, preset, load/chat/evict/unload).
* **Profiles:** `ServerProfile { id, name, model_id, config, auto_start }` records are stored in `config/profiles.json`; a profile can be launched as a separate server with one click.
* **Last session / default server:** Every launch of the default server (the Dashboard's own server) is written to the profile with `id = "default"` in `server_profiles.json` (the former `last_session.json`). If "Restore last session" is on, it is restarted at application launch together with the `auto_start` profiles.
* **Single source of truth for the default server:** This `"default"` profile. `servers::default_server()` (the `get_default_server` command, `Domain::default_server`) gives the value every view reads while the server is not running: the saved launch (`saved: true`), or, if nothing was ever saved, the server defaults in Settings (`server.host/port/default_ngl/default_ctx`, no model). If a record whose definition was deleted cannot be resolved, its address (host/port) still comes from the record. The Dashboard form loads this record on reopening; the Servers list, the server picker in the title bar and `app.port` use the same value (the live value while running). The port in Settings is only the starting value for new/never-saved servers. The "Saved / Not saved" label on the Dashboard compares the form to the record (a profile or `"default"`); on the default server, changes are saved at launch.

## 9. Chat Playground, Tool Calling and MCP

* **Playground:** Sends streaming requests directly (without a proxy) to the selected server's `/v1/chat/completions` endpoint. Chat content is not saved or sent anywhere beyond the local conversation store.
* **Tool loop:** The `delta.tool_calls` fragments in the stream are merged; tools are run in the Harness core (`tools_run` -> `ToolService`), and the result is fed back to the model (the round limit comes from the core, currently 8). The approval decision belongs to the core (`tools_decision`): the UI only shows the prompt when it says `ask`. Details, and why the loop stays in the UI, below ("Tool loop").
* **Tools:** The list offered to the model comes from the core via `tools_list` (seven built-in tools; each with a class, schema and policy decision). The tools of MCP servers also come from the core and run in the core; no path goes to llama-server's `GET/POST /tools` endpoint (the old `--tools` path was removed). Harness tools can also be offered to MCP clients (`harness-mcp` `harness_tools.rs`, `settings.tools.mcp_expose`, scope `tools`; see [MCP.md](MCP.md)).
* **Tool loop: why the orchestration lives in the UI.** `runAgentLoop` / `executeToolCalls` (TypeScript) manage the choreography of a streamed chat: they collect `tool_calls` fragments while tokens stream to the user, update each round on screen as a `ToolCallCard`, wait for the approval prompt, cut both the stream and the running call when Stop is pressed, measure the context threshold after every round and compact the conversation (`beforeNextRound`), and run two loops side by side in the split view. All of this depends on UI state (reactive message objects, the write queue, partial writes to `state.db`); moving it into the core would have required turning all of that state into an event stream and would have gained the Playground nothing. So the tool side moved into the core: the decision (policy), working-directory scope, timeout / size / cancellation, the log and the limits (`ToolLimits`); the UI only calls these and reads the values (the round limit, timeout and result size come from the core, shared with the CLI and API). What will be moved into a core loop when needed is the gateway's **server-side tools**: serving Harness tools to the model and running the loop on the server, without a client (Claude Code, Codex, a script) arriving at `/v1/chat/completions` with tool schemas, requires a loop on a surface that has no UI. `harness_core::tools::agent::run_agent` is the non-streaming loop; its streaming counterpart `harness_core::tools::agent_stream::run_agent_stream` was added later (see "Server-side tools" below). **The Playground's own loop was deliberately left in place:** the core loop yields an event stream (`AgentEvent`) and takes an `Approver` for approval, but the Playground's behavior is tied to UI state: the approval prompt waits for the user and "always approve in this session" is kept in memory, the split view runs two loops side by side, `ToolCallCard` states and partial `state.db` writes are fed from reactive message objects, and the `beforeNextRound` compaction changes the UI's message list. Translating these into a Tauri event bridge without loss of behavior would gain nothing today; since the core's hooks (`RoundHook`, `AgentEvent`) are ready, it can be moved later.
* **Server-side tools (`harness-gateway/src/server_tools/`).** The gateway can give the model a tool the client asked for and run the loop itself. It is off by default; `GatewaySettings.server_tools` enables `{web_search, tools[]}` per model definition (Settings > Gateway > "Server-Side Tools"). Flow: `plan()` reads the request and turns the hosted `web_search` tools (Chat `web_search_options` and `web_search*` types, Responses `web_search*`, Messages `web_search_2025…`) and explicitly enabled Harness tools into the list offered to the model; the tools go through `check_policy` (only those the policy runs without asking: safe or trusted; those with "ask"/"deny" get `403 server_tool_not_allowed`, an unknown tool `503 server_tool_unavailable`, and a dangerous class on a gateway listening on the network `403`). `serve()` converts the request to chat form (`convert.rs`), the core runs the streaming loop (`run_agent_stream`; a separate scheduler lease for each round; the round limit, call timeout and result size come from `ToolLimits`) and writes the result in the request's wire format (`wire.rs`). The client's own tools (functions in `tools[]`) are offered to the model but never run: if a round calls a client tool, the loop ends and the calls return to the client (server calls in the same round are dropped and counted). The client's `tool_choice` applies only to the first round. Visibility: `X-Harness-Compat` (`server_tools=…`, `hosted_fulfilled=web_search`, `server_tool_calls=N`, `server_tool_rounds=R`, notes on errors and dropped calls), `tool_involved` / `tools_offered` / `tool_calls` in the request log, and in the tool log the client `gateway` and chat = request id. If the client closes the connection, the loop is cancelled (`499`).
  * **Scope:** Chat Completions, Responses (JSON and SSE; including `previous_response_id` / `store` / `background`) and Anthropic Messages (JSON and SSE). In Responses only `web_search` appears as a `web_search_call` item, and other server tools are hidden; Messages has no `server_tool_use` block, and `usage.server_tool_use.web_search_requests` is filled in. If the round limit is reached, a short note is appended to the response.
  * **Out of scope:** The Ollama API path (`ollama/mod.rs`) does not use server-side tools; the tool-diagnosis categories ([TOOL-DIAGNOSIS.md](TOOL-DIAGNOSIS.md)) are not computed for requests with server tools; Anthropic `web_fetch` is not mapped; `harness launch codex` still passes `web_search=disabled`.
* **MCP client (`tools/mcp_client/`):** Harness speaks MCP itself. `mcp.rs` stores and validates server definitions (command/args/env or url/headers, disabled; secrets in the keychain) and imports them by reading the Claude Desktop / Claude Code / Codex / Cursor / LM Studio configurations (read-only). `McpHub` (part of `ToolService`) connects servers from these definitions on first need, keeps them open (reconnecting on call if one dies, restarting if the definition changes) and registers their tools in the `ToolRegistry` with the `mcp` source under the name `<server>_<tool>`; the surfaces (Playground, CLI, Control API) go through the same `ToolService` without knowing anything about MCP. How it works: `McpConnection` wraps a transport (a stdio process or Streamable HTTP) and a hand-written two-era JSON-RPC (2026-07-28 / `initialize`); background tasks read notifications (`list_changed` -> refresh the list). The tasks hold shared state, not the connection handle: when the handle is dropped, the server (for stdio, the process tree) dies. Legacy path: llama-server's own MCP option (a launch setting, off by default) produces `mcp_servers.runtime.json`, wrapping commands like `npx` with `cmd /c` on Windows, and passes it with `--mcp-servers-config`; the Playground does not use it.
* **Direction:** the tool loop is moving into the core; built-in tools and the MCP client are in the core, and llama-server's `--tools` path was removed. Only llama-server's own MCP option (`--mcp-servers-config`) remains; see §14.
* **Model requirement:** Tool calling needs a model whose chat template supports tool calls; models without that support produce the call as plain text.
* **Mermaid diagrams:** While splitting fenced blocks, `MessageContent` also tracks whether the block has closed; a ```mermaid block is shown as code until it closes. Once closed, when it approaches the viewport (IntersectionObserver) and has stayed unchanged for 400 ms, `playground/mermaid.ts` loads Mermaid with a dynamic import (it is not in the initial bundle) and renders it. Settings: `securityLevel: 'strict'`, `htmlLabels: false`, `suppressErrorRendering`, `maxTextSize` 50 000, `maxEdges` 500; the `%%{init}%%` directive inside a diagram cannot change the theme, `htmlLabels`, `themeCSS`, font and security keys thanks to the `secure` list. The output passes through DOMPurify with the SVG profile only (no `foreignObject`, `script`, `image`, `a`, animation; `href`s other than `#` and `@import` / external `url()` in CSS are removed). Colors for the `base` theme are read from the application's semantic tokens (`--card`, `--foreground`, `--primary`, `--chart-*`, ...); it is redrawn when the theme changes (`onSchemeChange`, `prefers-contrast`). On error: the code and a short localized message. Saving the SVG is `export_diagram_svg` (save dialog, at most 8 MiB).
* **Drag and drop in chat folders:** `ConversationSidebar` uses pointer events instead of HTML5 drag and drop: while Tauri's file-drop handler (`dragDropEnabled`, Playground documents) is on, WebView2 on Windows does not forward the HTML5 `drop` event to the page; and since a pointer drag does not start an OS drag, the file-drop event is not triggered. A 5 px threshold, `data-drop-folder` targets (a folder; for the root, the "Recent" section and a dashed area that appears during the drag), auto-scroll at the edge, cancel with Escape; persistence through the existing `move_conversation`. The keyboard path is "Move to folder" in the row menu.
* **Documents / local RAG (`harness_core::rag`):** files attached to a chat are processed on this machine; there is no network apart from the gateway.
  - Extraction (`rag::extract`): PDF with `pdf-extract` 0.12 (MIT, on top of `lopdf`), page by page; for DOCX, `word/document.xml` inside the zip is scanned by hand (`w:t`, `w:tab`, `w:br`, `HeadingN` -> `#`); text is UTF-8/16 per BOM, invalid UTF-8 as Windows-1252; a file with NUL bytes is treated as binary. Options rejected: `lopdf` directly (poor text quality, no font encodings/CMap) and Python/pdfium (an external dependency). `pdf-extract` can `panic!` on a corrupt file and the release profile is `panic = "abort"`: in a release build the PDF is read in a child process by the application's own exe with `--harness-extract-pdf <path>` (`main` calls `rag::extract::child_main` first; JSON on stdout; killed after 180 s). In `panic = "unwind"` builds (debug, test) `catch_unwind` is used in-process. A read cannot be interrupted but does not wait for cancellation: the work runs on a thread that blocks on the read and checks a cancel flag every 100 ms (`rag::blocking_or_cancel`); when the flag is raised the document becomes `cancelled` immediately, and the unfinished read keeps running in the background to its end and its result is discarded.
  - Chunking (`rag::chunk`): paragraphs separated by blank lines are packed to ~900 characters (at most 1200), with ~150 characters of overlap within the same section (the end of the previous chunk, at a sentence/word boundary); a Markdown heading starts a new chunk and is stored as `Parent › Child`; the heading is also given to the embedding. The page range is kept. Embedding servers take the model's training context as the batch size (`serve_mode`), which is far below the limit.
  - Store: `state.db` v5 (below). Vectors are L2-normalized f32 BLOBs; cosine = dot product. Search is exact (brute force): at most 6000 chunks per chat x e.g. 768 dimensions takes a few milliseconds, so no index structure is needed. Limits: file 64 MiB, text 4M characters, 50 documents per chat.
  - Embedding/rerank: to the gateway's managed endpoint (`/v1/embeddings`, `/v1/rerank`) with the definition alias, the Harness client token and `X-Harness-Client: Harness Playground`; the model is JIT-loaded and unloaded by TTL. Suitable definitions come from the GGUF header (`domain::detect_kind`, `rag::models`). Task prefixes by model family (nomic, E5, EmbeddingGemma, Qwen3-Embedding, mxbai/bge-en). Batches of 16; progress is the `rag-progress` event, the cancel flag is checked between batches. Only one indexing job at a time (memory). When the application closes, a half-finished document becomes `cancelled` and can be resumed (existing vectors under the same model are kept). Vectors from different models are never mixed: a model change re-embeds.
  - Retrieval (`rag::prepare`): ready documents are planned: `full` documents, and `auto` documents that together fit in half the context (`FULL_TEXT_SHARE`; 4096 if unknown), are added to the system message as full text (constant throughout the chat, so the prompt cache is preserved); the others are searched. Search: the question is embedded with the query prefix, cosine top 50 + FTS5 BM25 top 50 (a quoted OR query of the question's words), Reciprocal Rank Fusion (k=60), an optional reranker (`top_k x 4`, at least 20 candidates), and the top `top_k` excerpts are substituted for the last user message with `[1]..[k]` numbering (the stored message is unchanged; only for that turn). Sources and notes (`rag.notice_*`) are stored in the `meta.rag` field of the assistant variant.
  - Tauri commands are `rag_*` (`src-tauri/src/commands/rag.rs`); not in the Control API or CLI (chats are not in the API yet). The split view also uses documents (both sides see the same excerpts). Copying, forking and exporting a chat to JSON carries the documents (see `ExportedDocument` below).

### 9.1. Context Compaction (`harness_core::compaction`)

When a long chat exceeds the model's context, old turns are replaced **only in the request** with a summary written by the model; the latest turns go as they are. Research, the rationale for the defaults and measurements with real models: [COMPACTION.md](COMPACTION.md).

* **Persistence: a marker node, no schema change.** A compaction is a message appended to the end of the current path: `role = 'system'`, the summary in the variant's `content`, the details in `meta_json.compaction` (v4 column):
  ```text
  { version, boundary_id, covered, turns, kept_turns, trigger: auto|manual, strategy,
    instruction, model, tokens_before, tokens_after, summary_tokens,
    tool_results_cleared, exact_tokens, previous_id, undone, created_at }
  ```
  `boundary_id` is the last message the summary covers. The next user message is a child of the marker. Original messages are not deleted; search (FTS) indexes the summary as well. Because no new table or column was needed, `user_version` stayed at 6. Older versions do not display `system` messages, so they do not see the marker and send the full history.
* **Request rule (Rust `compaction::request_messages`, same as TS `buildApiMessages`):**
  - The newest marker on the path that is not `undone` and whose boundary is found earlier on the path is active.
  - The request: system prompt + a `<conversation_summary>` block (a single system message), followed by all chat messages after `boundary_id`. That is the remaining turns plus those after the marker; markers are never sent.
  - The summary is in a system message because some Jinja templates reject two consecutive `user` messages.
  - Documents (RAG) are re-applied on top of this each turn.
  - A marker made within a response turn (`mid_turn`) also carries `pinned_id`: the running turn's user message stays before the boundary but is sent verbatim right after the system message (`Active.pinned_index`; TS `activeCompaction().pinnedIndex`). The request always starts with the question, and the question being answered does not get mixed into the summary.
* **Branches and variants:**
  - A marker is attached to the active variant of the last message at the time it was written. Editing or regenerating a message before the marker opens a branch without the marker; that branch sends the full history and compacts itself if necessary.
  - Copy, fork and JSON import give messages new ids. `export::insert_export` translates the `boundary_id`, `previous_id` and `pinned_id` in the marker to the new ids (`compaction::remap_meta`).
  - In Markdown export, the summary is written under the heading "Summary of earlier messages".
* **Compaction within a response turn (long tool loop):** a single response can fill the context per round (each `read_file` is a few thousand tokens). In the Playground, `runAgentLoop` calls the `beforeNextRound` hook after each tool round, before the next request (`compactBetweenRounds`). The rule comes from the same settings as for a new message (`auto`, threshold, `autoPaused`): if the size of the last request (`promptN + cachedN + predictedN`) plus the estimate of this round's tool results is >= the threshold, `compact_conversation` is called with `mid_turn: true`. The call runs behind the write queue (the response so far must be in `state.db`) and rejects a stale path via `leaf_id`.
  - **Plan (`compaction::plan_mid_turn`):** the path ends with the running turn. If there are two or more assistant rounds, everything up to the second-to-last round (old turns and the first rounds of this turn) is summarized; the last round, whose results the model has not yet seen, stays as is; the turn's user message is pinned (`pinned_id`). In this emergency `keep_turns` does not apply: old turns are summarized too. If there is a single assistant round, only the earlier turns are summarized and the running turn stays whole. A single-turn, single-assistant-round chat has nothing to compact (`compaction.nothing_to_compact`). On a second compaction, the previous marker's summary is folded into the new summary and the pinned question is carried over.
  - **Summary prompt:** the pinned question is given to the summarizer as context first (it does not count as part of what is being summarized), and the extra instruction asks that every tool call made (name, argument, key result) goes under "Answers and decisions" and only still-needed work under "Open items". Without this, in a real trial the model forgot which file it had read and read the same file again.
  - **Safeguards:** `compaction.no_gain` (not applied if the summary does not shrink the request), `too_little` (10% of the context in auto mode) and `nothing_to_compact` are silently skipped; after an attempt fails once during a response, it is not retried in that response (`midTurnBlocked`). Undo/re-apply and the divider are the same; the divider shows a "during the answer" label. Stop also cancels a running compaction.
  - **None in the split view:** compaction does not run there at all (two side branches cannot be resolved into a single path).
* **Undo / re-apply:** `set_compaction_undone` changes only `meta.compaction.undone`. An undone marker is ignored in requests; if there is an older active marker, it takes effect. If the path's newest marker has been undone, automatic compaction stops on this branch (`auto_paused`); otherwise the same compaction would be repeated on the next message. Manual compaction or re-applying lifts the pause.
* **Plan (`compaction::plan`):**
  - Chat messages after the active boundary are split into turns. A turn is a user message and all the assistant/tool rounds that answer it; a tool call is never separated from its result, so no `tool_call_id` is left dangling.
  - The last `keep_turns` turns (default 2) are kept verbatim. If these exceed 40% of the context, fewer are kept. At least one turn is always summarized.
  - If automatic compaction would summarize less than 10% of the context in text, `compaction.too_little` is returned and the message goes as is. This way the prompt cache is not broken for a small gain.
  - If there is a previous summary, it is folded into the new one (a rolling summary).
* **Summary request (`compaction::compact`):**
  - It goes to the chat's target: the managed endpoint and alias if the gateway is on, otherwise the server's `/v1`; the Playground supplies the headers.
  - Parameters: non-streaming, `temperature 0.2`, `chat_template_kwargs.enable_thinking=false`, `max_tokens` = the summary budget.
  - The summary budget is 1/8 of the context (256-2048) or the value in the settings.
  - The transcript consists of `User:` / `Assistant:` / `Assistant called tool …` / `Tool result …` lines. When "Shorten old tool results" is on, a tool result is cut at 300 characters.
  - If the transcript does not fit in a single request (context - summary - instruction - previous summary - 5%), it is split into chunks and the summary is carried from chunk to chunk.
  - The prompt is `structured`: sectioned, concrete details verbatim, in the user's language. `brief` and `incremental` are used only in the comparison test.
  - Extra instruction: the persistent instruction in the settings + `/compact <instruction>` or the field in the composer.
  - Cancellation: the `cancel_compaction` flag cuts the requests. Only one compaction runs at a time in the same chat (`compaction.busy`).
* **Token counting:**
  - First, the `/tokenize` of the chat model's own llama-server is used (if it is the selected server). Otherwise the endpoint's `/v1/messages/count_tokens` is tried (the gateway passes it through; it counts with the template), and finally an estimate of ≈3 characters/token. The first failure moves on to the next method.
  - A template allowance of 5 tokens per message is added. `exact_tokens` is stored in the marker.
  - The trigger decision is made in the Playground: the measured prompt + generation tokens of the last response (the value of the context indicator) + the estimate for the new message.
* **Trigger and settings:**
  - `Threshold::Percent` (default 80%) or `Threshold::Tokens` (at most 95% of the context). `should_compact(used, incoming, n_ctx)` in Rust, `thresholdTokens` in TS.
  - The context is the chat model's per-slot context (`/props`; on the gateway, the definition's `context_size`).
  - Settings are a global default (`localStorage`) or the chat's own setting (`PgSettings.compaction`, in the chat's `settings_json`; `null` = global). Fields: auto, type, threshold, kept turns, summary model, tool-result shortening, summary length, persistent instruction.
  - The summary model can be another gateway alias; its context is read from the definition.
  - No compaction is done in the split view; an existing marker applies to both sides.
* **UI:**
  - In the composer, "Compact Now" (with an optional extra instruction) and `/compact [instruction]`.
  - In the chat, a divider: "Earlier N messages summarized · auto/manual · tokens before -> after". The summary expands and collapses, with Undo / Re-Apply.
  - Summarized messages appear dimmed and become clear on hover.
  - The context indicator shows the threshold with a line. After a compaction, until a new response arrives, it uses the marker's `tokens_after` value.
  - Error keys are `compaction.*` (`errorsStore.ts`), texts are in `locales/compaction.ts`.
* **Prompt cache:** Compaction changes the start of the prompt. llama-server reprocesses from the first differing token, so the first request after a compaction processes the entire (shrunken) prompt. Later turns benefit from the prefix again, because the summary is a fixed system message. Infrequent, large compaction (threshold + the 10% lower bound) keeps this cost rare.
* **Gateway: compaction in chained Responses (implemented):**
  - The gateway forwards the `/v1/chat/completions` messages the client sends as they are; a stateless client must compact its own history. In a stateful Responses chain (`previous_response_id`) the gateway builds the history itself, so compaction works there.
  - **Request:** `context_management: [{"type":"compaction","compact_threshold":N}]` or `settings.gateway.responses.compaction.auto`. Settings: `auto` (false), `threshold_percent` (80, 10-95; a percentage of the per-slot context), `keep_links` (2, 1-50). `compact_threshold` >= 256 tokens. Any other `context_management` type gets `400 invalid_value`.
  - **Flow (`responses::build_chained`):** `prepare` loads the chain with `StateDb::response_chain_compacted` (stopping when it reaches the newest response with a summary; it works even if the links the summary covers have been deleted) and builds the body after the model is resolved. If compaction was requested, an admission (`acquire_tokens(def, None)`) is taken for the model; the chain + new input is counted with the server's `/tokenize`; if the threshold is exceeded, the old links (`link_entries`: messages, tool calls, tool results shortened to 300 characters) are summarized by the same model's llama-server with `compaction::summarize_transcript` (sectioned strategy, same prompts and chunking as the Playground), and shrinkage is verified with `require_gain`. The request is sent with the summary appended to `instructions` (`<conversation_summary>`, a single system message) and the last `keep_links` links.
  - **Storage:** the summary is stored in the new response's object as `harness_compaction` = `{through, summary, tokens_before, tokens_after, model, links, created_at}` (no schema change; v6). Later requests following the chain stop at the `through` link and append the summary to `instructions`; the client no longer needs to ask for the stored summary every turn. A new summary folds the previous one in (rolling). With `store: false`, the summary is not stored.
  - **A failure never drops the request:** if the summary cannot be written, there is no gain, or the context window is unknown, the request goes without compaction; `x-harness-compaction: skipped: <reason>`. On success, `x-harness-compaction: <before>-><after> tokens`.
  - **Not done:** the summary is not a separate `compaction` item in `input_items`; there is no separate event in the stream; the tool loop within a single response turn is not compacted.
  - **Control API / MCP:** `POST /conversations/{id}/compact` (Playground chats; `harness_core::compaction::compact`; the summary request goes through the gateway running with the gateway client token, otherwise `409 compaction.gateway_required`), CLI `harness conversations compact`, MCP `compact_conversation`.
* **Tests:**
  - `compaction::tests` (21, real SQLite): threshold, budget, chunk, plan (kept turns, 40% limit, at least one turn, automatic lower bound), request rule, undo / return to an older marker, branch, tool-round integrity, tool-result shortening, id translation on fork/copy, prompts.
  - `compaction::e2e` (`#[ignore]`, real llama-server + Qwen3-4B, `-c 4096`): the automatic trigger fires at the threshold, a summarized fact is remembered, the prompt shrinks, undo returns the full history; strategy comparison.
  - `compaction::e2e::compaction_in_the_middle_of_a_tool_loop` (`#[ignore]`, `-c 12288`, `--jinja`): the model reads three real files in a row with a real `read_file` tool, the threshold is exceeded in the middle of the response; the marker is `mid_turn`, the question is pinned, the prompt goes 4385 -> 2240 tokens, the title of the summarized file is present in the final answer, and undo brings all the rounds back. Five unit tests were added to `compaction::tests` (27): the in-response plan (two rounds / one round / second compaction), translation of the pinned id on copy, `meta.rounds` rounds entering the request.

## 11. Desktop Integration

* **Tray:** Show / stop all servers / quit menu; the tooltip shows the number of running servers. If "Minimize to tray on close" is on, closing the window does not terminate the application.
* **Window lifecycle in the tray (`desktop.rs`, `windowActivity.ts`):** The page of a window hidden to the tray is closed after 30 s, if the page has no request in flight and no server is processing a request (`release_window`; "Keep the window loaded in the tray" turns this off); the application stays a single process. When the cursor reaches the tray icon (`Enter`/`Move` on Windows and macOS) or the icon is pressed (`Click` + `Down`, including right-click), the window is rebuilt in the background, hidden (`prewarm_main_window`); a click only shows it. If it is not shown within 20 s (a cursor waiting on the icon extends the time), it is closed again the same way. On Linux the tray is a StatusNotifierItem (`ksni`), which reports only the click (no hover or press): a left click builds and shows the window, and "Show" in the menu does the same. The rebuilt window opens at its previous position and size, and maximization is applied when it is shown; the open tab comes from `localStorage` and is not deleted until the window is seen (a background page closed without being seen leaves it for the next one). The window and web view are built with the theme's background color (`apply_window_background`; must match `--background` in `src/app.css`), and the page is drawn with the script-free launch screen in `src/app.html` (`#hs-splash`); the application removes it when the first screen or the error screen is ready (`#lib/splash.ts`).
* **Autostart:** Launching with the operating system is done with the `--minimized` argument; in this case the window opens hidden.
* **Single instance:** A second launch brings the existing window to the front and closes itself.
* **Window frame:** On Windows/Linux, `decorations: false` + `shadow: true` (`tauri.conf.json`); the application draws the title bar (`Header.svelte`, `common/WindowControls.svelte`). Dragging uses `data-tauri-drag-region` (text/empty area; `deep` only on non-interactive subtrees), double-click to maximize comes from Tauri's drag script. Tauri 2 handles edge resizing on a frameless window itself (`tauri-runtime-wry` `undecorated_resizing`); there is no separate handle. The close button calls `close()` -> `CloseRequested`, so the minimize-to-tray rule applies as is. On macOS, `tauri.macos.conf.json` opens the window with `titleBarStyle: Overlay` + `hiddenTitle` and native traffic lights (since arrays do not merge, the whole window definition is there). Permissions in `capabilities/default.json`: `core:window:allow-minimize`, `allow-toggle-maximize`, `allow-internal-toggle-maximize`, `allow-is-maximized`, `allow-close`, `allow-start-dragging`.
* **Layout:** The title bar and navigation share the same "chrome" tone (`bg-sidebar`), and pages sit on a surface with a rounded top-left corner. Side panels are managed by a single component (`common/ResizablePane.svelte`) and one `PaneState` per panel (`stores/panes.svelte.ts`): width, collapsing, dropping to a strip or opening over the content when the window is narrow; thresholds are based on the window's CSS px width (including the UI scale). State is in `localStorage` as `harness_pane_<id>`.

### 11.1. Theme Token System

* **A single token set:** `src/app.css` defines the same semantic variables for every theme: surfaces (`background` < `card` < `popover`, `secondary`, `muted`, `accent`, `sidebar-*`), text (`foreground`, `muted-foreground`, `*-foreground` on fills), lines (`border` separator, `input` control border, `ring` focus, `--focus-width`), emphasis (`primary`), status (`success`, `warning`, `destructive`, `info`), data (`chart-1…5`; stages and test types, not status), log and diff (`log-warn/error/info`, `diff-add/remove`; aliases to the status colors by default), and code (`terminal`). Components use only these tokens (`text-success`, `bg-chart-3`, `text-diff-add`); no palette classes or hex. The single exception: the dialog backdrop `bg-black/10`. The title bar's close button uses the `window-close` token: the platform's red (`#c42b1c`, white × on it 5.66:1; in high-contrast dark, 3.6:1 against the black title bar), and in high-contrast light `#a31d16` (× 7.65:1, 7.0:1 against the title bar). The title bar and navigation are `sidebar`, the content surface is `background` + `border`; in OLED and high-contrast dark both are black, so the content surface is separated by its border alone.
* **Type scale:** The root font is 13 px, so Tailwind's `rem`-based sizes would shrink (`text-xs` 9.75 px). In `app.css` `@theme` the scale is fixed in pixels: `text-xs` 12 / `sm` 13 / `base` 14 / `lg` 16 / `xl` 18 / `2xl` 22 / `3xl` 28 px (with line heights). Arbitrary `text-[Npx]` is not used; the smallest text is 12 px. Spacing stays `rem`-based (a dense desktop layout).
* **Selection:** `#lib/theme.ts` writes `data-theme` (dark, light, oled, night, hc-dark, hc-light; "system" in its resolved form), `data-scheme` (dark/light; the Tailwind `dark:` variant, toasts) and `data-cvd="on"` to `<html>`. ## 13. Target Architecture: One Core, Four Surfaces

The goal is for the GUI, CLI, Native API and MCP to use **the same Rust services**. A feature is written once, in `harness-core`; the surfaces are only thin adapters. Plan and priorities: [ROADMAP](ROADMAP.md); comparison: [FEATURES.md](FEATURES.md).

            └──────┬───────┘ └──────┬───────┘ └─────────┬─────────┘ └──────┬───────┘
                   └────────────────┴───────────┬───────┴──────────────────┘
                                                 v

### 13.1. Crate Structure
- Crates at the workspace root:
  - `crates/harness-core`: no dependency on Tauri or an HTTP server. With the `openapi` feature enabled, the types the API exposes derive `utoipa::ToSchema`.
  - `harness_core::tools`: the tool engine. `ToolRegistry` (registration + guarded execution: schema check, timeout, 16,000-character result limit, cancellation), `ToolPolicy` / `decide` (permission class × policy -> run / ask / deny), `Workspace` (locks file tools to a single directory tree, including symlinks), `builtin` (llama-server's seven tools, with schemas taken from a real `GET /tools` response), `ToolService` (policy -> working directory -> run -> `tool_calls` log in `analytics.db`). The Control API (`/tools`), the CLI (`harness tools`) and the Playground's `tools_*` Tauri commands only call this service; running calls are cancelled by `RunTable` with the id the client chose, limits are exposed via `ToolLimits`, and `tools::agent` is the seed of the core loop. Details: [SECURITY_MODEL.md](SECURITY_MODEL.md#tool-engine-harness_coretools).
  - `crates/harness-api`: the Control API. axum + tower-http + utoipa; handlers only call core services. Both the GUI and `harness serve` use this crate.
  - `src-tauri`: the GUI shell. `#[tauri::command]` wrappers, tray, updater.
  - `crates/harness-cli`: the `harness` binary (clap); `serve`, user commands, service installation, `mcp` (stdio). Reference: [CLI.md](CLI.md).
    - **Packaging:** The CLI ships as a Tauri sidecar (`bundle.externalBin: ["binaries/harness", "binaries/harness-hidden", "binaries/harness-onnx"]`; the third is the ONNX embedding/reranking server, see 14.4; the second is the console-less launcher for the service task on Windows and a plain relay on other systems; per the Tauri 2 documentation (v2.tauri.app/develop/sidecar), the file must be found as `binaries/harness-<target-triple>[.exe]`; when packaging, the triple is stripped and the binary is placed next to the application). Because `tauri_build` requires this file on every cargo build, `src-tauri/build.rs` produces it: `cargo build -p harness-cli -p harness-onnx --target <triple> [--release]` in a separate target directory (`target/sidecar-build`; the main directory's lock is held by the outer cargo), and it copies to `src-tauri/binaries/` only if the content changed. `cargo build`, `tauri dev` and `tauri build` (including release.yml; the signing and updater flow are unchanged, and on macOS Tauri signs the sidecar too) use the same path; it is rebuilt when CLI/core sources change. Locating it and adding it to PATH: `harness_core::integrations::cli_install` (see CLI.md).
  - `crates/harness-mcp`: the MCP server (protocol, tool catalog, stdio loop). It does not depend on axum or the CLI. Tools call the Control API through a `Backend` trait: an HTTP client in the CLI, an in-process call to the router in `harness-api` (`POST /mcp`). Reference: [MCP.md](MCP.md).
- Audit finding: most of the services are already plain Rust without Tauri.
  - Those tied to Tauri: `commands/*`, `lib.rs`, `desktop.rs`, `app_update.rs` and a single `emit` in `runtime_update.rs`.
  - The move is mostly a matter of moving files; no rewrite is needed.
- Global state (`config::CACHE`, the hardware cache, `paths::DATA_ROOT`) is gathered into a `Core` context struct. Tests can open independent instances.
- **Single-owner rule** (`harness_core::instance`, implemented): the data directory is managed by one process at a time (the GUI or `harness serve`).
  - An operating-system file lock on `instance.lock` (`std::fs::File::try_lock`: `LockFileEx` on Windows, `flock` on Unix). When the process crashes, the operating system releases the lock.
  - The owning process writes the pid, start time, kind (`gui` / `headless`), version, Control API address and the path of the session token file to `instance.json`. When the API closes, the address and path are deleted; on a clean exit the file is removed.
  - A leftover `instance.json` while the lock is free is considered stale (`probe` -> `Stale`) and the new owner overwrites it. `probe` tries the lock in shared mode and releases it immediately.
  - The GUI takes the lock at startup. If there is another owner, the GUI opens as before, writes to the log, does not run the Control API, and shows the owner's pid under Settings > Developer > Control API.
  - CLI discovery (implemented): every command talks to a Control API, so the `--json` schema is the same on every path.
    - `--host` / `HARNESS_HOST`: a remote API, with a named token.
    - Live owner and the API is on: the address in `instance.json` and the session token file.
    - Live owner, API off: exit 4 (`cli.owner_without_api`); the CLI does not write to another process's data directory.
    - No owner or stale: for the duration of the command, a temporary in-process owner (lock + the same API, random loopback port). When done it stops its servers and releases the lock and `instance.json`. Commands that start llama-server do this only with `--headless`.
    - `status` and `doctor` do not take the lock and do not write (the capability probe is not cached to disk).
  - `harness serve` is the headless owner: it does the same things as GUI startup, with the API always on. `POST /shutdown` (admin) works only on a headless owner (`ApiServer::set_shutdown_hook`); the GUI returns 409.

- **Error keys** (`harness_core::error_key`): the core and Tauri commands keep returning `Result<_, String>`, but the string is a key, not a sentence: `key`, the legacy `key: detail`, or `key {"name": "value"}` (`err("fs.read_failed").with("path", p).with("error", e)`). Technical details such as a path, an operating system error message, a URL or an id are untranslated parameters; a parameter can be a nested keyed error.
  - GUI: all commands take `invoke` from `#lib/ipc` (Tauri's `__TAURI_INTERNALS__` object is read-only and cannot be patched globally); in this wrapper a rejected command throws `BackendError`, and `message`/`toString()` is the translation in the current language (components that display `String(e)` get the translated text unchanged). Code that branches on the key uses `errorCode(e)` / `rawError(e)`; error texts in event and state fields are translated with `localizeError`. The texts are in `src/lib/locales/errors*.ts` (general `fs.*`, `json.*`, `http.*`, `task.*`, `db.*` + per-area files).
  - Control API: `{code, message_key, params}`; the HTTP status is `error_key::http_status` (`*.not_found` -> 404, conflicts 409, `network.*`/`api.*` 400, others 422). The CLI uses the same mapping and the same English texts (see CLI.md).

### 13.2. Runtime Capability Registry
Implementation: `crates/harness-core/src/capabilities/` (`parse`, `features`, `verify`) and `params.rs` + `params.toml`.
- Key per binary: `(path, mtime, size)`; `build`, `commit` and version are also written to the record. It is held in memory and in `config/runtime_capabilities.json` (`schema_version`, the newest 6 binaries); it is reread when the binary changes, and a failed read is not written to disk. The legacy `ServerCaps` is derived from this record. The outputs that are parsed (stdout + stderr together, without opening a window, with a timeout):
  - `--version`: `version: X (build N, commit H)` and the legacy `version: N (hash)`.
  - `--help`: the header line in column 0 (all spellings, `--no-*` negations, value hint), indented continuation lines, `(env: …)`, `default:`, allowed values (`[a|b]`, `{a,b}`, "allowed values:", `- name:` lists), section, `DEPRECATED`, "argument has been removed". Removed flags do not count as "present".
  - `--list-devices`: `Vulkan0: <name> (<total> MiB, <free> MiB free)`.
- The **parameter catalog** (`params.toml`, `include_str!`, parsed once) is the common source for the UI and `build_args`. Each entry:
  - `id`
  - `flags` (in order of preference, legacy names last), `off_flags`
  - `kind`: bool, int, float, enum, multi_enum, string, path, list, json; `values` / `values_from_help`
  - `group`, `level`: basic or advanced
  - `label_key`, `help_key`, `feature`, `requires` (`mode:router`, `legacy:<field>`), `conflicts`, `deprecated_by`, `min`/`max`, `loopback_only`, `value_fallbacks` (e.g. `load_mode` -> the legacy `--no-mmap`/`--mlock`)
  - `legacy_field`: only defines the typed `LaunchConfig` field (UI hiding, flag explorer); the argument is produced by typed code and its output is pinned by golden tests.
- Values are held in the general `ParamValues` (`BTreeMap<id, ParamValue>`) in `LaunchConfig.params` and `ModelPreset.params` (not written if empty). The `load` field of ModelDefinition uses the same type. `render_params` picks the first spelling the binary accepts; it does not send a parameter that is not in the catalog or not found in the runtime, and logs it. An invalid value, a conflict and a protected flag (`params::PROTECTED_FLAGS`: host, port, API key, tools, MCP, agent) are errors.
- **Capability levels** are kept separate. A flag appearing in `--help` does not mean the feature is usable.
  - `FlagDetected`: the flag or endpoint name exists in the binary.
  - `EndpointVerified`: verified in a real run. Sources: a `/props` field, a `/metrics` metric name, inference-free route checks (count_tokens, apply-template, `/v1/responses`), the effective value in the log. A real `/v1/embeddings` on a server started in embedding mode and a real `/rerank` smoke request in rerank mode (`embeddings_endpoint`, `rerank_endpoint`). Cached by binary key. Real `/v1/messages` and `/rerank` requests are in `#[ignore]` smoke tests (`serve_mode::e2e`); the probe stays inference-free.
  - `ModelDependent`: features that depend on the model. Sources: GGUF and `/props` (`modalities`, `chat_template_caps`, pooling, `expert_count`, SWA). Examples: vision, tool calling, reasoning, embedding/rerank, MoE.
  - `PlatformDependent`: depends on the backend or device. Examples: FA, `split-mode tensor`, `--load-mode dio`, CUDA-specific options, `--list-devices`.
  - The UI and API return the level and the reason for each feature. Example: "available in the runtime, not in this model".
- If the flag is not in the binary, the parameter is neither shown nor sent. Aliases and a migration mapping are kept for removed flags.
- Unknown new flags are listed raw in the "All flags" explorer. They can be used without updating the catalog.
- After launch (the first `/health` ok), **effective values** are read from `/props` and the log: requested/actual `n_ctx` (per slot), slot count, unified KV, training context, build; for ngl, from `offloaded N/M` in the log if present (only at `-lv 4`), otherwise by llama.cpp's rule `min(-ngl, block_count + 1)` (0 if the runtime has no GPU device; `gpu_layers_source`). In the same round, inference-free endpoint checks are made: GET `/props`, `/metrics` (metric names), `/slots`, `/v1/models`, `/lora-adapters`; POST `/v1/messages/count_tokens`, `/apply-template`; an empty-body POST to `/v1/responses` (400 = the route exists). 401/403, network errors and 5xx (except 501) do not count as results. In router mode, only `/metrics` is checked.
- **`--props` is not added:** this flag only enables changing global settings with POST `/props`; GET `/props` works without it (verified on b11236 with `endpoint_props: false`). In the catalog, `props` is an advanced, `loopback_only` parameter.
- **Multiple binaries:** because the key is the binary, the capabilities of each registered runtime (§13.8, `runtimes/`) are kept separately. `server_binary_for(registry, mgr, server_id, runtime)` returns the binary of the runtime the server chose; parameter hiding on the Dashboard, "All flags" and the feature status (the `runtime_id` parameter) are computed for the selected runtime. The same registry produces a "parameters in the catalog that are not supported" summary per runtime.
- **Quant type support** (`runtimes/quant.rs`): the `ggml_type` numbers in the GGUF tensor table are read (`GgufMetadata.tensor_types`). The types a build can load are derived from the `llama-quantize --help` list in the same folder (cached by binary key); if it is missing, `Unknown`. Official table: `GGML_TYPE_COUNT` 43 (including Q1_0=41, Q2_0=42); only in a fork: PrismML `PQ2_0`=142, `PTQ1_0`=143. `Unsupported` blocks launching, `Unknown` does not.
- Feature status `features::feature_status(caps, model?)`: `Unsupported`, `Unknown` (known only via an endpoint, not yet checked), `FlagDetected`, `EndpointVerified`, `ModelDependent` (GGUF + an earlier `/props` observation), `PlatformDependent` (backend/device count). The reason is a `caps.reason.*` i18n key + parameters.

### 13.3. Domain Models: Four Separate Concepts
To avoid stuffing everything into one structure and then having to separate it, the concepts are kept apart from the start:

| Concept | What | Where it is stored | Key fields |
|---|---|---|---|
| **LocalModel** | The physical artifact on disk (GGUF, shard set, mmproj, LoRA) | Not stored; derived by scanning. User state (favorite, last use) is in `state.db` | `id` (canonical path), `kind`, `shards`, `size`, GGUF summary, `source` (library/linked) |
| **ModelDefinition** | A logical model; a different alias, adapter, template and load defaults on the same base | `model_definitions.json` | `id`, `alias` (the API `model` name, unique), `base` (LocalModel path or `hf:repo:file`), `mmproj`, `adapters[]`, `draft`, `chat_template`, `load{}`, `default_preset`, `ttl`, `pinned` |
| **ServerProfile** | How a ModelDefinition is served | `server_profiles.json` | `id`, `name`, `purpose`, `definition_id`, `host`, `port`, `auto_start`, `api_key_ref`, `serve_overrides{}` |
| **InferencePreset** | Request-side settings | `inference_presets.json` | `id`, `name`, `builtin`, `system_prompt`, `sampling{}`, `reasoning`, `stop[]`, `response_format` |

- The same GGUF can be used in several ModelDefinitions. The gateway and API resolve the `model` field to an alias.
- Implementation: `crates/harness-core/src/domain/` (`mod.rs` types and alias rules, `launch.rs` layering, `presets.rs`, `store.rs` persistence + compatibility layer + migration).
  - `LocalModel` = `models::LocalModel`; `kind` comes from the GGUF header: `general.type` (`model`/`mmproj`/`adapter`), `clip.*`, `<arch>.pooling_type` (1-3 embedding, 4 rank), `classifier.output_labels`, classification head tensors (`cls.weight` / `cls.output.weight`; bge-reranker-v2-m3 is distinguished by this alone). "Draft" is not a file type but a usage (`ModelDefinition.draft`). `origin`: library/linked.
  - Serve mode (`serve_mode.rs`): `serve_mode` (`chat`/`embedding`/`rerank`, automatic if absent) is a Harness-level `ParamValues` key outside the catalog (like `custom_args`); it is carried in the definition/profile layers, and inside `ProcessManager::start`, `serve_mode::prepare` turns it into `embeddings`/`rerank` values and removes it from the arguments. The stored launch setting preserves the user's choice; the effective mode is in `ActiveServerInfo.serve_mode`.
  - Alias `[A-Za-z0-9._:-]{1,128}`, unique case-insensitively.
  - `load` and `serve_overrides` are the same `ParamValues` type; the typed `LaunchConfig` fields are carried with catalog ids (`gpu_layers`, `mmproj_path`...), and the two keys with no flag in the catalog are `custom_args` and `lora_scale`. In a layer, an empty string means "remove the setting". The catalog groups `server`/`router` live only in the profile.
  - `model_definitions.json` also holds `model_defaults{file: {definition_id, api_key_ref, serve_overrides}}`: the Dashboard's per-model setting (formerly `presets.json`). In `server_profiles.json`, `id = "default"` is the Dashboard's last session (pinned by the snapshot layer).
- The effective load setting is merged in this order: defaults (ngl, ctx, host, port from settings; the rest is llama-server's own default) <- ModelDefinition `load` <- ServerProfile `serve_overrides` <- launch-time temporary changes (`resolve_launch`).
- Migration of existing files (on first access, once):
  - `presets.json`: each model becomes a ModelDefinition (alias = file name, invalid characters `-`, `-2` on a clash).
  - `profiles.json`: if the model setting is the same as the Dashboard definition, that definition is shared; otherwise a `<file>-<profile name>` definition is created; the ServerProfile points to the definition.
  - `last_session.json`: the `"default"` profile.
  - Old files are preserved as a `.pre-v2` backup; keychain accounts do not change (`preset:<hash>`, `profile:<id>`, `session`).
  - The compatibility layer produces the old command shapes (`list_server_profiles`, `get_model_preset`...) from this structure. If a shared definition is changed from the Dashboard, the profiles using it move to a copy (profile behavior does not change).
- Portable format `*.harness.toml` (`harness.model.v1`, `domain/portable.rs`): `[model]` alias/description/base, file paths relative to the models folder (with `/`) or `hf:owner/repo:file`; `[load]` catalog values; optional `[preset]`. Import previews first (`DefinitionImport`: was the file found, what is missing, alias clash, suggested alias).
- Launch flow:
  - The definition's alias goes as `--alias` via `LaunchConfig.alias`; `definition_id` carries the launched definition (the model picker status `domain/status.rs` reads this).
  - The Dashboard form is a temporary layer: `resolve_form` = defaults <- definition `load` <- (the profile serving the same definition) `serve_overrides` <- `diff_layer(definition, form)`. Start does not save; `save_form` writes the difference to the definition (default) or to a new definition.
  - `ModelDefinition.auto_created`: definitions from migration and profile copies; when the owning profile is deleted and no reference remains, it is deleted (`drop_orphan_auto`). A user save removes this flag.
  - The served model name (`--alias`) is unique among running servers (the gateway and clients choose a server with it). Profiles can share a definition ("New Server" shares the selected server's definition and does not create a separate one); an instance started while a server serving the same name is running gets a separate name for that run (`orchestrator::distinct_served_alias`, inside `launch_with_binary`): `<alias>-<profile>` if the profile name says more than the model (the `profile_alias_base` rule), otherwise (the `<model> :<port>` automatic name, Dashboard, `m-<alias>`) `<alias>-<port>`; if that is taken too, `-2`, `-3`... The definition does not change and `definition_id` is preserved: the gateway routes the definition's alias to both servers, and `external_models` counts both as defined. A user `--alias` in custom arguments is not renamed; if it clashes, launching is rejected with `servers.alias_in_use`. `process::served_alias` takes a custom `--alias` into account.
  - `model_definitions.json` v2 (`definitions_v1_to_v2`): aliases of the form `<stem>-<model>-:<port>` (optionally `-<n>`) produced by the old "New Server" code are converted to the clean base (`<stem>`, `-2` if taken) with `profile_alias_base`. Applied only to local definitions and exactly in this form (stem from the file name, case-exact); other aliases do not change. The framework keeps the v1 file as `model_definitions.json.bak-v1`.
  - Definition loading is `orchestrator::plan_load_definition` + `run_load_plan`: the target is an existing instance, a new instance (`m-<alias>`, free port), or the profile serving the definition. A launch that hits the network rule is stored as `PendingStart` and repeated through the same path (`launch_form`) after "Open anyway".
  - The preset format is `harness.preset.v1` (`presets.rs`: `export_presets`, `parse_presets`); on import the ids are regenerated, validation is `InferencePreset::validate`.
- My Library capabilities (`library::caps_of` + `apply_observations`): tools and reasoning are first inferred from the template text; once the model has been loaded, the `/props` observation in the registry (`CapabilityRegistry::observation_for`, the newest of all remembered binaries) makes tool support definite and upgrades reasoning (`supports_reasoning_effort` or `supports_preserve_reasoning`); `LibraryEntry.caps.verified = {tools, reasoning, observed_at}`. `/props` saying "no" does not take reasoning back (templates that drop it from history also say no); only `verified.reasoning = false` remains, and the UI says "in the template, the server did not report it".
- Split model repair (`library::ops::repair`, `library::sources`): the downloader writes the URL of every file it finishes to `model_sources.json` (query/fragment/credentials are dropped; on a move, the record goes with the file). Repair source order: a file downloaded from a custom URL (the recorded URL), the `<library>/<owner>/<repo>/` layout (the HF file list), the record of an HF file that is out of the folder layout. In repair from a URL, the missing shard's URL is derived by changing only the `-0000N-of-0000M` number in the existing shard's URL (the name root and shard count must be the same), every URL goes through the same SSRF check as a custom-URL download, and files land in the model's own folder. For a file with no record (copied by hand), the reason is explained and the user can repair it by entering the URL of one shard (`repair_model_shards(modelId, url)`).
- The Ollama Modelfile converter (`modelfile.rs`) maps onto this structure; since the result is a `DefinitionImport`, it is saved with `Domain::import_definition`:
  - `FROM` -> `base` (a GGUF path or Ollama `manifests`->`blobs`, read-only; projector -> `mmproj`)
  - `PARAMETER` -> `InferencePreset.sampling` (sampling, `stop`, `num_predict`->`max_tokens`) / `load` (`num_ctx`->`context_size`, `num_gpu`, `num_thread`, `num_batch`, `main_gpu`); unrecognized -> warning
  - `SYSTEM` -> preset system prompt
  - `MESSAGE <role> <text>` (and the stored messages of an installed Ollama model) -> appended to the end of the same system prompt as an "Example conversation" section (`User: …` / `Assistant: …`). `InferencePreset` has no turn list; every consumer that applies the system prompt (Playground, gateway) carries the examples automatically, but these are examples inside the system message, not real history turns (the `messages_as_examples` warning in the preview says so). Multi-line `MESSAGE user """..."""` is supported; an unknown role or empty text is an `invalid_value` warning.
  - `ADAPTER` -> `adapters`
  - `TEMPLATE` -> warning; the Jinja template in the GGUF is used
- Inference preset: `system_prompt`, sampling parameters, `stop`, `reasoning`, a `response_format` template. Built-in presets are read-only; they can be copied and edited.

### 13.4. Gateway and Scheduler
- A streaming reverse proxy with `axum` + `reqwest`. The body is parsed only to read the `model` field and for compatibility conversion; the SSE response is relayed chunk by chunk, without copying.
- **Managed and direct endpoints:**
  - While the gateway is on, Harness's own clients use the managed endpoint by default: the Playground, integrations, `harness launch`, and the endpoint given via MCP.
  - Direct llama-server ports are for advanced use; for traffic arriving this way, only `/metrics` totals are visible.
- **Responses/Codex compatibility:** unsupported tool types are not dropped silently.
  - Those that can be translated while preserving meaning are translated (e.g. `namespace` -> prefixed functions, mapped back in the response).
  - Those that cannot get an explicit `400 unsupported_tool_type` error.
  - Ignoring is done only with an explicit per-definition setting; when done, it is flagged in the response header (`X-Harness-Compat`) and in the log.
- **Stateful Responses (`harness-gateway::responses`, `harness_core::gateway::responses`):** llama-server's `/v1/responses` is stateless; state lives in the gateway.
  - Request: `store` (default `true`; not stored if `settings.gateway.responses.store` is off) and `previous_response_id` are taken out of the body. The previous id is followed backwards within the caller's scope (`token:<id>` / `harness` / `anonymous`) with `StateDb::response_chain`; the links' input items and the response `output` items are prepended to the new `input` in order (`chain_context`). `instructions` is not carried over; if `model` is absent, the last link's alias. A missing link gives `404 previous_response_not_found`. This step runs after rate-limit admission and before model resolution; `compat::prepare` (namespace flattening) is applied to the combined input, so namespaced calls in the history are translated too.
  - Response: for non-streaming, the JSON is buffered, `previous_response_id`/`store`/`instructions` are added, and if `store` is on it is saved before being sent to the client. For streaming, the Response object of every lifecycle event is decorated with the same fields; `SseScan` finds the last event (`completed`/`incomplete`/`failed`/`cancelled`), the response is saved on the blocking thread, and only then is the event sent.
  - **`background: true`:** If `proxy::handle` sees `background` in the body (`responses::start_background`), it stores a `queued` placeholder with a pre-generated `resp_<uuid>` and runs the request in a tokio task through the normal path. With `stream: false` the placeholder is returned to the client as JSON. With `stream: true`, the task consumes the upstream SSE body to the end independently of the client; it writes events to the state.db v7 `gateway_response_events` table with an increasing `sequence_number` assigned by the gateway. The POST stream and `GET /v1/responses/{id}?stream=true&starting_after=N` read the same persistent log and wait for new events while the task is running; a client disconnect does not stop generation. Re-streaming is available only for responses whose first request was background+stream. Event ownership is checked by a join on the parent `gateway_responses.scope` row, and events are deleted by cascade when the response is deleted. The task registry is `(scope, id) -> AbortHandle`; cancellation writes the terminal response and the `response.cancelled` event. `store: false` together with background is 400 because of the existing local-storage requirement; on restart, a half-finished response becomes `failed` / `interrupted`.
  - **`include`:** the official values are validated as array/type; any value with no local equivalent gets `400 unsupported_value` instead of a silent compatibility loss. Although llama-server supports token probability generation on other endpoints, the current Responses converter builds `output_text.logprobs` as a fixed empty array, so `message.output_text.logprobs` is explicitly rejected too. Web/file/code-interpreter/computer tool data and encrypted reasoning are also not produced locally.
  - `GET /v1/responses/{id}`, `DELETE /v1/responses/{id}`, `POST /v1/responses/{id}/cancel`, `GET /v1/responses/{id}/input_items` (OpenAI pagination: `after`, `before`, `limit`, `order`); endpoint group `chat` (token policy). The stored input is the request's own `input` (a string -> a single `input_text` user message), and items without ids get stable ids.
- Scheduler states:
  - Per definition: `unloaded -> loading -> ready -> draining -> unloaded`.
  - Shared: the `max_loaded` limit and the memory budget.
- Steps of the load decision:
  - Estimate first.
  - If it does not fit, the least recently used idle definition (one with no active request) is evicted. Pinned definitions are not evicted.
  - If it still does not fit, `503 insufficient_memory` is returned, with a list of suggestions.
- The queue is per definition. If the depth limit is exceeded, 503 and `Retry-After`. If the client connection drops, the llama-server request is cancelled too.
- **OOM recovery hook:** when the gateway gets `servers.out_of_memory` on a load, it obtains the plan with `orchestrator::recovery_plan`. It first evicts the oldest idle definition and retries once with `retry_with_overrides` (`gateway_model` event, `action: oom_retry`); if that fails, it returns `503 insufficient_memory` with the plan's options.
- **Implementation:**
  - Layers: `harness_core::gateway` (settings, `validate_settings`, `EndpointKind`/`ClientEndpoint`, the in-process state record `status()`, the client token file, `RequestRecord` + `UsageObserver`) and `harness_core::gateway::scheduler` (no HTTP). The HTTP side is `crates/harness-gateway`: `GatewayServer::start/stop`, `router`, `proxy`, `compat`, `auth`, `errors`. No separate process; the GUI (`src-tauri`, in the owning instance) or `harness serve` starts it. Limit changes are applied without a restart; when the address/port/CORS changes, the listener is rebuilt.
  - Resolution: `model` -> definition alias (or id). If a running server already serves the definition (`domain::status::definition_states`), the request goes to it; otherwise JIT: `plan_load_definition(NewServer)`, host `127.0.0.1`, automatic port (`port_auto`, range 11440-11499; see §8 Automatic port), server id `gw-<alias>` (an alias longer than 48 characters is cut and ends with 8 hex digits of its SHA-256, so aliases that only differ after the cut do not share a server), `run_load_plan`.
  - Concurrency: a `Semaphore` per definition, sized by llama-server `/props` `total_slots` (gateway loads use the agent rule, §5.4d; on a reload with fewer slots the excess permits are taken back, and `waited` counts requests that arrive while all slots are full). If the number of waiters exceeds `max_queue`, `503 queue_full` + `Retry-After` (from the average request duration). The lease (`Lease`) is held until the stream ends or the client disconnects; when dropped, `last_used` is updated.
  - Making room: `max_loaded_models` counts only the servers the gateway loaded (`gw-`). Memory: the `vram::fit_with` estimate is compared with the free memory from `devices::report` and the `memory_headroom_mib` margin; the memory that will be freed on eviction is measured from the process VRAM (`gpu::process_vram_bytes`). The victim: the oldest idle, unpinned model loaded by the gateway.
  - Co-residency pre-check (split view): `Scheduler::co_residency(models)` applies the same limits to all of them at once, without loading anything. `max_loaded_models`: if the models in question (loaded or to be loaded) + other busy/pinned gateway models exceed the limit, `max_loaded_models`. Memory: for each model to be loaded, a `plan` + `memory_picture` estimate and the margin; the footprint of other idle, unpinned gateway models is added to the free VRAM; if exceeded, `insufficient_memory`. For a single model it returns the `/props` slot count. Tauri `gateway_co_residency`; the Playground asks this first, and if `503 max_loaded_models`/`insufficient_memory` still comes, it repeats that side when the other one finishes.
  - Maintenance loop (1 s): idle models whose TTL has expired are unloaded (`unloaded_ttl`). At startup, pinned definitions are warmed up.
  - Events: `gateway_request` (a record per request; persisted in `analytics.db`, §13.5) and `gateway_model` (`loaded`, `unloaded_ttl`, `evicted`, `unloaded`, `load_failed`, `oom_retry`); `analytics_written` (`count`): records were written to `analytics.db` (~1.2 s after `gateway_request`, `ENRICH_DELAY`); views that read the request log refresh with it. `last_session_saved` (`server_id`): the Dashboard server's launch was saved as the last session after reaching Running; the UI rereads the saved launch with `last-session-changed`.
  - Response headers: `x-harness-request-id`, `-model`, `-server`, `-queue-ms`, `-load-ms`, `-evicted`, `-compat`; `x-harness-error` on errors.
  - Authentication: Bearer or `x-api-key`. Accepted: the gateway client token (`hsg_`, refreshed on every start, `<data>/gateway-token`) or a named token with `inference`/`admin` scope. On an open loopback gateway with no token, the clients' placeholder keys are ignored. `Host` check on loopback.
  - Management: Control API `GET /gateway` (status, settings, model slots), `gateway` inside `/status`; Tauri `get_gateway_status` (including the count/size of stored Responses), `set_gateway_settings`, `unload_gateway_model`, `clear_gateway_responses`.
- llama-server's router mode remains as an alternative backend for users who want "multiple models in one process". But memory-aware eviction and per-request logging are done with the Harness scheduler; the router applies only count-based LRU.
- **Ollama translation layer (`crates/harness-gateway/src/ollama/`):** Ollama's native API on the same port (and optionally on the Ollama port). Since Ollama also runs `llama-server` as a child process for GGUF, the fields map directly. Formats follow the official reference: [ollama/docs/api.md](https://github.com/ollama/ollama/blob/main/docs/api.md), [docs.ollama.com/api](https://docs.ollama.com/api) (errors: [docs.ollama.com/api/errors](https://docs.ollama.com/api/errors)); field names and `keep_alive` parsing are from `api/types.go`; verified against the real `ollama` 0.34.4 CLI.
  - Layers: `ollama::convert` (pure translation: request, response, SSE -> NDJSON stream translator, `keep_alive`, names, time), `ollama::info` (GGUF header: `details`, `model_info`, template, capabilities; file + mtime cache), `ollama` (routes, scheduler lease, llama-server request, record). Every inference request goes through the same path as `/v1/*`: `auth::check`, `Scheduler::resolve/acquire`, `RecordGuard` (request record, content record), `UsageObserver`; in the record, `endpoint` is `/api/chat`, etc.

  - **Ollama port:** `GatewaySettings.ollama_port_enabled` (off by default), `ollama_port` (default 11434; >= 1024, different from the gateway and Control API ports, otherwise `gateway.ollama_port_conflict`). On startup, `http://<host>:<port>/api/version` is probed first: if it returns `version` without the Harness marker, it is a real Ollama (`gateway.ollama_port_ollama`); if it returns with the marker, it is another Harness gateway (`gateway.ollama_port_harness`); a connection error or any other response means the port is in use (`gateway.ollama_port_busy`). If nobody answers the probe, the process holding the port is looked up: if its name starts with `ollama`, again `gateway.ollama_port_ollama`; if it is some other program, `gateway.ollama_port_busy` (the program name is in the warning). If Ollama is installed (on PATH or in the default install location, `ports::ollama_installed`) but not running, 11434 is not taken either (`gateway.ollama_port_installed`): otherwise Ollama could not be started later. In no case is the port taken by force, and the gateway keeps running on its own port; the warning is in `GatewayStatus.ollama_warning` (Settings, Connections, `harness serve`). If it binds, the same router runs on a second listener (`ollama_port`), and it closes when the gateway stops.
- **Clients of the managed endpoint:** `harness launch` and the GUI "Launch" tool start with the gateway client token and the alias (if the model is not loaded, a one-token warm-up request triggers the JIT load); the MCP `get_endpoint` returns `kind: managed` while the gateway is on; the Playground model list is the gateway's `/v1/models` list (`harness.state`). The launch plan (`harness_core::integrations::launch`) is pure data: arguments, environment, environment variables to remove, temporary files; the CLI and Tauri run the same plan. Persistent integrations are written key by key via `integrations::keyed` and reverted with a ledger (`config/integrations.json`). OpenCode desktop detection/opening is in `integrations::opencode_desktop`; the agent tools' model list, the tool-call decision (a real trial `config/tool_checks.json` -> local tool-call responses in analytics -> the GGUF template) and prompt speed are in `integrations::agent_models` (analytics: `AnalyticsDb::agent_signals`). Details: [INTEGRATIONS.md](INTEGRATIONS.md).

### 13.5. Observability and Analytics
- The live layer stays as is: `/metrics` + `/slots` (1 Hz while a request is in flight or the window is open, 5 s when idle; see section 6), with an in-memory history of 600 samples.
- The request log is kept for requests that pass through the gateway. Requests arriving directly at a port are not seen one by one; only the token total derived from the server's total counters is kept, as "Direct" (below).
  - Sources: `timings` and `usage` in the llama-server response (`prompt_n`, `cache_n`, `predicted_n`, `*_ms`, speculative `draft_n`), the queue wait and total duration measured by the gateway, and the VRAM sample at that moment.
- Storage is `analytics.db` (SQLite, WAL):
  - `requests` table: raw rows, 30 days.
  - `daily_rollup` table: permanent.
  - Percentiles are computed at query time.
  - This is a deliberate exception to the earlier "no database" principle: JSON files are inadequate for percentile and periodic queries.
- Content logging is off by default. If enabled, it is per definition, time-limited and passed through the sanitizing rules.
- Export: a combined Prometheus `/metrics` (gateway + all servers + scheduler) and optional OTLP (below).
- **Implementation, `harness_core::analytics`:**
  - Recording path: when a request finishes (or the client disconnects), the proxy's `RecordGuard` calls `analytics::submit(record, content)`. `submit` updates the Prometheus counters and puts the record into a bounded queue (`QUEUE_CAPACITY` 4096, `std::sync::mpsc::sync_channel`) with `try_send`; it never waits and never touches the disk. If the queue is full, the record is dropped and counted (`RecorderStatus.dropped`, `harness_analytics_records_dropped_total`). The record sent on the event path (`gateway_request`) carries no content; content goes only through this queue.
  - Writer: a separate thread (`harness-analytics`; independent of the tokio runtime, the same in tests and the GUI). Records are held for `ENRICH_DELAY` (1.2 s), then written in batches of at most 512 in a single transaction. The wait is so that the telemetry sample taken after the request ends also falls inside the window. `flush()` writes pending records immediately (on shutdown and in tests).
  - Enrichment: from the telemetry history supplied with `set_telemetry(poller)` (1 Hz while the request runs; the sampler takes a sample immediately when a gateway request ends), the peak VRAM and RAM (whole GPU/system; not per process) within the `[start, end]` seconds of the request's server. If there is no sample in the window, the sample closest to the end, at most 2 s away. The GUI and `harness serve` supply the poller.
  - Added to the lease: `ctx_size` (llama-server `/props` `default_generation_settings.n_ctx`, the per-slot context) and `backend` (from the `ggml-*` libraries in the server's binary folder). `RequestRecord` gained the `oom`, `ctx_size` and `backend` fields. OOM: `insufficient_memory`, `servers.out_of_memory` on load, or a successful retry after OOM.
  - If the client closes the connection before the stream ends (e.g. a client that reads the `[DONE]` line and closes), the usage observed up to that point is recorded; if the finish reason has already been passed on, the request does not count as cancelled.
  - Calculations: error = an error code or a status of 400 and above other than 499 (a client cancellation is not an error). Mean speeds are token-weighted: sum(`predicted_per_second` x `predicted_ms`) / sum(`predicted_ms`) (the same for the prompt). P50/P95 are computed at query time from raw rows by linear interpolation (Hyndman-Fan type 7, the NumPy default; `analytics::stats::percentile`). Days whose raw rows have been deleted come from the daily rollups (counts, totals, means, peaks; no percentiles). A day is not counted in raw rows and rollups at the same time (`day NOT IN (SELECT day FROM requests)`).
  - Timeline (`stats::timeline`): load (inside the queue wait) -> remaining queue -> prompt (`prompt_ms`) -> generation (`predicted_ms`) -> other (the remainder of the total: proxy, network, sampling). The first-byte marker is `ttft_ms`.
  - Benchmark comparison: the best `pp` (prompt only) and `tg` (generation only) result of the most recent completed llama-bench run for the definition's local model file (path mapping via `library::state_key`).
  - **Direct (non-gateway) usage (`analytics::direct`):** A request going straight to a llama-server port does not pass through the gateway, but the server's `/metrics` counters (`prompt_tokens_total`, `tokens_predicted_total`) count all of them, including the gateway's requests. The telemetry sampler (`orchestrator::run_telemetry_sampler_watched`) calls `direct::observe` after every round. The calculation is per server and sampling interval: `direct = counter increase - the tokens the gateway recorded for that server`. The gateway side is accumulated in memory in `analytics::submit` (`note_gateway`; per server id, prompt - cache and generation tokens), not read from the database, so both sides are compared at the same moment. Unit: llama-server's `prompt_tokens_total` does not count tokens that came from the cache (real measurement: two identical chats, usage 41+41 prompt and 0+40 cache, counter 42), so the gateway side is `usage.prompt_tokens - cached_tokens`.
    * No guessing, no negatives: if the gateway recorded more than the server counted, the difference is zero, not negative direct usage. Because the server counter and the gateway record can increase at different moments (one a sample earlier), a difference counts only if it holds across two consecutive samples (`DirectTracker`: cumulative difference, the smaller of the last two samples, allowing a deficit of the gateway's tokens in that interval); so direct usage appears one sampling interval late, and when the server stops, the last pending difference is dropped. If the counters go backwards (the server restarted), a new baseline is taken.
    * Storage: `direct_usage(minute_ms, day, server_id, label, prompt_tokens, completion_tokens)` is a per-minute total (`label` is the model file name); minutes older than `raw_retention_days` are folded into `direct_daily` (day, server) in the maintenance round. `AnalyticsSummary.direct` carries the total for the range, the per-server breakdown and the daily series. In the UI there is a separate "Direct (outside gateway)" card on the overview, explicitly labeled as a total; `harness analytics` in the CLI adds a line. Servers started with `/metrics` disabled are not visible; nothing is written while the setting is off (`analytics.enabled`).
  - **Persistent rate-limit counters (`gateway::limits`, `analytics::counters`):** `RateLimiter::persistent(db)` keeps the same in-memory buckets and additionally writes to the `rate_counters(token_id, kind, level, capacity, at_ms, rev)` table in `analytics.db` (`kind` is `rpm`/`tpm`; concurrency is not written). There is no disk on the request path: the table is read once at startup; the `harness-limits` thread writes changed buckets in a single `IMMEDIATE` transaction every `FLUSH_EVERY` (2 s) and reads what other processes wrote; one last write is made when `Core` is dropped. The level in the row is the value at the wall-clock `at_ms`; on load it is refilled for the elapsed time at the rate `capacity/60` (full if the window has elapsed), and rows older than a day are deleted.
    * Across processes: the row's `rev` version increases on every write. If the process sees the version it last wrote/read, it writes its own level (no rounding loss in a single process). If someone else has written, the recorded level (refilled over time) is taken as the baseline, what this process has consumed since its last write (`pending`) is subtracted from it, and the result is written; a process with no pending consumption just adopts the baseline. This way Harness instances sharing the same data folder consume a single budget; they see the other's consumption with at most `FLUSH_EVERY` delay. If a write fails (e.g. a newer schema, read-only), the consumption stays in `pending` and is retried in the next round; if `analytics.db` cannot be opened at all, the limiter works in memory.
  - Surfaces: the Analytics screen (Overview: KPIs, daily bars, client distribution, model table, benchmark and real usage; Request inspector: a filtered list and a detail drawer), content logging in the Model Definition window. Control API `GET /analytics/summary?range=24h|7d|30d|90d|all` (or `from_ms`/`to_ms`), `GET /analytics/requests` (filters: `model`, `client`, `endpoint`, `status=ok|error|oom|cancelled`, `tool_issue`, `tool_category=runtime|context|model|client`, `from_ms`, `to_ms`, `before_ms`, `limit` at most 1000), `GET /analytics/requests/{id}`, `GET /metrics`; all `read`. CLI `harness analytics`, `harness requests [id]`. **Tool call diagnosis:** the gateway classifies every tool turn with `harness_core::gateway::tool_diag` (culprit server/template, context, model or client) and writes the result to the request row (`requests` columns `tool_*`, schema v5); rules, model level and recommended tool count: [TOOL-DIAGNOSIS.md](TOOL-DIAGNOSIS.md). Tauri: `get_analytics_summary`, `list_analytics_requests`, `get_analytics_request`, `get_analytics_info`, `set_analytics_settings`, `clear_analytics`.
- **Combined `/metrics` names** (gateway `GET /metrics`, Control API `GET /api/harness/v1/metrics`; text format 0.0.4). Counters are since this process started:
  - `harness_gateway_up` (gauge).
  - `harness_gateway_requests_total{model,endpoint,status}`, `harness_gateway_request_errors_total{model,code}`, `harness_gateway_requests_cancelled_total{model}`, `harness_gateway_oom_total{model}`, `harness_gateway_prompt_tokens_total{model}`, `harness_gateway_completion_tokens_total{model}`, `harness_gateway_cached_tokens_total{model}` (counter).
  - `harness_gateway_request_duration_seconds`, `harness_gateway_ttft_seconds`, `harness_gateway_queue_wait_seconds`, `harness_gateway_model_load_seconds` (histogram, `model` label; buckets 0.05 · 0.1 · 0.25 · 0.5 · 1 · 2.5 · 5 · 10 · 30 · 60 · 120 · 300 s).
  - `harness_gateway_model_loaded`, `harness_gateway_in_flight_requests`, `harness_gateway_queued_requests` (gauge, `model`; the definitions the scheduler knows).
  - `harness_analytics_records_written_total`, `harness_analytics_records_dropped_total`, `harness_analytics_write_errors_total`.
  - `harness_system_vram_used_bytes`, `harness_system_vram_total_bytes`, `harness_system_ram_used_bytes`, `harness_system_ram_total_bytes` (the last telemetry sample).
  - `llamacpp:<name>{server="<id>"}`: each llama-server's own `/metrics` values, from the telemetry's last sample (traffic arriving directly at a port is visible here too).

- **OTLP export (`harness_core::otel`, `otel` feature):**
  - Settings are `AppSettings.otel` (`enabled`, `endpoint`, `protocol` = `http_protobuf` | `grpc`, `service_name`, `traces`, `logs`, `metrics`, `metrics_interval_secs`, `include_content`, `header_names`); header values are in the keychain. `logs` is a separate opt-in and is off by default. `otel::apply` starts, rebuilds or stops the exporter (at GUI startup and on save, when `harness serve` starts); on shutdown, `otel::shutdown` sends what is pending.
  - Traces: the SDK's tracer is not used; in the same place as `analytics::submit` (`RecordGuard::finish`), `otel::record(record, content, trace_context)` is called and the `SpanData`s are built directly from the `RequestRecord` (start = end - `total_ms`). The root span is of kind `SERVER` (`chat <alias>`), and the child spans are `gateway.queue` (the wait other than loading), `gateway.load` (JIT load, evicted models), `llama-server.generate` (the `gen_ai.first_token` event, `prompt_ms`/`predicted_ms`). A valid W3C version 00 `traceparent` becomes the root span's trace id and remote parent; `tracestate` is preserved. An invalid/missing context creates a new root trace. Valid headers are also forwarded to llama-server in the existing upstream header forwarding. Its own batch export task: a bounded queue (4096; dropped and counted when full), batches of 512, 2 s delay.
  - Logs: for every finished request, a `gateway_request` record is sent from a separate bounded queue, with the content-free `RequestRecord` body given to Analytics and queryable basic attributes. `trace_id` and `span_id` are the same as the same request's server span. Content is added only if `include_content` and the model definition's content logging are both on, with the same 16 KB limit as spans.
  - Metrics: `SdkMeterProvider` + `PeriodicReader`, cumulative. The exporter runs on its own single-threaded tokio runtime (the SDK's reader thread is outside the runtime).
  - Transport: `opentelemetry-otlp` 0.33. OTLP/HTTP (protobuf; `/v1/traces`, `/v1/logs`, `/v1/metrics`) is sent with the workspace's reqwest 0.12: a small `opentelemetry_http::HttpClient` adaptation in `otel/export.rs` (`ReqwestHttp`; TLS from the operating system like the rest of the application, connection 5 s, request 10 s, response at most 4 MiB). There is no second reqwest (0.13). OTLP/gRPC (tonic, `tls-ring`, system roots) is compiled only with the `otel-grpc` feature; the default builds (GUI, `harness`) do not include it. Choosing gRPC in those builds is an `otel.grpc_not_built` error in `validate_settings` (save, test and start); `OtelStatus.grpc` says whether the build includes gRPC, and Settings > OpenTelemetry and `harness otel` read it. To build with gRPC: `cargo build --release -p harness-cli --features otel-grpc` (GUI: `-p harness-studio --features otel-grpc`). "Send test" (`otel::test_export`) sends a single `harness.test_export` span without retries and returns the collector's response with the duration.

### 13.6. Security Model
- The Control API (`harness-api`, implemented) requires `Authorization: Bearer` on every request except `/health`.
  - The local session token (`hss_` + 256 bits) is refreshed on every API start and kept in memory and in the `<data>/api-token` file. The file is open only to the user: 0600 on Unix, and on Windows a protected DACL with a single entry for the current user (Win32 `SetNamedSecurityInfoW`; `icacls` is not called). It has full authority.
  - Named tokens (`hs_<id>_<256 bits>`) are created with scopes: `read`, `inference` (access to the gateway), `models:write`, `downloads:write`, `servers:write`, `servers:control`, `conversations`, `tools` (runs Harness tools; does not include `read`), `admin`. `admin` covers everything, and write scopes cover read too; `models:write` covers `downloads:write`, and `servers:write` covers `servers:control`. The scope is determined from the route and method by a central table (`auth::required_scope`).
  - Token policy (`harness_core::token_policy`): `models` (alias globs), `endpoints` (`GatewayEndpoint` groups), `limits` (`requests_per_minute`, `tokens_per_minute`, `max_concurrent`); fields flattened into `TokenInfo`/`StoredToken`. In the gateway, `auth::Caller` carries the policy: the endpoint check right after authentication, the rate limit after the body is read (so the analytics/OTLP record of a rejected request has the model name), and the model permission after alias resolution.
  - Rate limit (`harness_core::gateway::limits::RateLimiter`, `GwState.limiter`): two token buckets per token id (capacity = the per-minute limit, refilled at limit/60 per second) and an in-flight request counter. `admit` checks all of them together; if one rejects, none is consumed and the longest wait is returned. The returned `Permit` is held in `RecordGuard`, and when the request ends, `complete(prompt + response tokens)` is deducted from the token bucket and the concurrency slot is released. The snapshot is written to the response headers (`x-ratelimit-*`, `anthropic-ratelimit-*`, `x-harness-ratelimit-*`).
  - Only a salted SHA-256 digest is stored (`config/api_tokens.json`, schema v2; v1 is migrated with a `.bak-v1` backup). Because the secret is 256 bits of randomness, a slow hash like argon2 would gain nothing and would slow every request. The plain value is returned only once, at creation. Comparisons are constant-time.
  - The "Open anyway" confirmation is given from the API only with the `admin` scope; the rule is written to the same record as in the GUI.
- **Fallback port (gateway and Control API):** If the port in Settings (11435 / 11500) is held by another program, the listener moves to a fallback port (`ports::bind_with_fallback`): first the last fallback port (`config/ports.json`, `PortState`), then the first free port above the configured port; well-known ports, the llama-server range (11440-11499) and the other listener's port (for the gateway, the Control API and Ollama ports; for the API, the gateway port) are skipped. The check is done with connect + bind as with server ports (so that it does not bind next to another program's wildcard listener on Windows and split traffic). The state is in the `port_fallback {configured, holder}` field (`GatewayStatus`, `ApiStatus`); Settings > Gateway, Settings > Developer > Control API and the managed endpoint card in Connections show the program holding the port and the actual port. Since the API's actual address is already written to `instance.json`, the CLI finds it on its own. Every port the gateway listens on is added to `PortState.gateway_history`; after the gateway starts, client settings Harness wrote for one of these ports are moved to the new address (see INTEGRATIONS.md). A port given explicitly with `harness serve --port` / `--gateway-port` does not fall back; when it is taken, `api.bind_failed` / `gateway.bind_failed` is returned (with the program holding the port).
- The API is off by default and binds to `127.0.0.1:11500`. Another address needs an explicit setting (`allow_network`) and at least one named token. On loopback, the `Host` header must be loopback (DNS rebinding). CORS is off by default; it opens only to explicitly written `http(s)://host[:port]` origins (no `*`).
- The OpenAPI document is public on loopback (it contains no secrets; tools read it without a token); with a network bind it requires `read`.
- The gateway binds to `127.0.0.1:11435` by default. Opening it to the LAN needs `allow_network` and at least one named token with the `inference` scope; on a network address a token is always required (no keyless LAN).
- MCP (implemented): `/mcp` is behind the same guard; a valid token (`read`) is enough to connect, each tool requires its own scope, and `tools/list` is filtered by the token's scope. Tools call the API in-process with the caller's token, and the scope is checked a second time there. `Origin` only for those in the CORS list. The stdio `harness mcp` narrows the local session token with `--scope` (default `read,servers:write,tools`). Harness's built-in tools are offered over MCP only when `settings.tools.mcp_expose` is on and only for calls the policy runs without asking. Opening to the network (`/exposure-ack`) does not exist in MCP.
- CORS is managed with an allowed-origin list. The existing protected flag list and keychain layout are preserved.
- **Implemented:** the rules for llama-server are in `harness_core::network`. `prepare_launch` resolves the default bind address, the CORS value and the "Open anyway" confirmation on every launch path (`orchestrator::launch`); `check_exposure` reapplies the same rule inside `build_args`. Errors are i18n keys (`network.*`). Details: [SECURITY_MODEL.md](SECURITY_MODEL.md).

### 13.8. Engine Abstraction and the MLX Evaluation

- **audio.cpp (`engine/audio_cpp.rs`, Apache-2.0):** a resident `ServerEngine` from `0xShug0/audio.cpp` release archives. One process serves one TTS model. `ProcessManager` owns a temporary run directory containing `server.json`, starts `audiocpp_server --config server.json --no-ui`, and polls `/health`. The config binds only `127.0.0.1`, loads lazily, and resolves `auto` to the installed backend; the gateway scheduler owns leases, eviction, and TTL.
  - `general.architecture = audiocpp` and `audiocpp.model_spec.family` identify the engine and TTS family. Unsupported audio.cpp families remain non-runnable and cannot fall through to llama.cpp. Companion files make the model path a folder; otherwise it is the GGUF. PocketTTS language comes from its language folder, and voice ids come from sorted `embeddings/*.safetensors` stems.
  - `speech.rs` forwards the definition alias, text, and voice to the resident `/v1/audio/speech`, requests WAV, and uses the shared audio encoder for other response formats. The Playground checks the selected model's engine installation. Hub variants of `audio-cpp/audio.cpp-gguf` keep each model's folder companions separate. Memory is estimated as model file bytes × 1.5 for weights and compute buffers, without llama KV calculations.

- The `Engine` trait:
  - `detect_capabilities`
  - `build_launch`
  - `health`
  - `openai_base`
  - `metrics_source`
  - `supports(format)`
- The first implementations come with `LlamaCppEngine`: the official release, a system or custom binary, and forks such as PrismML. Runtime selection stops being global and is done **per server**.
- **Engine abstraction (implemented; `crates/harness-core/src/engine/`):** the trait `Engine` (family, kind, `release_source`, `release_asset`, `pick_release_assets`, `supports(format)`, `detect_capabilities` / `cached_capabilities` / `probe_capabilities`, `param_catalog`) and two sub-traits:
  - `ServerEngine`: `build_launch`, `health_path` / `health`, `openai_base`, `metrics_source` / `parse_metrics`, `estimate_memory`. `LlamaCppEngine` delegates these to the `process`, `capabilities`, `params`, `vram` and `telemetry` modules; golden tests (`engine_golden_tests.rs`) pin the output to its pre-refactor state.
  - `JobEngine`: `job_binary`, `parse_progress`; `job::run_job` starts the process, extracts progress from lines, kills the process tree on cancellation (Windows Job Object, Unix process group: `command-group`), and checks the expected output files. Its first user is `LlamaBenchEngine` (`engine::llama_bench()`): because it is a tool of the llama.cpp family it is in the `engines()` list, i.e. it is not a registerable runtime family. `BenchmarkManager` (`benchmark.rs`) builds the arguments and gives the job to `run_job` on a thread with its own single-threaded tokio runtime (independent of the calling context: GUI, API, CLI, automatic measurement), turns events into `BenchmarkProgress` / `BenchmarkFinished`; the time limit is a timer that triggers the cancel channel.
  - Selection: `runtimes::engine_for(runtime_id)` (the official and system runtime are llama.cpp; the registered runtime's `family` field; an unknown family is an error) and `orchestrator::server_engine_for` (an explicit runtime, a running launch, a registered profile: the same selection as `server_binary_for`). Capability, catalog and flag commands, and `GET /runtime/flags` use this; `capabilities::runtime_flags(engine, caps)` maps the flag to the engine's catalog.
  - GitHub install (`runtimes/github.rs`): archive naming is the family's job (`Engine::pick_release_assets`; llama.cpp: `llama-<tag>-bin-<os>-<backend>[-<version>]-<arch>` + the `cudart-*` companion for CUDA); explicit asset name, version order, SHA-256 check, validation of the download prefix, and `.staging` / `--version` are shared.
  - Deliberately left: `params::is_protected` (the flags Harness manages) is specific to llama-server (whisper's is `whisper_cpp::is_protected`).
- **whisper.cpp (implemented):**
  - `WhisperCppEngine` (`engine/whisper_cpp.rs`, family `whisper.cpp`, binary `whisper-server`). `server_for(config)`: if it is not router mode and the model file is `.bin` (`ModelFormat::GgmlBin`), whisper; otherwise llama. Version probing is `--help` (`Engine::version_arg`; `whisper-server --version` hangs the process), and the version number is from the GitHub tag (`runtimes::version_from_tag`). Flag capabilities come from the `--help` table via `capabilities/whisper.rs`; the catalog is `params_whisper.toml` (33 parameters, `wparam.*`).
  - Launch: `-m model --host --port [-t N] [--no-gpu] --language auto` + catalog + custom arguments; loopback only (no authentication, the gateway is the gate). Health is `GET /health` (200 + `{"status":"ok"}`); there is no `/metrics` or slots, and telemetry is online/offline only. `ProcessManager::run_claimed` does the llama-specific preparation (serve mode, slot plan, KV, main GPU) only for llama; `ServeMode::Transcription` skips validation. Response headers are `x-harness-model`, `x-harness-audio-seconds`, `x-harness-asr-ms`.

### 13.9. Test Strategy
- No mocks.
  - Unit tests use real files and output samples (e.g. a real `--help` dump).
  - End-to-end tests run as `#[ignore]` against a real llama-server with `HS_LLAMA_SERVER` and `HS_TEST_MODEL`.

### 13.10. Persistence Decision: JSON for Configuration, SQLite for State and Chats
Evaluation:

| Criterion | JSON files + a separate index | SQLite (`state.db`) |
|---|---|---|
| Atomic multi-entity change (message + variant + fork + folder) | Multiple files and indexes must be kept in sync; risk of inconsistency on a crash | A single transaction, consistent |
| Search | Requires reading and scanning all files | FTS5 full-text index |
| Large history, pagination | The chat file is read and written in full | Only the needed rows are read |
| GUI + CLI + API read at the same time | Locking and races are handled by hand | Concurrent reads with WAL, a single writer |
| Schema evolution | A version and converter in every file | `PRAGMA user_version` + sequential SQL migrations |
| Human readability, hand editing, diffs in git | Good | Poor; compensated by JSON/Markdown export |
| Dependency | None | `rusqlite` (bundled), about 1-1.5 MB binary increase |
| Backup | File copy | `VACUUM INTO` / backup API (single file) |

**Decision:**
- **Chats and user state are in SQLite (`state.db`).** Scope:
  - conversations, messages, message_variants, forks
  - folders, pin/favorite
  - tool_calls, attachments metadata
  - FTS5 search
  - library state (favorite, last use)
  - The JSON option was rejected. Relations between entities (variant <-> message, fork <-> source message) and search make file + index synchronization fragile. SQLite is the right tool for exactly this kind of persistence.
- **Request telemetry is in a separate file (`analytics.db`).** Reasons:
  - The retention period (30 days of raw rows) and the write load are different.
  - The user's "delete analytics" action must not affect chats.
  - Implementation: `analytics::AnalyticsDb`, the same rules as `state.db` (WAL, `synchronous=NORMAL`, 5 s busy timeout, `PRAGMA user_version` + sequential migrations in a single transaction, a newer schema opens read-only) and additionally `secure_delete=ON`. A single connection behind a mutex; the writer is the `harness-analytics` thread.
- **Small configurations the user can edit by hand and share stay JSON.** Scope: `settings`, `model_definitions`, `server_profiles`, `inference_presets`, `mcp_servers`. These are small, rarely changing, portable documents that can be put in git. They do not need relational queries, so SQLite's advantage does not apply here.
- **Every persistent format carries a version.**
  - JSON has a `schema_version` field. The migration chain is `v1 -> v2 -> …`:
    - a `.bak-v<N>` backup is taken before migration
    - writes are atomic
    - if a newer, unknown version is encountered, the file is opened read-only and is not overwritten
  - In SQLite, `user_version` + sequential migrations are applied within a transaction on every open.
  - Implementation: `store::Schema { file, current, envelope, migrations }` + `JsonStore::{load,save,update}_versioned`. A file without a version counts as v1. In object files the field is added to the root (`Merged`); array/free-map files are wrapped (`Wrapped`: `downloads.json` -> `jobs`, `model_hashes.json` -> `hashes`, `model_sources.json` -> `sources` (v1), `benchmarks.json` -> `runs`, `external_models.json` -> `models`; these are v2). A file with a newer version returns `read_only`, and writes are rejected with a `[store.newer_version]` error. `get_data_files_status` gives each file's version.
- Export and import: chats as JSON and Markdown; ModelDefinitions and presets as JSON and `*.harness.toml`.

**`state.db` schema (v1-v6, `harness_core::state`):**
- `folders(id, name, parent_id, sort, created_at)`. When a folder is deleted, the chats and subfolders in it move to the parent folder.
- `conversations(rid, id, title, title_source, folder_id, pinned, favorite, created_at, updated_at, last_opened_at, server_id, model_alias, preset_id, system_prompt, settings_json, metadata_json, current_leaf_id, forked_from_conversation_id, forked_from_message_id)`.
  - `title_source`: `none | fallback | auto | user`; an automatic title does not overwrite a title the user wrote.
  - A fork is not a separate table: the new chat keeps its source with the `forked_from_*` fields.
- `messages(id, conversation_id, parent_id, parent_variant_id, role, created_at, active_variant_id)`: messages form a tree. The visible path goes from the root to `current_leaf_id`.
  - Edit = rewind from here (`rewind_before`): the user message and everything after it leave the active path; `current_leaf_id` goes to the message's parent (if it is attached to the parent with that variant, `active_variant_id` also returns to it). If the first message is rewound, the path is empty: `current_leaf_id` = the empty string (`EMPTY_LEAF`), `build_view` returns an empty path and the next message replaces it. Nothing is deleted: a new user message sent under the same parent message is a sibling of the old one (the branch arrows bring back the old continuation, `select_branch`). The UI asks for confirmation, puts the message text into the input box and shows an "Undo" notification. The old `edit_user_message` command (writing a sibling message right away) still exists but the UI does not use it.
  - "Branch from here" (`fork_conversation`) is a separate operation: a new chat, a copy of the path.
  - Regenerate: a new variant on the message. Later messages know which variant they belong to through `parent_variant_id`; the continuation of the old variant is not lost.
- `message_variants(rid, id, message_id, content, reasoning, tool_calls_json, stats_json, finish_reason, stopped, tool_limit_reached, error, model_alias, created_at)`.
  - Tool calls (name, arguments, status, result) live in the variant's JSON field instead of a separate table: they are always read and written together with the variant and returned to the context in order, never queried on their own.
- `attachments(id, message_id, kind, name, mime, size, sha256, path, created_at)`: metadata only.
- `app_state(key, value)`: flags for one-time operations (e.g. the legacy Playground migration).
- v2: `model_state(model_id, favorite, last_used_at, last_definition_id, last_preset_id, added_at)`. `model_id` is the normalized file path (`library::state_key`: `/` separator, lowercase on Windows). Last use is written when a server is launched (`orchestrator::launch_with_binary`), and the added time on scan (only if empty); on a move the row switches to the new path, on deletion it is removed. The shared connection is `state::shared()`.
- v3: `vram_measurements(model_key, settings_key, model_size, measured_at, data_json)`, primary key `(model_key, settings_key)`. After a successful load (`process::verify_after_start` -> `vram::record_after_load`), the last load's log buffers (`model/KV/compute buffer size`, written only with `-lv 4`/`--verbose`) and the process's GPU memory are written. `settings_key` consists of context, ngl, KV types, slots, FA, ubatch, SWA and mmproj; the newest 16 rows per model are kept, and a measurement is ignored if the file size changes. Router and draft-model runs are not recorded.
- v4 (split view): `message_variants.meta_json` (a JSON object from the client; non-object values are not stored). A split turn is a single assistant message, and A and B are its variants; the side is marked with `meta.compare = {group, side, model, target, server_id, preset_id, preset_name, sequential}`. `PathMessage.compare` carries all sides in the displayed variant's group (in side order). The message after a split turn is appended without `parent_variant_id` (`AppendMessage.any_parent_variant`), so it stays on the path whichever side is shown. `adopt_compare_side` turns the active variant of the split messages on the path to one side. Split settings are in the chat's `metadata_json.compare`. In export, `ExportedVariant.meta` (absent in old files; `harness.conversation.v1` stays the same); Markdown writes both sides of the split turn. When a split turn is regenerated, a second comparison group (a new `group`) is added to the same message; `PathMessage.compare_groups` gives each group's A variant (oldest to newest), and the arrow buttons walk among them with `select_variant`. If a split side runs a tool loop, the variant is the last round (`content`, `tool_calls`), and earlier rounds are in the `meta.rounds` array (`{content, reasoning, tool_calls, stats, ...}`); the request builder (Rust `request_messages`, TS `buildApiMessages`), the compaction count and the summary dump put these rounds in order first, then the variant. This way message ids, variants and regeneration stay in a single message.
- v5 (local RAG): `rag_documents(rid, id, conversation_id -> conversations ON DELETE CASCADE, name, kind, source_path, size, sha256, pages, content, chars, status, error, mode, embed_model, embed_dims, created_at, updated_at)`; `status` `pending | extracting | embedding | ready | failed | cancelled`, `mode` `auto | full | retrieval`, `content` is the full text with pages separated by `[Page N]` lines. `rag_chunks(rid, document_id -> rag_documents, seq, text, page_start, page_end, heading, embedding BLOB)`: the vector is little-endian f32 produced by `embed_model` (alias) with `embed_dims` dimensions. `rag_fts` (FTS5 external content, `unicode61` accent-insensitive) follows the chunk text via triggers. The same SHA-256 is not added to a chat twice. Documents travel with the chat: copying and forking copy `ready` documents with their chunks and vectors to the new chat (`export::read_export(.., in_database = true)` -> `insert_export`; a document that is not ready is not copied); JSON export writes `ConversationExport.documents` (name, kind, mode, SHA-256, pages, full text, chunks) and does not write vectors or the source path; an imported document is `ready` and searchable by keyword, and its vectors arrive when it is reindexed with the embedding model. If the `documents` field is missing (an old file), it is imported without documents. The document count and chunk ceiling also apply on import. Markdown export lists the document names.
- v6 (stateful Responses): `gateway_responses(rid, id UNIQUE, scope, previous_id, model, created_at, last_used_at, input_json, response_json, bytes)`, index `last_used_at`. `scope` is the caller (`token:<id>`, `harness`, `anonymous`); every read/delete is filtered by scope, and an `INSERT` with another scope's id does not overwrite. Retention (`settings.gateway.responses`): if `last_used_at` is older than the age limit it is invisible and deleted on every insert; then rows beyond `max_stored` and bytes beyond `max_mib` (a cumulative total via a window function) are deleted by last use. When a chain is continued, the `last_used_at` of all links is refreshed. Deletions in this table are made with `secure_delete` on (the rest of state.db is unaffected); "Delete all" also truncates the WAL.
- Context compaction (no schema change): the marker is a `role = 'system'` message, the summary is in `content`, and the details are in `meta_json.compaction` (v4 column); see §9.1.
- `search_index` (FTS5, `unicode61`, accent-insensitive): titles (rowid = `-conversations.rid`) and variant contents (rowid = `message_variants.rid`); kept in sync with triggers.
- The export format is `harness.conversation.v1`: the whole tree, every variant, timestamps. On import the structure is validated (duplicate ids, missing parent message, cycles) and new ids are assigned.

**`analytics.db` schema (v3, `harness_core::analytics`; v2 `requests.slots`/`waited`, v3 `rate_counters`, `direct_usage`, `direct_daily`):**
- `requests` (raw rows; the primary key is the gateway request id): `started_at_ms`, `day` (UTC day number), `endpoint`, `model`, `alias`, `definition_id`, `server_id`, `client` (label), `user_agent`, `harness_client`, `token_name`, `stream`, `status`, `error_code`, `oom`, `cancelled`, `queue_wait_ms`, `load_ms`, `evicted_json`, `ttft_ms`, `total_ms`, `prompt_tokens`, `completion_tokens`, `cached_tokens`, `prompt_ms`, `predicted_ms`, `prompt_per_second`, `predicted_per_second`, `draft_n`, `draft_accepted`, `finish_reason`, `ctx_size`, `context_fill`, `vram_peak_bytes`, `ram_peak_bytes`, `backend`, `compat_json`, `content_captured`. Indexes: time, (alias, time), day. Retention is `settings.analytics.raw_retention_days` (default 30) full days.
- `daily_rollup` (permanent, `WITHOUT ROWID`, key `(day, alias, client, endpoint)`): `requests`, `errors`, `ooms`, `cancelled`, token totals, `total_ms_sum`, `ttft_ms_sum`/`ttft_n`, `queue_ms_sum`, `load_n`/`load_ms_sum`, `gen_tokens_timed`/`gen_ms_sum` and `prompt_tokens_timed`/`prompt_ms_sum` for token-weighted speed, `vram_peak_max`/`vram_peak_sum`/`vram_n`, `ram_peak_max`, `draft_n`/`draft_accepted`, `last_used_ms`, `definition_id`. Maintenance (30 s after startup and hourly; immediately when the retention setting changes): every day before today that has raw rows is re-aggregated (overwritten, running it again is harmless), then raw rows older than the retention period are deleted.
- `request_content` (only for definitions with `capture_content` on): `request_id`, `captured_at_ms`, `expires_at_ms`, `request_body`, `response_body`, `request_truncated`, `response_truncated`. Deleted when it expires or its raw row is deleted.
- `rate_counters` (v3, `WITHOUT ROWID`, key `(token_id, kind)`): `level` (bucket level, can go negative), `capacity`, `at_ms` (wall clock), `rev` (write version). `clear_analytics` does not touch this table.
- `direct_usage` (v3, key `(minute_ms, server_id)`): `day`, `label`, `prompt_tokens`, `completion_tokens`; `direct_daily` (v3, key `(day, server_id)`): the daily total of minutes older than the retention period. `clear_analytics` deletes both.

## 14. Target: Multi-Runtime and Tool Platform

Plan and order: [ROADMAP](ROADMAP.md). This section defines the boundaries and constraints; detail is added as things are implemented.

```
                 ┌──────────── harness-core ─────────────┐
 Surfaces ──────▶│ Tool Engine            Engine registry│
 (GUI/CLI/API/   │  ├ built-in tools       ├ llama.cpp   │──▶ llama-server
  MCP/gateway)   │  ├ MCP client           ├ whisper.cpp │──▶ whisper-server
                 │  ├ installed/generated (JS) └ (sd.cpp …)│
                 │  └ permission + log + network layer     │──▶ internet (only from here)
                 └───────────────────────────────────────┘
```

### 14.1. Tool Engine
- A tool = name + description + JSON Schema input + permission class + source (`builtin`, `mcp:<server>`, `installed`, `generated`). Only the schemas of tools enabled for that chat/request go to the model.
- The loop is in the core: `tool_calls` are merged from the stream (today's `ToolCallAccumulator` logic, in Rust), the permission is checked, the tool runs, and the result is appended as a `tool` message. Round limit, per-call timeout, result size limit, cancellation. The Playground, the Control API and the gateway use the same loop.
- The model produces text and does not reach the network. The only component that reaches the network is Harness's network layer (`fetch_url`, `web_search`, MCP HTTP, the tools' `harness.http`); every request goes through the SSRF check and the tool log.
- If Harness can fulfill the gateway's server-side tools (e.g. Responses `web_search`), it completes them locally; if it cannot, today's explicit 400 behavior continues.
- MCP: Harness is the client (stdio + Streamable HTTP), implemented (§9). The configuration `config/mcp_servers.json` stays as is; Harness connects (it is given to llama-server only if llama-server's own MCP option is on). `harness-mcp` (Harness's MCP server) is independent of this.

### 14.2. Engines
- The `Engine` trait (§13.8) covers two kinds: **server** (a long-lived process, an HTTP endpoint: llama-server, whisper-server) and **job** (a process per request, or a queue; progress, cancellation, file output). stable-diffusion.cpp is connected as a server (sd-server); the job kind is kept separate for a future family.
- Four llama.cpp-specific layers are split behind an interface per runtime family: capability reading, the parameter catalog, memory estimation, telemetry. whisper.cpp's catalog and memory estimation live in its own file.
- The scheduler runs the VRAM budget across families from a single calculation; the gateway's JIT/TTL rules are independent of families.
- The model registry carries a capability -> format -> compatible runtime mapping; GGUF is just one format. Implementation: `model_registry` adds no new estimates, it unifies the existing ones: `Capability` (for the Hub from the `hub_tasks` task, for a local file from `library::ModelCaps`), `ModelRecord` (capabilities + `hub_compat::ModelFormat` + runtime family + `Compatibility`; the Library's `LibraryEntry.record`, the Hub's `HfModelSearchResult.capabilities`), `fit_on_machine` (an engine by file format: GGUF `vram::fit`, whisper ggml via the whisper engine's `estimate_memory`; the `estimate_fit` command calls this). A format/capability with no runtime is recorded as "not supported".

### 14.3. Security of Installed and Generated Tools
- **Implementation:** the package format is `tools/package.rs` (manifest + validation), the engine is `tools/js_engine.rs` (`rquickjs`: memory and call stack limits, a time/cancel interrupt hook; `harness.http` is checked per request and per redirect against the domain list, then goes through `fetch_url`'s public-address check; `harness.fs` is resolved with `Workspace` and stays within the given folder), and the registry is `tools/installed.rs` (`<data>/tools/<name>/`, source `installed`, class: file writing is dangerous, network/file reading is restricted, otherwise safe). The package test is `tools/package_test.rs` (a `cases` array, the same sandbox and permissions, a temporary working folder). The generator `tools/generator.rs`: the selected chat model writes the manifest + code + test, errors are fed back to the model (at most 2 retries), the permissions the user wrote are the upper bound (`within_bounds`), and an approved tool is registered in memory with source `generated` (at most 5 per session, the same policy/approval/tool log); "Save Permanently" writes to `<data>/tools/`.
- Code runs in the embedded JS engine; the environment gives no file, network or process access by itself. Capabilities come only through the objects Harness injects, and the permissions in the manifest (domain list, file scope) are enforced inside these objects.
- This guarantee does not exist for Python/Node child processes (MCP servers, and PyTorch in the future): on Windows a per-process network block requires an administrator-privileged firewall rule, and macOS `sandbox-exec` is deprecated. The UI does not say "network off" for these processes; it shows only what can be observed (requests passing through Harness).
- Distribution: the manifest in the index repository carries a SHA-256; a downloaded package is not installed without verification. A tool on the `revoked` list is disabled and the user is warned.

### 14.4. ONNX Encoder Engine (`harness-onnx`)

Runs Hugging Face ONNX encoder models (embedding and reranking) without Python; it is the third engine family (`onnxruntime`, `ModelFormat::Onnx`, `.onnx`).

- **Sidecar:** `crates/harness-onnx` (library + the `harness-onnx` binary; `ort` 2.0.0-rc.13 `load-dynamic`, `tokenizers`, axum). It ships with the application (`externalBin`) and listens only on local `127.0.0.1` (there is no authentication; the gateway exposes it to the outside). Endpoints: `/v1/embeddings` (OpenAI format, `float`/`base64`, `dimensions`), `/v1/rerank` (llama.cpp/Jina/Cohere format; aliases `/rerank`, `/reranking`, `/v1/reranking`), `/v1/models`, `/health` (503 while loading, `{"status":"ok"}` when ready). A wrong endpoint (like rerank on an embedding model) gives 501.
- **Model package:** `onnx/model.onnx` (or `model_quantized`, `model_fp16`, `model_O*`, etc.) + `tokenizer.json`. Pooling is from `1_Pooling/config.json` / `modules.json` (mean, cls, max, last-token, sqrt-len, weighted), L2 if `2_Normalize` exists, and the longest sequence in the order `sentence_bert_config.json` -> `tokenizer_config.json` -> `config.json` (upper limit 8192). A `ForSequenceClassification` architecture is a reranker (the last logit is the score). Unsupported sentence-transformers modules such as Dense are rejected with an explicit error; repositories with only safetensors are not supported (the Hub marks them as can't run).
- **Execution providers:** DirectML (Windows, AMD and NVIDIA), CUDA (optional), CPU. `auto` tries the available GPU provider; if the session cannot be created, it falls back to CPU. On the Windows CUDA build Harness passes `--cuda-fallback-exit`: when the CUDA session cannot be created the sidecar exits with code 86 and Harness restarts the model once on DirectML, saying so in the server log. The Windows CUDA build (opt-in, Settings > Runtime > Registry > ONNX Runtime) installs with the CUDA 12.9 runtime, cuBLAS, cuFFT and cuDNN 9.27 DLLs, read out of NVIDIA's `nvidia-*-cu12` PyPI wheels with pinned SHA-256s (about 2.1 GB; NVIDIA's licence texts beside them); the sidecar adds its ONNX Runtime folder to its own DLL search path (`SetDllDirectoryW`), so no PATH or system setting changes. Once that build is installed, `auto` launches with it. A CUDA launch whose CUDA build is missing runs on DirectML and the server log says so. For DirectML, the memory pattern and parallel execution are turned off.
- **ONNX Runtime delivery (decision):** the library is not embedded in the installer; it is downloaded on first use as a managed runtime (`harness_core::onnx_runtime`, `<data>/bin/onnxruntime/<build>-<version>/`). Rationale: the installer would grow by ~25 MB for DirectML and hundreds of MB for CUDA; most users never use this engine; the same rule as the llama.cpp/whisper.cpp runtimes (download, verify, show in Settings > Runtime). Every file has a pinned SHA-256 (DirectML build ORT 1.24.4, CPU/CUDA 1.28.3); ZIPs are opened by fetching only the needed files with HTTP range requests (CRC-checked), and a tgz archive is downloaded whole and verified against the archive digest. Verification and removal are done from the Settings card and the Control API (`/onnx-runtime`). Linux and macOS tgz installs rely on the archive digest alone.
- **Task pipelines (`/hf`, gateway `/v1/hf/{model}`):** a `config.json` head that is not an embedding or reranker makes a task model (`ModelKind::Pipeline`, `LocalModel.task`, `ServeMode::Pipeline`): `*ForSequenceClassification` with more than one label is text-classification (an NLI model with entailment/contradiction labels is zero-shot-classification), `*ForTokenClassification` token-classification, `*ForMaskedLM` fill-mask, `*ForQuestionAnswering` question-answering. Pre- and post-processing are in Rust (`tasks.rs`, `hf_api.rs`), no Python. The request and response are the Hugging Face Inference API's, shared with the Python worker:
  - Request: `{"inputs": ..., "parameters": {...}}`. `inputs` is a string or a list of strings; question-answering takes `{"question", "context"}`, a text pair `{"text", "text_pair"}`. Parameters: `top_k`, `candidate_labels`, `multi_label`, `hypothesis_template`, `aggregation_strategy` (`none`/`simple`/`first`/`average`/`max`).
  - text-classification: one list per text, `[[{"label", "score"}]]` (a single text too). zero-shot-classification: `{"sequence", "labels", "scores"}`. token-classification: `[{"entity_group" | "entity", "score", "word", "start", "end"}]` (a list of lists for several texts). fill-mask: `[{"score", "token", "token_str", "sequence"}]`. question-answering: `{"answer", "score", "start", "end"}`, a list when `top_k` > 1. `start` and `end` are character offsets (Python string indices), not bytes.
  - Limits: at most 256 texts and 64 candidate labels per request. A question-answering context longer than the model is read in overlapping windows (the transformers `doc_stride`, at most 32 windows), and the best spans of all windows are returned. A text model refuses a `data:` URL input (a file sent to the wrong model) with 400. A cross-encoder with one output, or two unnamed outputs (`LABEL_0`/`LABEL_1`), stays a reranker.
  - The gateway route takes the model from the path and writes it into the body as `model`. A raw image or audio body (`Content-Type: image/*`, `audio/*`, `video/*`, `application/octet-stream`, with `?parameters=<json>`) becomes `{"inputs": "data:<type>;base64,...", "parameters": ...}`, so the upstream always gets JSON; a raw file over 47 MiB is refused with `payload_too_large` (413) before it is encoded. The token endpoint group is `pipelines`. The Playground **Tasks** tab (Advanced) has a form and a result view per task and a JSON body for the others.
- **Vision heads (`vision_pkg`, `vision`, `vision_engine`):** a repo with `preprocessor_config.json` and a vision head in `config.json` is a task model too: `*ForImageClassification` image-classification, `*ForObjectDetection` (DETR, YOLOS) object-detection, `*ForSemanticSegmentation` (SegFormer, BEiT, DPT) image-segmentation, `*ForDepthEstimation` (DPT, Depth Anything, GLPN) depth-estimation. The image processor is read from its config (resize: exact, shortest edge with a longest-edge cap, DPT's aspect-keeping multiple, GLPN's divisor; center crop; rescale; normalize; PIL's resample filter) and applied with the `image` crate; the graph gets `pixel_values` (FP16 when the export asks for it) and `pixel_mask` when it has one. `inputs` is the image as a data URL or base64 (no URLs are fetched; at most 8192 px a side). Responses: image-classification `[{label, score}]` (`top_k`, 5 by default); object-detection `[{score, label, box: {xmin, ymin, xmax, ymax}}]` in pixels of the original image (`threshold`, 0.5 by default); image-segmentation `[{score: null, label, mask}]`, the mask an 8-bit PNG in base64, largest area first (logits upsampled bilinearly to the image); depth-estimation `{depth, width, height, min, max}`, `depth` a PNG scaled by its maximum as the pipeline does. The Playground **Tasks** tab takes an image for these tasks and draws the boxes, overlays the masks and shows the depth map next to the image. Measured on the COCO cats photo (CPU) against the transformers pipeline: ViT (q8) Egyptian cat 0.945 (reference 0.938); DETR (fp32) two cats 0.998, two remotes, a couch, boxes within 1 px of the reference (the q8 export finds the same objects with boxes up to ~10 px wider); SegFormer and Depth Anything give the reference labels and depth range. DirectML crashes the process on the integer operators of dynamically quantized (q8) exports: `ConvInteger` (vision, CTC speech) and `MatMulInteger` (text encoders such as DistilBERT, seen on an NVIDIA GPU). A graph that uses either runs on the CPU (the sidecar scans the file for them before it builds the session); FP32 and FP16 exports stay on DirectML.
- **Zero-shot image classification (dual encoders):** a `CLIPModel` or `SiglipModel` repo exported as one graph (transformers.js `onnx/model*.onnx`, inputs `input_ids`, `pixel_values` and, for CLIP, `attention_mask`; output `logits_per_image`) scores the image against the labels of the request: `{"inputs": "<image>", "parameters": {"candidate_labels": [...], "hypothesis_template": "This is a photo of {}."}}` answers `[{label, score}]` for every label, best first. Each label is put in the template (the pipeline's default), tokenized with the repo's `tokenizer.json` and padded with its `pad_token`: CLIP to the longest label, SigLIP to 64 tokens as it was trained; for SigLIP the sentence is first lower-cased and stripped of punctuation, as transformers' `SiglipTokenizer` does (its `tokenizer.json` does not). CLIP's scores are a softmax across the labels, SigLIP's a sigmoid per label (they do not add up to 1). The towers alone (`text_model*`, `vision_model*`) are not offered for download and are not served; such a repo is not an embedding model either, though it has a tokenizer. Measured on the COCO cats photo with five labels against the transformers pipeline (CPU, FP32): CLIP ViT-B/32 cats 0.9854 (reference 0.9856), relative logits within 0.07; SigLIP base cats 0.0532 (reference 0.0542), the same order. The q8 exports drift: CLIP q8 swaps the 2nd and 3rd labels, so the Hub's FP32 `model` variant comes first.
- **Zero-shot object detection (OWL-ViT, OWLv2):** an `OwlViTForObjectDetection` / `Owlv2ForObjectDetection` repo exported as one graph (`input_ids`, `attention_mask`, `pixel_values` in; `logits` `[patches, queries]` and `pred_boxes` out) serves zero-shot-object-detection.
  - `parameters.candidate_labels` are the queries as they are: no sentence around them, as in the pipeline. Each is padded to 16 tokens.
  - Every patch keeps its best query. Its sigmoid score must reach `threshold` (0.1 by default). Boxes come back in pixels of the original image, best first, cut to `top_k`.
  - OWLv2's processor pads the image to a square (bottom and right, grey) before the 960×960 resize, so its boxes are relative to that square; the sidecar pads the same way.
  - The Playground Tasks tab takes an image and labels and draws the boxes.

  COCO cats photo, labels "cat, remote control, couch", q8, CPU:
  - OWLv2: both cats 0.64 / 0.56, both remotes 0.72 / 0.46, the couch 0.51, 2.8 s.
  - OWL-ViT: the cats and one remote at 0.18–0.22, 0.25 s.
- **Image captioning (`decoder`, `generation`):** a `VisionEncoderDecoderModel` repo (ViT + GPT-2 such as `nlpconnect/vit-gpt2-image-captioning`) exported as `encoder_model*.onnx` and a text decoder serves image-to-text. The library entry is the encoder, and the decoder graphs belong to it. The decoder of the same precision is taken (`decoder_model_merged_quantized.onnx` next to `encoder_model_quantized.onnx`), falling back to the unsuffixed one. The downloader puts each encoder variant together with its decoder and offers no decoder alone. Generation is greedy:
  - A merged decoder (`use_cache_branch`, `past_key_values.*` / `present.*`) runs its first step with an empty cache and every later step with the cache and the newest token only.
  - A decoder without cache inputs gets the whole sequence every step.
  - Generation starts at `decoder_start_token_id` (or `bos_token_id`) and stops at `eos_token_id`, read from `generation_config.json`, `config.json` or its `decoder` section. The logits follow the transformers rules the config names: `min_length`, `no_repeat_ngram_size`, one-token `bad_words_ids`, `forced_bos_token_id` and `forced_eos_token_id`.
  - `parameters.max_new_tokens` defaults to `max_length - 1` from `generation_config.json` (19 when it names none, as in transformers) and is capped at 256.

  The answer is `[{generated_text}]`, and the Playground Tasks tab shows the caption next to the image. Measured on the COCO cats photo (CPU):
  - q8: "two cats laying on a bed with a remote", 0.75 s.
  - fp32: "a cat laying on a blanket next to a cat laying on a bed", 1.1 s.
- **Text encoder-decoders (`seq2seq_pkg`, `seq2seq_engine`):** a T5 / mT5 / BART / Marian / Pegasus / Blenderbot repo (`*ForConditionalGeneration`, `MarianMTModel`) exported as `encoder_model*.onnx` and a decoder is one library entry. Like the captioner, it pairs the decoder of the same precision; `ModelPackage` refuses all of its graphs as text encoders (`TextGenerator`).
  - Task: Marian is translation. A model whose only `task_specific_params` entry is `summarization` (distilbart-cnn, Pegasus) is summarization, with that entry's lengths and n-gram rule. Anything else is text2text-generation (T5: the prefix such as `translate English to German:` is part of the input).
  - Answers: `[{summary_text}]`, `[{translation_text}]` or `[{generated_text}]`, as the transformers pipelines give them. `inputs` is one text, cut to `model_max_length` / `max_position_embeddings` tokens; `parameters.max_new_tokens` works as for captions.
  - Generation through the shared `decoder`. The cross-attention cache of the first step is fed again on later steps. With `num_beams` above 1 (the model's config, or `parameters.num_beams`, at most 8) it is beam search as transformers' `BeamSearchScorer` does it: the beams run as one batch, each beam's self-attention cache follows it, finished hypotheses are ranked by `log p / length ^ length_penalty`, and `early_stopping` ends the search once `num_beams` have finished. Beams share a budget of 1024 decoder rows (4 beams get 256 new tokens, 8 get 128).
  - transformers.js Marian exports carry a `Precompiled` normalizer whose charsmap is `null`, and the tokenizers crate panics on it. The charsmap is SentencePiece's `nmt_nfkc` table, so the loader rebuilds it from its rules: NFKC, tab / line feed / carriage return / vertical tab / form feed as spaces, the other C0 controls, DEL and zero-width characters removed. Full-width forms and ligatures fold as in SentencePiece, and a line break separates words as a space does.
  - mBART, M2M100 and NLLB (source and target language tokens) are not covered.

  Measured with q8 exports (CPU): `t5-small` "translate English to German: The house is wonderful." → "Das Haus ist wunderbar." in 0.1 s; `opus-mt-en-de` "The weather is nice today. I am going to the park." → "Das Wetter ist heute schön. Ich gehe in den Park."; `distilbart-cnn-6-6` with its 4 beams summarizes the Eiffel Tower paragraph in 3.7 s ("The Eiffel Tower surpassed the Washington Monument to become the tallest man-made structure in the world . It is the second tallest free-standing structure in France after the Millau Viaduct . …"; greedy decoding takes 2.3 s and gets the facts wrong). Marian fp32 with 4 beams translates both sentences of "Hello, how are you? I would like to book a table for two people tonight."; greedy decoding, and the q8 export even with beams, drop the first sentence.
- **Audio classification (`audio_pkg`, `audio_engine`):** a repo with `preprocessor_config.json` and a `*ForAudioClassification` (or `*ForSequenceClassification` of a speech encoder: wav2vec2, HuBERT, WavLM, AST...) head in `config.json` serves audio-classification. `inputs` is a WAV file as a data URL or base64 (PCM 16/24/32 or float32, any rate and channel count; mixed to mono and resampled to the processor's `sampling_rate`; at least 25 ms; at most 60 s for a raw-waveform model, whose self-attention grows with the square of the length; at most 10 minutes for an AST, which computes only the frames it keeps). The processor decides the features: `Wav2Vec2FeatureExtractor` gives the raw waveform (zero mean, unit variance when `do_normalize`), `ASTFeatureExtractor` Kaldi filter banks computed in Rust (25 ms frames, 10 ms shift, DC removal, 0.97 pre-emphasis, a Hann window, a 512-point power spectrum, `num_mel_bins` triangular mel filters, log), padded or cut to `max_length` frames and normalized with the processor's mean and std. The response is `[{label, score}]` (softmax, `top_k`, 5 by default). The Playground **Tasks** tab decodes any format the webview reads (WAV, MP3, FLAC, OGG) into a 16 kHz WAV before sending it. On JFK's "ask not" clip (CPU) the AST AudioSet model gives Speech 0.556, Male speech 0.230, Narration 0.202 (q8: 0.572, 0.222, 0.195), 0.6-0.9 s a clip; the q8 export of `superb/wav2vec2-base-superb-ks` loses most of its accuracy (spoken "yes" comes out as "no" 0.23), its fp32 export is right ("yes" 0.75, "stop" 0.98), so the fp32 file is the one to pick for small keyword models.
- **Image feature extraction (bare backbones):** a bare `*Model` export of an image backbone (`model_type` vit, dinov2, deit, beit, convnext, swin, mobilevit, efficientnet, resnet, clip_vision_model, siglip_vision_model and the like) serves image-feature-extraction. The answer is `last_hidden_state` as nested lists, `[1, tokens, dim]`, as the pipeline's `tolist()` gives it. `parameters.pool: true` returns `pooler_output` (`[1, dim]`). DINOv2, whose pooled output is its CLS token, gets that row from the hidden states when the export has no `pooler_output`; another model without one answers 400. The Playground Tasks tab shows the tensor's shape and the first values. `Xenova/dinov2-small` on the COCO cats photo (CPU, ~40 ms): `[1, 257, 384]`, CLS starting -2.656, -1.782, -3.357, -2.237 (transformers reference -2.648, -1.812, -3.327, -2.201).
- **Integration:** `hub_compat` considers ONNX runnable for the feature-extraction / sentence-similarity / text-ranking tasks and the task pipelines above (text-classification, zero-shot-classification, token-classification, fill-mask, question-answering, image-classification, object-detection, image-segmentation, depth-estimation, zero-shot-image-classification, audio-classification, image-feature-extraction, image-to-text, zero-shot-object-detection, summarization, translation, text2text-generation); `downloader` downloads the files an ONNX repository needs (model, `.onnx_data`, tokenizer, pooling configurations) with the folder layout and verifies that it is not a "web page"; `models` recognizes it in the library as Embedding/Reranker; `ProcessManager` sets `ServeMode::Embedding/Rerank`; `orchestrator::launch` installs ORT if it is missing; the gateway forwards `/v1/embeddings` and `/v1/rerank` requests by alias (JIT-loading if needed); RAG model selection and the Playground Embedding/Rerank tabs use the same endpoints. Memory estimate: model size + `max(160 MiB, model/3)`.
- **Tests:** unit (pooling, normalization, request/response mapping, package discovery, ORT constants, remote ZIP, install), `crates/harness-onnx/tests/e2e.rs` (cosine > 0.99 against the all-MiniLM-L6-v2 sentence-transformers reference; ms-marco cross-encoder ranking; DirectML = CPU) and `crates/harness-gateway/tests/onnx_e2e.rs` (JIT loading through the gateway, the RAG client), all `#[ignore]`.


### 14.5. Lemonade Engine (`lemond`)

Lemonade (`lemonade-sdk/lemonade`, Apache-2.0) is an optional managed engine: for running models with FastFlowLM on Ryzen AI NPUs and for offering its own ROCm / Vulkan llama.cpp builds as a second backend. It does not replace Harness's llama.cpp, whisper.cpp and ONNX engines; unless it is installed, nothing changes.

- **Verified against a real release (v2026.41.1):** `lemonade-embeddable-<version>-windows-x64.zip` (5.4 MB; `lemond.exe`, `lemonade.exe`, `LICENSE`, `resources/`), plus `ubuntu-x64`, `ubuntu-arm64`, `macos-arm64` tar.gz. `candidate-v<next>` pre-releases are also published with the same asset names; `Engine::accepts_release` skips them (the stable tag is `vYYYY.NN.N`). Every asset has a GitHub `digest` field (SHA-256 is verified). `lemond [--host H] [--port P] [--no-broadcast] [--log-file MODE] [cache_dir] [config_dir]`; the two directories are positional arguments. Settings are in `config_dir/config.json` (`models_dir`, `websocket_port`, `llamacpp.backend`...). The `LEMONADE_API_KEY` environment variable binds every path except `/live` (including `/internal/*`) to a Bearer key (verified: 401 without a key). Endpoints: `GET /live`, `/v1/health`, `/v1/models[?show_all=true]`, `/v1/system-info`, `POST /v1/pull`, `/v1/delete`, `/v1/load`, `/v1/unload`, `/v1/install` (backend; pull and install stream SSE `progress`/`complete`/`error` events), `/internal/shutdown`; chat, embeddings, rerank and transcription are OpenAI-compatible. A model loads by itself on the first request; if the backend is missing, it is downloaded during that request (Vulkan llama.cpp 35 MB ≈ 6 s). Models are under `models_dir` in the Hugging Face cache layout; if `models_dir` does not exist, pull gives `500`, and on Windows, if the total path exceeds 260 (a long data directory + `models--owner--repo/snapshots/<40 digits>/`), the file cannot be written either.
- **Family:** `engine/lemonade.rs` (`LemonadeEngine`, family `lemonade`, server kind, supports no `ModelFormat`: models are in Lemonade's own registry, not files). Installation follows the same path as the other families: `runtimes::github::install` (archive + digest, a `lemond --version` trial, `runtimes.json`); a new version is a new record, the newest is used, and the older one is the rollback path (`LemonadeSettings.runtime` pins a version). Capability reading is `capabilities/lemonade.rs` (`--version`).
- **Process (`lemonade/mod.rs`):** its own lifecycle instead of `ProcessManager` (there is no model file): one `lemond` per Harness, with HTTP and WebSocket ports chosen by Harness (`ports::AUTO_RANGE`), `127.0.0.1`, a random key on every run (in memory and in the child's environment; not written to the UI or log), `--no-broadcast`. Data is under `<data>/lemonade/`: `cache/` (backends Lemonade downloaded), `config/config.json` (keys Harness owns are written on every start, others are preserved), `models/`, `lemond.log`, `settings.json` (llama.cpp backend `auto|vulkan|rocm|cpu`, the pinned version), `catalog.json` (the last run's registry and backend states: the card and gateway use this while the server is off). On Windows a job object (`kill_on_drop`) and on Linux `PDEATHSIG` kill `lemond` and its backends (llama-server...) even if Harness crashes; on a normal exit, `shutdown_now()`. Lemonade's backends run on their own ports starting at 8001 (loopback only).
- **Verification limit:** Harness verifies the embeddable archive; Lemonade checks the model files it pulls against Hugging Face (the log says "Hash verified"). The version of the backend binaries Lemonade downloads (llama.cpp, whisper.cpp...) is pinned in `resources/backend_versions.json` in the archive, but in 2026.41 only a few third-party backends have a SHA-256 table (none for the llama.cpp zips); Harness cannot add this check. The card does not hide this.
- **NPU detection (`lemonade/npu.rs`):** a SetupAPI device dump on Windows (no process is opened), `/sys/bus/pci/devices` on Linux. An AMD (`VEN_1022`) device with `DEV_1502` (XDNA) / `DEV_17F0` (XDNA 2) is an NPU; if the driver is installed, the Windows device name is "NPU Compute Accelerator Device" (class `ComputeAccelerator`). An NPU without a driver shows as "detected, no driver". A desktop without an NPU shows "not detected" and Lemonade itself reports the `flm:npu` backend as `unsupported`; FastFlowLM models do not appear in the registry on that machine either. FastFlowLM (the NPU backend): the code is MIT, the NPU kernels are closed binaries and free to use per the README ("Powered by FastFlowLM" attribution is requested), while TERMS.md sets a commercial license requirement for companies with annual revenue over 10 million dollars; the two conflict, so Harness does not distribute FastFlowLM; it only has Lemonade download it at the user's request on a machine with an NPU, and the card shows the attribution and the terms. The NPU path has not been tested on NPU hardware.
- **Gateway:** downloaded and routable-kind (chat, embedding, rerank, transcription) Lemonade models appear in `Scheduler::external()`/`resolve()` under their Lemonade names as temporary definitions with runtime `lemonade` (`lemonade::definitions`; id `lemonade:<name>`; a registered definition with the same alias wins). `Scheduler::acquire_lemonade` starts `lemond` if needed and sends the request to it with the key (`Lease.upstream` = the `lemond` address, `server_id` = `lemonade`); one concurrent request (llama.cpp single slot), the rest wait in the gateway queue; when the gateway's default idle time passes, models are `unload`ed (`expire_lemonade`). `/v1/audio/transcriptions` forwards Lemonade transcription models to it with `POST /v1/audio/transcriptions` (`audio.rs`; no translation). The gateway cache comes from `catalog.json`: the list is visible before the server starts.
- **UI and API:** the Settings > Runtime > "Lemonade (Ryzen AI NPU)" card (`LemonadeSettings.svelte`; install/update check/version selection and removal, NPU status, server start/stop, llama.cpp backend selection, backend installation, model list + download/delete). Control API `/lemonade*` (reads `read`, changes `admin`), Tauri commands `*_lemonade*`, CLI `harness lemonade ...` (CLI.md).
- **Tests:** unit (NPU classification with real device samples, version/asset selection with a real GitHub response, registry and system info with real `lemond` responses, SSE parsing, config.json merging, command line, definition conversion) and `crates/harness-gateway/tests/lemonade_e2e.rs` (`#[ignore]`: downloads the real release, starts `lemond`, pulls Qwen3-0.6B-GGUF and nomic-embed with Lemonade, does chat/streaming/embedding through the gateway with the Vulkan llama.cpp backend, then stops).

### 14.6. ONNX Chat Models (onnxruntime-genai)

The same `harness-onnx` sidecar serves onnxruntime-genai-format text-generation repositories on Hugging Face (`genai_config.json` + `model.onnx(.data)` + tokenizer; `microsoft/Phi-3-mini-4k-instruct-onnx`, `Phi-4-mini-instruct-onnx`, `onnx-community/*-GENAI-ONNX`, etc.) as chat models without Python. There is no new binary: if `--model` points to a folder with `genai_config.json` (or the decoder `.onnx` inside it), the sidecar does not use the encoder path (`ort`) and loads onnxruntime-genai instead.

- **Library and binding:** ONNX Runtime GenAI 0.17.0 (MIT) comes as `onnxruntime-genai.dll`; there is no ready-made Rust binding (crates like `ort-genai` do not track versions), so `crates/harness-onnx/src/genai.rs` binds the ~30 functions it uses from the C API with `libloading` and wraps them in RAII types (`Genai`, `Model`, `Generation`). Load order: first the managed `DirectML.dll` and `onnxruntime.dll` are loaded by full path (so that the old `onnxruntime.dll` in Windows' System32 does not win when genai loads by name), then `onnxruntime-genai.dll`. Model paths over 150 characters are converted to the `\\?\` form (Microsoft's long file names + deep folders; otherwise ORT says "File doesn't exist").
- **Delivery:** on Windows x64, each of the three ORT builds (`directml`, `cpu`, `cuda`) also carries the GenAI archive: the official `onnxruntime-genai-0.17.0-win-x64-winml.zip` (the build that has the DirectML code path; it also works on CPU, and the CUDA build also gets `onnxruntime-genai-cuda.dll`). The zip is opened like the ORT files, by fetching only the DLLs with HTTP range requests (8 MB), and the archive (GitHub `digest`) and each DLL's SHA-256 are pinned in the code; written to `manifest.json`, and the Settings > Runtime card and `verify`/`remove` work through the same path. Every file named in the spec must be in the manifest: a build installed before GenAI counts as "not installed" and is fetched again. The GenAI library does not exist yet on Linux/macOS; launching a chat model is rejected with `onnx.genai_unsupported_platform`.
- **API (`/v1/chat/completions`, `/chat/completions`):** OpenAI format, streaming (SSE: role chunk, `content` deltas, `finish_reason`, an optional `stream_options.include_usage` chunk, `[DONE]`) and non-streaming; `temperature`, `top_p`, `top_k`, `max_tokens`/`max_completion_tokens` (-1 = until the context is full), `stop` (a string or a list; partial matches are held back when streaming), `seed`, `repeat_penalty`/`repetition_penalty`, `chat_template_kwargs` (e.g. `enable_thinking`); `usage` and llama-server's `timings` fields in the response. Only `text` parts are accepted in a content array (image/audio is 400). `n` is only 1. The embedding/rerank endpoints give a descriptive 400 on a chat model, and the chat endpoint on an encoder. **There is no tool calling:** `tools` is ignored, `caps.tools` is off in the library; the `tool` role passes to the template as is.
- **Chat template:** the model's `chat_template.jinja` file or the `chat_template` field of `tokenizer_config.json` (a string or a list of named templates) is rendered with `minijinja` in `transformers`' environment (`trim_blocks`, `lstrip_blocks`, Python string methods `pycompat`, `raise_exception`, `strftime_now`, `bos_token`/`eos_token`); if there is no template, genai's `OgaTokenizerApplyChatTemplate` is tried. The template's own `raise_exception` becomes a client error (400). The output is encoded with the genai tokenizer; SentencePiece's leading space at the start of the answer is dropped.
- **Generation:** one generation per request (mutex; DirectML/CPU sessions are not shared for concurrent generation, and the gateway scheduler sequences between models). The context is the smaller of `--ctx-size` (Harness `context_size`; 0 = 4096) and the model's `context_length`, and the KV cache is limited per request to `prompt + max_tokens` (genai reserves KV up front; at a 40k context GBs are wasted on DirectML). Sampling defaults come from the `search` section of `genai_config.json`. Every request writes a `harness-onnx: chat: N prompt tokens ..., M generated tokens at X tokens/s` line.
- **Provider:** `--provider auto` follows the model's own `genai_config.json` provider (`dml` -> DirectML, empty -> CPU, `cuda` -> CUDA; `OnnxEngine::provider_of` resolves this before choosing the ORT build); `cpu`/`directml`/`cuda` change the providers in the genai configuration (`OgaConfigClearProviders` + `AppendProvider`). On DirectML, genai captures the whole decoding graph (graph capture); for a generic export that contains an operator DirectML does not run (e.g. `hb-dev/Qwen3-0.6B-ONNX-GenAI`), loading fails with a "graph capture" error and the sidecar retries once with `enable_graph_capture=0` (it works, but on that model the output was corrupted on DirectML: only Microsoft's `directml-*` folders and exports produced for DirectML are recommended).
- **Integration:** `hub_compat::is_genai_repo` (`genai_config.json` at any depth in the list, or an `onnxruntime-genai` tag) treats the repository as ONNX and, with `hub_compatibility_for`, makes it `Runnable` for `text-generation`/`conversational`/untagged tasks (not vision-language genai repositories; a `Chat` capability is added to an untagged repository). `downloader::genai_variants` produces a variant for each `genai_config.json` folder (the graph in the folder, `.onnx.data`, tokenizer, template, configurations; not `.py`/`.md`; preserving the pattern with the repository path) and brings the one that fits this machine to the front: on Windows `directml-*`, then `cpu-*`, then `cuda`/`gpu`; NPU, WebGPU, OpenVINO and QNN folders are removed. The variant drawer shows this order, and the user chooses (`harness pull owner/repo --file <variant-name>`). `models` lists the decoder `.onnx` as `ModelKind::Llm` (named `<repo>-<variant folder>`, size = graph + `.onnx.data`, quantization from the folder name); other graphs in the same folder (vision, embedding) and vision-language models are not listed. `process`/`serve_mode` start these with `ServeMode::Chat`; `process::model_alias` produces the alias from the folder name (so that `model.onnx` does not always give the same name). The gateway and scheduler manage this like a chat server other than llama.cpp (JIT, TTL, unloading). Memory estimate: weights + KV cache (`2*2*layers*kv_heads*head_dim*context`) + `max(256 MiB, weights/8)`; VRAM 0 on the CPU provider.
- **Measurement (Windows, RX 7900 GRE):** `microsoft/Phi-3-mini-4k-instruct-onnx` DirectML int4 (AWQ, block 128): decoding ~100-130 tok/s, first prompt ~0.2-0.6 s, load ~5 s (ORT 1.24.4 DirectML + GenAI 0.17.0). The CPU int4 (RTN, block 32) version of the same model: ~12.5 tok/s (≈9x). Qwen3-0.6B (generic export, CPU): ~68 tok/s.
- **Tests:** unit (`genai_pkg` folder reading/name/provider/KV, `chat` request validation + template + stop filter + response shape, `hub_compat`, `downloader::genai_variants`, `models` scan, `engine::onnx` provider/VRAM/arguments, `onnx_runtime` GenAI constants); `#[ignore]` e2e: `crates/harness-onnx/tests/genai_e2e.rs` (sidecar: streaming, stop, context overflow, DirectML and CPU speed) and `crates/harness-cli/tests/onnx_genai.rs` (`harness serve --gateway` + `harness run`: ORT/GenAI download, library entry, gateway chat).

### 14.7. Safetensors to GGUF Conversion (`harness_core::convert`)

Runs most LLM safetensors repositories (text generation and vision chat, architectures llama.cpp recognizes) with the existing llama.cpp engine: downloads, converts to GGUF, quantizes, and places in the library.

- **An exception to the "no Python required" principle (design decision):** Python runs only at conversion time. The official `convert_hf_to_gguf.py` is Python (it knows every architecture's tensor layout and tokenizer); instead of rewriting it, it is run in a single-purpose, deletable environment that Harness builds itself. Running models, servers, the gateway, the CLI and the UI do not need Python; the system's Python is not touched, and nothing is added to PATH. Rust, not Python, downloads the weights (the Python side converts a folder and exits).
- **Environment (`convert/env.rs`, `<data>/bin/convert-env/`):** it sits next to the runtimes under `bin/`, because `<data>/tools/` is the folder the tool registry scans.
  - `uv/<version>/uv`: the astral-sh/uv 0.12.20 release archive, **SHA-256 pinned in the source** (Windows x64 zip, Linux x64 and macOS arm64 tar.gz); a mismatch rejects the install.
  - `python/`: uv's python-build-standalone download (`uv venv --python 3.12 --managed-python`; uv verifies with its own embedded digests, and the system Python is not searched for).
  - `venv/`: the tag's own `requirements/requirements-convert_hf_to_gguf.txt` file (torch CPU, transformers, numpy, sentencepiece, protobuf) + `tqdm pyyaml requests`, with `--index-strategy unsafe-best-match`. PyPI/PyTorch wheels are verified by uv, but Harness does not pin digests for them (an explicit limitation). torch cannot be skipped: the converter does `import torch` in its first lines. The uv cache is deleted after installation; the environment is about 700 MB (693 MB measured on Windows).
  - `src/<tag>/`: from the GitHub tag archive (~38 MB) of the managed runtime's llama.cpp tag (`.harness-runtime.json`, e.g. `b11559`), only `convert_hf_to_gguf.py`, `conversion/`, `gguf-py/`, `requirements/` are extracted. There is no published digest for this archive; the trust is the TLS connection to GitHub. The tag can only be `^b[0-9]{3,7}$`; old tag sources are deleted. The venv is not rebuilt unless the requirements digest (`requirements_sha256`) changes.
  - `manifest.json`, `hf-home/`. The "GGUF Conversion Environment" card under Settings > Runtime shows the status, installs and deletes; `harness convert env status|install|rm`; `GET/POST/DELETE /convert/env`. Deletion is rejected while a conversion is running (`convert.env_in_use`).
  - Licenses: uv MIT/Apache-2.0, Python PSF, PyTorch BSD-3, Transformers Apache-2.0, llama.cpp and gguf-py MIT. All are downloaded on the user's machine and are not part of the Harness package.
- **Plan (`convert/plan.rs`):** `GET /api/models/<repo>?blobs=true` (`hf_refusal` errors for gated/private repositories). `config.architectures[0]` must be in the converter's registered list; the list is read **from the pinned script itself** (`convert/arch.rs`: `@ModelBase.register(...)` decorators, those derived from `MmprojModel` count as vision; on b11559, 273 text + 74 vision names, a 3-name difference with `--print-supported-models`, which is also caught at run time by the converter's own error). The task must be `text-generation` or `image-text-to-text`. Rejection reasons are keyed: `convert.not_llm`, `no_safetensors`, `adapter_only`, `no_config`, `no_architecture`, `unsupported_architecture`. The downloaded files are only root-level `*.safetensors/.json/.txt/.model/.jinja/.tiktoken`. The result size is parameters × bits/weight (Q4_K_M 4.9; Q5_K_M 5.7; Q6_K 6.6; Q8_0 8.5; F16/BF16 16); required disk = (download + 2·parameters + result) × 1.05 + 256 MB, with free space taken from the model library's drive; if it is not enough, the job does not start.
- **Pipeline (`convert/run.rs`), one conversion at a time (others are `Queued`):**
  1. *Preparation*: the environment is installed if it is missing or the runtime tag changed.
  2. *Download*: `<library>/.cache/convert/<owner>__<repo>/src/` (the library does not scan `.cache`; since it is on the same drive, the final move is a rename). Resume per file with `.part` + `Range`, 4 attempts, SHA-256 verification.
  3. *Conversion*: `convert_hf_to_gguf.py --outtype auto|f16|bf16`; for a vision model a second pass with `--mmproj` (its failure is only a warning).
  4. *Quantization*: `llama-quantize` next to the managed runtime; the intermediate 16-bit file is deleted.
  5. *Placement*: `<library>/<owner>/<repo>-GGUF/<repo>-<TYPE>.gguf` (+ `mmproj-<repo>-F16.gguf`), the GGUF header is verified. `--keep-original` leaves the safetensors under `<library>/<owner>/<repo>/`; otherwise the working folder is deleted.
  - The model definition is created by the UI after completion, not by the core or the CLI (`converts.svelte.ts` -> `ensureDefinition`); the library finds the GGUF by itself anyway.
  - Cancellation: the child process is killed, intermediate files are deleted, and the downloaded `src/` is kept for a retry (`kept_bytes`); it is deleted when the job is removed. Errors are localized with `convert.*` keys (`src/lib/locales/convert.ts`, the CLI reads from the same file); on a converter error, the last lines of its output are appended.
- **Surfaces:** a "convertible" badge on the card of safetensors LLM repositories in the Model Hub (heuristic; the exact check is the plan in the drawer), a `ConvertPanel` in the drawer (quantization choice, size/disk estimate, "keep original files", "Convert to GGUF and Download"), and a `ConvertQueuePanel` under the download queue. Tauri commands `convert_plan`, `convert_start`, `list_convert_jobs`, `cancel_convert_job`, `remove_convert_job`, `clear_finished_conversions`, `get_convert_env`, `install_convert_env`, `cancel_convert_env_install`, `remove_convert_env`; changes arrive with the `converts-changed` event (core `CoreEvent::Convert` / `ConvertRemoved`, `convert` / `convert_removed` in the Control API event stream). Control API: `GET /convert/plan?repo=`, `GET/POST /convert`, `GET/DELETE /convert/{id}`, `POST /convert/{id}/cancel` (`downloads:write`; reads `read`), `GET/POST/DELETE /convert/env` (`admin`). CLI: `harness convert` (see CLI.md), no running instance needed.
- **Tests:** unit (`convert/tests.rs`, 24 tests: architecture parsing, file selection, plan and disk estimate, path layout, output parsing, tag validation, archive filtering, environment status, child process monitoring and cancellation) and the `#[ignore]` end-to-end `crates/harness-gateway/tests/convert_e2e.rs` (real `HuggingFaceTB/SmolLM2-135M-Instruct`: plan, environment, download, conversion, Q4_K_M, library, managed llama-server, a chat reply through the gateway "The capital of France is Paris."; plus cancellation and an invalid type). Measured on Windows: ~85 s in total with the environment ready, ~142 s including the environment. The Linux/macOS uv specifications are defined but untested.

### 14.8. Safetensors Chat Engine (mistral.rs)

Runs Hugging Face safetensors checkpoints (LLM and VLM) on an OpenAI-compatible chat server without converting to GGUF; family `mistral.rs`, binary `mistralrs` (`engine/mistralrs.rs`, `MistralRsEngine`). In practice it is for NVIDIA.

- **Runtime:** there is no managed download (the official Windows release is CPU only): the user builds with `cargo build --release --features cuda -p mistralrs-cli` and adds the folder with `mistralrs(.exe)` as a local runtime (Settings > Runtime > Add Local Folder, family `mistral.rs`; CLI `harness runtime add --local DIR --family mistral.rs`). Adding runs `mistralrs --version`; the version line (`mistralrs 0.7.0`) is recorded with `Engine::version_text`. Capability reading is `capabilities/mistralrs.rs` (`mistralrs serve --help`, clap layout); if help cannot be read, the catalog ships with the documented flags. There is no update/rollback; verification and removal are the same as for other local runtimes.
- **Model:** a folder with `config.json` (a text-generating `architectures`, not a diffusers component) + root-level `*.safetensors` (`is_model_dir`). `models::scan_directories` adds these as `ModelKind::Llm` (`gguf: None`, the path is the folder, `shard_paths` are the weights); the chat template and vision tower are read from the folder; if shards listed in `model.safetensors.index.json` are missing, `is_ready` is false. `model_registry`: format Safetensors, runtime `mistral.rs` (`NeedsRuntime` if not registered). Deletion removes the folder (only inside the library root).
- **Hub:** `hub_compat::mistralrs_compatibility`: if the task is `text-generation` / `image-text-to-text`, the format is Safetensors and the list has `config.json` + `.safetensors` at the root, `Runnable{mistral.rs}`. `downloader::safetensors_variants` downloads the repository as a single variant: the root weights (excluding `consolidated*.safetensors` when shards exist) + configuration, tokenizer, `generation_config.json`, chat template and processor files, under `<library>/<owner>/<repo>/`.
- **Launch:** `server_for` routes the folder to mistral.rs. Arguments: `serve -m <folder> --host 127.0.0.1 -p <port> --no-ui [--cpu (gpu_layers 0)] [--max-seq-len <context>] [--max-seqs <concurrent>] [--pa-context-len <context> (GPU, if the user gave no PagedAttention size)]` + the catalog (`params_mistralrs.toml`: `isq`, `dtype`, `arch`, `max_model_len`, `paged_attn`, `pa_*`) + custom arguments (`-m`, `--host`, `-p`, `--no-ui` are protected). Loopback only. If no context is given, the default chat context comes from the training context in `config.json`. Health is `GET /health` (it listens after the model is loaded). `ServeMode::Chat`, but `ActiveServerInfo::is_llama` is false: `/props`, `/slots`, `/metrics` and verification probes are skipped; the scheduler takes concurrency from the launch (`parallel_slots`, otherwise 8), and there is no KV pool or `/tokenize` counting.
- **Gateway:** `/v1/chat/completions`, `/v1/completions`, `/v1/responses` (and the Ollama / server-side tools paths) go through the same JIT / TTL / queue path; the body's `model` field goes upstream as `default` (the server only knows the model it was started with). `/v1/models` comes from the definitions.
- **Memory estimate (rough):** weights (shrunk by the bit ratio if ISQ is given, not shrunk for an already-quantized checkpoint) + 16-bit KV (`2 × layers × kv heads × head dim × context × 2`) + `max(512 MiB, weights/20)`; it does not touch the llama.cpp estimate (`non_llama_vram_need`, `model_registry::fit_for`).
- **Tests:** argument line, folder recognition, library registration, a Hub listing fixture (`tests/data/hf-safetensors-llm-listing.json`), download variant, local folder validation, family routing, a scheduler without `/props`. `tests/data/mistralrs-serve.help.txt` was written from the documentation, not taken from a real build.

### 14.9. MLX Chat Engine (Apple Silicon)

Runs MLX-format chat models (`mlx-community/...`, including ones with no GGUF) with Apple's MLX through mlx-lm's OpenAI-compatible server; family `mlx` (`engine/mlx.rs`, `MlxEngine`). Apple Silicon only, macOS 14 or later.

- **Runtime:** the managed Python environment `mlx` (`pyenv::envs::MLX`, compiled in on macOS aarch64 only): `python/mlx.in` pins `mlx-lm`, `python/mlx.lock` is its `uv pip compile --generate-hashes` output for `aarch64-apple-darwin` with `MACOSX_DEPLOYMENT_TARGET=14.0` (the MLX wheels start at macOS 14; the app itself runs on 13.3). Installed like the other Python environments (`--require-hashes --no-deps --only-binary :all:`, about 330 MB, no PyTorch). `EnvSpec.min_macos` refuses the build on an older macOS with `pyenv.macos_too_old`; `EnvStatus.refusal` carries that to Settings > Runtime > Installed Runtime > Other Runtimes, which shows the row with the reason instead of hiding it.
- **Worker:** `python/mlx_worker.py`, written next to the environment, starts `mlx_lm.server` in the same process with Harness's policy: it binds 127.0.0.1 whatever it is given; every route but `/health` needs `Authorization: Bearer <HARNESS_WORKER_API_KEY>` (from the environment, removed once read, compared in constant time, never logged; the key is the user's or one made for the run, as for `python-hf`); a request's `model` / `adapters` never loads another path (mlx-lm would load any local folder or adapter it is given); `/v1/models` lists the one model; `--trust-remote-code`, `--adapter-path`, `--draft-model` and `--allowed-origins` are refused (no CORS), and so is any abbreviation of a flag Harness owns or a second `--model` / `--port` (argparse would expand `--trust` to `--trust-remote-code`; abbreviations are also turned off in mlx-lm's parser); without a key it exits instead of serving unauthenticated; proxy variables are cleared; `HF_HUB_OFFLINE=1`. The Rust side refuses the same abbreviations in custom arguments (`params.protected_flag`). **There is no network isolation on macOS** (the Linux `unshare` of `python-hf` has no counterpart): the worker can reach the network like any user process; it only loads the local folder and never runs remote code.
- **Model:** a transformers text-generator folder (`mistralrs::is_checkpoint_dir`) whose weights are MLX's: `config.json` has MLX's `quantization` (`bits`, `group_size`), or the card says `library_name: mlx` (bf16 conversions). mistral.rs can't read those, so `mistralrs::is_model_dir` leaves them. Vision folders (`vision_config`) are the `mlx-vlm` engine's (§14.10). The library lists them (`ModelKind::Llm`, quantization `4bit`) on Apple Silicon only.
- **Hub:** `hub_compat::mlx_compatibility`: an MLX repo (`library_name: mlx` / the `mlx` tag) of `text-generation` (or untagged) with `config.json` + `.safetensors` at the root is `Runnable{mlx}` on Apple Silicon ("Runs with MLX"; "Required: MLX runtime" until it is installed), `UnsupportedPlatform` on macOS 13, unchanged (`Unsupported{mlx}`) elsewhere.
- **Launch:** `<env python> mlx_worker.py --model <folder> --port <port> [--alias <alias>] [--max-tokens N (default 8192; mlx-lm's own is 512)] [--kv-bits 4|8] [--prompt-cache-size N]`; health `GET /health`, OpenAI base `/v1`, no metrics. Serve mode `Chat`, JIT/TTL through the gateway like mistral.rs.
- **Memory estimate (rough):** weights + weights/5 + 300 MiB of unified memory. Measured on an M1 8 GB with Qwen3-4B-Instruct-2507: MLX 4-bit 24.0 tokens/s generation, 158 tokens/s prompt, 2.7 GB peak; the same model as GGUF Q4_K_M on llama.cpp (Metal) 22.4 / 200 tokens/s, 2.7 GB. The difference is small, so there is no rule that picks one over the other: MLX matters for the models that have no GGUF.
- **Tests:** folder recognition (MLX vs mistral.rs, card-only, vision), argument line and protected flags, loopback-only launch, the worker's guards, the lock pins every wheel, the macOS version refusal, Hub verdicts. `harness-gateway/tests/mlx_e2e.rs` (`#[ignore]`, `HS_MLX_MODEL`): builds the environment (17 s), the library finds the folder, a chat through the gateway (first answer 4.7 s with the load), streaming, a tool call, and a request to the worker's port without its key is refused (401).

### 14.10. MLX Vision Engine (mlx-vlm, Apple Silicon)

Chat with images using MLX-format vision-language models (`mlx-community/Qwen3-VL-...`, Gemma 3, ...) through mlx-vlm's server; family `mlx-vlm`, the vision flavour of `MlxEngine` (`MlxEngine::VISION`, `engine/mlx.rs`). Apple Silicon only, macOS 14 or later.

- **Runtime:** its own managed Python environment `mlx-vlm` (`pyenv::envs::MLX_VLM`), because mlx-vlm brings much more than mlx-lm (transformers, OpenCV, datasets, pyarrow, mlx-audio; about 760 MB, no PyTorch). `python/mlx-vlm.in` pins `mlx-vlm`; `python/mlx-vlm.lock` is compiled like `mlx.lock` (`MACOSX_DEPLOYMENT_TARGET=14.0`, `aarch64-apple-darwin`, hashes). The same `min_macos` refusal applies.
- **Worker:** `python/mlx_vlm_worker.py` serves mlx-vlm's FastAPI app in the same process behind an ASGI guard. Only `GET /health` (which answers `{"status":"ok"}`, because mlx-vlm's own lists the model path), `GET /v1/models` (the alias) and `POST /v1/chat/completions` are served. Everything else is 404: management, unload, image generation, audio, embeddings, websockets and CORS preflight. Authentication works as in `mlx`: the `Bearer` key comes from `HARNESS_WORKER_API_KEY`, is compared in constant time and is removed once read. A chat body is checked before mlx-vlm sees it:
  - `adapter_path` / `adapters` / `draft_model` / `model_path` are refused.
  - Every image, audio or video source must be a base64 `data:` URL of its own kind (`data:image/…;base64,`, `data:audio/…`, `data:video/…`). OpenAI `input_audio` base64 is checked and rewritten into a `data:audio/<format>;base64,` URL. mlx-vlm would otherwise fetch an http URL or read any local file a request names, and it takes base64 that starts with `/` for a path. `detail` / `format` must be short labels; files (`file_id`) are refused.
  - Bodies are limited to 64 MB.
  
  mlx-vlm's model loader is pinned to the folder given at start (a request's `model` loads nothing else). `MLX_TRUST_REMOTE_CODE=false` and `trust_remote_code=False` forced on mlx-vlm's loader, `HF_HUB_OFFLINE=1`, proxies and mlx-vlm's own key and model-folder variables are cleared, and it binds 127.0.0.1. As with `mlx`, there is no network isolation on macOS.
- **Model:** an MLX folder (as in §14.9) whose `config.json` has a `vision_config` (`mlx::is_vlm_dir`). The library lists it as a chat model with vision (`ModelCaps.vision` through `mlx::inspect`), so the Playground and the gateway send it images. `engine::server_for` picks `mlx-vlm` for these folders and `mlx` for the others.
- **Hub:** an MLX repo of `image-text-to-text` with `config.json` and safetensors at the root is `Runnable{mlx-vlm}` on Apple Silicon ("Runs with MLX (vision)"; "Required: MLX vision runtime" until it is installed).
- **Launch:** `<env python> mlx_vlm_worker.py --model <folder> --port <port> [--alias <alias>] [--max-tokens N (default 8192)] [--kv-bits 4|8]` (catalog `params_mlx_vlm.toml`). Health, OpenAI base, serve mode, JIT/TTL and the memory estimate are the same as `mlx`.
- **Measured** on an M1 8 GB with Qwen3-VL-2B-Instruct-4bit (1.8 GB): building the environment takes 38 s; the first answer with an image takes 26 s with the load (prompt about 87 tokens/s, generation about 30 tokens/s, 2.0 GB peak).
- **Tests:** vision folder recognition (`mlx-vlm`, not `mlx`, mistral.rs or the Python engine), the argument line, the lock pins every wheel, Hub verdicts. `harness-gateway/tests/mlx_vlm_e2e.rs` (`#[ignore]`, `HS_MLX_VLM_MODEL`) builds the environment, has the library find the folder, sends a red image through the gateway (answer "red"), streams text, and checks that an http URL, a file path and a `file://` image are refused (400).

### 14.11. MLX Audio Engine (mlx-audio text to speech, Apple Silicon)

Text to speech with mlx-audio models from mlx-community (Qwen3-TTS for now, with its preset voices) behind the gateway's `/v1/audio/speech`; family `mlx-audio`, the audio flavour of `MlxEngine` (`MlxEngine::AUDIO`, `mlx::Flavour::Audio`). Apple Silicon only, macOS 14 or later.

- **Runtime:** no environment of its own. The `mlx-vlm` environment (§14.10) already carries mlx-audio 0.5.9 and everything its text-to-speech models need, so installing either engine makes both ready. Settings > Runtime > Installed Runtime > Other Runtimes lists both against the same environment.
- **Worker:** `python/mlx_audio_worker.py` is Harness's own small ASGI server around mlx-audio's model loader; mlx-audio's server is not used. That server has realtime websockets, transcription, voice lists fetched from the Hub and reference audio read from a path the request names, and it imports a package with no wheel. The worker serves:
  - `GET /health`: `{"status":"ok"}`.
  - `GET /v1/models`: the alias and the model's voices.
  - `POST /v1/audio/speech`: `input`, `voice`, `speed` (0.25–4), `language` in; 16-bit mono WAV out.
  
  Every other route and websockets get 404. Bodies are limited to 1 MB, and the input to `--max-chars` (default 4096). Unknown fields are refused, `ref_audio` included, so there is no voice cloning and no file path. A voice must be one of the model's speakers. OpenAI's voice names (`alloy`, …) get the default voice, so OpenAI clients work. The key, 127.0.0.1, `HF_HUB_OFFLINE=1` and cleared proxies work as in the other MLX workers, and `trust_remote_code=False` is forced on transformers' loaders. Requests are spoken one at a time.
- **Model:** `mlx::is_tts_dir`: a folder whose `config.json` `model_type` is a tested architecture (`TTS_TYPES`: `qwen3_tts`), with safetensors and an MLX card (`library_name: mlx-audio` / `mlx`) or MLX quantization. Kokoro is left out because mlx-audio's Kokoro needs misaki and spaCy data fetched at run time; sherpa-onnx already runs Kokoro. The library lists the folder as a pipeline model (`ModelKind::Pipeline`, quantization `8bit`), the way the Python engine lists its speech models.
- **Speech folders are never chat models:** `mlx::is_audio_folder` covers a card with `library_name: mlx-audio`, a speech `pipeline_tag`, or a `model_type` of mlx-audio's speech models (whisper, parakeet, kokoro, qwen3_tts, …). Such folders have configs like `WhisperForConditionalGeneration` and `Qwen3TTSForConditionalGeneration`, and both the `mlx` engine and mistral.rs leave them. MLX-format Whisper and Parakeet recognition models run with mlx-audio on Apple Silicon (macOS 14+), using `mlx_audio_worker.py --task transcription` and the gateway’s `/v1/audio/transcriptions`. The Hub marks supported repositories as running with mlx-audio; transcription has bounded input duration and execution time.
- **Gateway:** `/v1/audio/speech` tries sherpa-onnx voices first. Otherwise a definition that is a Python engine or mlx-audio speech model is leased and posted to (`speech.rs`, `pyhf::post`), and its WAV is encoded to the asked format. For mlx-audio, `voice` and `speed` are passed on. Serve mode `Pipeline`.
- **Hub:** an MLX `text-to-speech` repo whose name is a tested architecture's (`mlx::is_tts_repo`: `qwen3-tts`) is `Runnable{mlx-audio}` ("Speaks with MLX"; "Required: MLX audio runtime").
- **Library (all MLX engines):** MLX folders are recorded with format `mlx` and their engine's family as the runtime, not as GGUF / llama.cpp. Deleting one removes the whole folder (`mlx::delete_model_dir`, only strictly inside the library).
- **Measured** on an M1 8 GB with Qwen3-TTS-12Hz-0.6B-CustomVoice-8bit: the first answer through the gateway took 27 s including the load. After that, a short sentence took 3.7 s, and 4 s of speech took about 3.3 s.
- **Tests:** speech folder recognition (Qwen3-TTS is mlx-audio's; whisper, Kokoro and speech-tagged folders are nobody's chat model), the audio argument line, the worker's checks and routes around a stand-in speaker (system Python), the MLX library records and folder deletion, routing and Hub verdicts. `harness-gateway/tests/mlx_audio_e2e.rs` (`#[ignore]`, `HS_MLX_TTS_MODEL`) runs the library, then a WAV through the gateway with a named voice, then an OpenAI voice name, then an unknown voice (400 listing the model's voices).


### Experimental audio.cpp TTS

audio.cpp is **experimental and off by default**. Enable it in Settings > Runtime > Installed Runtime > Other Runtimes after confirming the risk notice. Its local server has no authentication or Host/Origin checks and accepts server-side file paths (`voice_ref`, JSON `audio`, and `/v1/tasks/*`). While running, a web page on this computer can send requests and pass file paths directly to that server. Loopback binding does not remove this risk.

Disabled engines refuse gateway, Load, and CLI launches. Models remain visible in the Hub and library with an experimental engine requirement. Workers start on demand, bind only to `127.0.0.1` on a random free port (excluding 11435, 11440, and 11500), and use `--no-ui` without `--ui-management`. Harness stops the process after five minutes without requests; `--idle-unload-ms 300000` also releases model memory. Pinned models do not bypass this timeout or start at gateway startup.

The gateway forwards only `POST /v1/audio/speech`, rebuilding model, input, discovered voice, speed, response format, and optional inline `voice_ref` (`type: base64`, decoded size at most 5 MiB). String/path references and undiscovered voices return 400. Other fields are dropped; transcriptions, alignments, tasks, models management, and all other worker routes are never forwarded. These gateway restrictions do not secure direct access to the worker port.

## CrispASR Speech Recognition

[CrispASR](https://github.com/CrispStrobe/CrispASR/tree/v0.8.43) (MIT) is a managed native ServerEngine pinned to v0.8.43. Settings > Runtime > Installed Runtime > Other Runtimes installs it; the runtime registry updates/removes it. Windows AMD uses Vulkan, Linux AMD prefers HIP then Vulkan, NVIDIA uses CUDA, Apple Silicon uses Metal, and other platforms use CPU. The runtime record stores the chosen backend.

Only CrispASR-format ASR GGUFs are supported: Parakeet, Canary, Cohere, Qwen3-ASR, Voxtral, Nemotron, GigaAM, Granite, VibeVoice, Moonshine, SenseVoice and cstr wav2vec2/HuBERT/Data2Vec. Hub ASR `cstr/*-GGUF` repositories offer GGUF variants with fitting Q5/Q4 recommendations. Architecture/provenance are checked; Cohere additionally requires CrispASR tensor names. handy-computer exports are unsupported except `handy-computer/canary-180m-flash-gguf`. TTS, codecs and chat are outside scope. Source-only repositories retain their status. Whisper ggml .bin, sherpa-onnx catalog models and ONNX CTC retain their engines.

Playground > Speech > Transcribe, the gateway audio API and `harness transcribe audio.wav --model <alias>` use this engine (CLI also accepts supported local GGUF paths). It starts on demand and managed workers stop after the gateway idle TTL. A worker exit reports an upstream error; the next request can restart it. Bind is 127.0.0.1 only, on a random free port outside the automatic server range. Each run gets a fresh random key through CRISPASR_API_KEYS, never argv; Harness sends Bearer authentication. CORS and automatic model downloading are disabled.

Only POST /v1/audio/transcriptions and POST /v1/audio/translations reach the worker. Multipart is rebuilt with file bytes, the definition alias as model, language, prompt, response_format, temperature and timestamp_granularities (including the [] spelling). Unknown fields or model/path fields such as diarize_embedder, lid_model, punc_model, truecase_model and voice return 400. Worker /load, /inference, /backends, chat and speech synthesis are never forwarded. Ollama /api/chat, /api/generate and /api/embed return 400 for these models before starting a worker.

The CrispASR worker never downloads anything from the network. Its helper models (language detection `ggml-tiny.bin` and punctuation restoration `fireredpunc-q4_k.gguf`) are pinned to a repository revision with a size and SHA-256 and come through Harness's own verified downloader: they show in the download queue and in Settings > Runtime > Installed Runtime > Other Runtimes > CrispASR Helper Models (Download / Remove), and reach the worker only as local paths (`--lid-model`, `--punc-model`). A missing language model starts the worker with `--lid-backend off` and the gateway answers a request without a language with a 400; a missing punctuation model means `--no-punctuation`. Every launch passes `--cache-dir <data>/cache/crispasr` and sets `CRISPASR_CACHE_DIR` to it, and the worker's proxy variables point at a closed local port. On Linux the worker is not put in a network namespace: CrispASR can only listen on a TCP port, which a namespace without network would hide from the gateway (python workers listen on a Unix socket for that reason), so the closed proxy, the empty cache folder and the absent download flags are the guard there. A model downloaded or removed while a worker runs takes effect when that worker restarts.
